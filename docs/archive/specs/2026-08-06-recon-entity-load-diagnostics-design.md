# Recon 엔티티-로드 러버밴딩 — 진단 계측 설계

> **이 슬라이스의 산출물은 "고침"이 아니라 "원인 확정"이다.** 계측기를 깔고 실험을 수행해
> A(서버 틱 밀림) / B(클라 프레임 저하) / 제3의 원인 / 재현 안 됨 중 하나로 못 박는다.
> 대응(AoI 도입이든 서버 틱 예산 최적화든)은 결과를 보고 **별도 슬라이스**로 간다.

## 1. 배경

**관찰 (2026-06-24, 사용자):** 서버에 엔티티를 많이 스폰한 상태로 입장하면, 내 캐릭터가 **주변에
아무것도 없는 빈 곳에서 점프**해도 통통 튕기는 reconciliation(러버밴딩)이 보인다. 충돌과 무관하니
타이밍·부하가 유발한 recon이다.

그때 계측기(클라 FPS·엔티티 수·서버 프레임 시간)를 프로토타입했으나 **"나중에 각 잡고 다시 보자"며
전체 롤백**했고, 원인은 미확정 상태로 파킹됐다. 각 잡을 시점이 지금이다.

**그사이 바뀐 것:** 2026-07-09에 캐릭터 이동이 **다이나믹 PhysX → 클·서 공유 키네마틱 컨트롤러**로
전환됐다(예측=권위). 이 변경만으로 지면 reconciliation이 상당 부분 소멸했다. 따라서 **지금도 재현되는지
자체가 불확실**하며, "재현 안 됨"도 정당한 결론이다.

### 왜 갭이 점프에서만 보이나

```
recon 갭 ≈ 타이밍 오차 × 그 순간의 속도
```

가만히 서 있으면 속도가 0에 가까워 같은 타이밍 오차가 눈에 안 보인다. 점프는 수직 속도가 커서
**같은 오차를 증폭해 보여주는 확대경**이다. 그래서 실험 동작을 점프로 고정한다.

## 2. 목표 / 비목표

| | |
|---|---|
| **목표** | 원인을 A / B / 제3 / 재현 안 됨 중 하나로 확정하고, 되돌리기 실험으로 **엔티티 수가 원인임을 귀속**한다 |
| **목표** | 그 판정에 쓴 계측 항목을 **정식 HUD 항목으로 남긴다**(성능 회귀는 또 온다) |
| **비목표** | 고치는 것. AoI(관심영역) 도입도, 서버 틱 예산 최적화도 이 슬라이스가 아니다 |
| **비목표** | 대시·외삽 등 다른 동기화 주제. 별도 트랙이다 |

## 3. 원인 가설

| | 가설 | 메커니즘 | 직접 지표 |
|---|---|---|---|
| **A** | 서버 틱 밀림 | 엔티티 증가 → 서버 per-tick 작업(World.Tick + Physics.Simulate + AI) 증가 → 틱 레이트 미달 → 입력이 서버에서 다른 시점·상태에 적용 → recon | 서버 프레임 ms vs 틱 예산 (서버) / **서버틱 지연** (클라에서 관측) |
| **B** | 클라 프레임 저하 | 서버가 (AoI 없이) 모든 엔티티를 보냄 → 클라가 전부 렌더·보간 → FPS 하락 → 예측 루프 흔들림 → recon | **클라 FPS** |
| **제3** | 대역폭·입력 타이밍 | 스냅 청크 증가로 손실·지연, 입력 prune | 도착 간격 max · prune · seqGap |

### 원인 A를 서버 없이 클라에서 보는 법

서버의 **벽시계**(Mirror 서버 시간)는 부하와 무관하게 흐른다. 반면 **틱 카운터**는 프레임이 밀리면
뒤처지고, `TickCatchUp.ClampTarget`이 프레임당 캐치업에 상한을 걸기 때문에 한 번 밀리면 따라잡지
못한다. 따라서 클라에서

```
서버틱 지연 = 서버틱추정(벽시계 기반)  −  방금 받은 내 캐릭 스냅의 tick
```

이 값이 **자라면 서버가 밀리고 있다**. 절대값에는 편도지연이 상수로 깔려 있으므로 보는 것은
*절대값이 아니라 변동과 증가*다.

## 4. 계측 항목

| 지표 | 무엇을 말해주나 | 출처 | 상태 |
|---|---|---|---|
| **FPS / 프레임 ms** | 원인 B의 직접 증거 | `Time.smoothDeltaTime` | 신규 (getter) |
| **엔티티 수** | 실험 조건 그 자체 | `EntityRegistry.Count` | 신규 (주입 + getter) |
| **원격 보간 쿠션** | 스냅 도착이 얼마나 들쭉날쭉한가 | `InterpolationDelayEstimator.Cushion` | **이미 계산 중** — 노출만 |
| **서버틱 지연** | 서버가 벽시계 대비 밀렸나 = 원인 A | `ServerTickEstimate − 최신 수신 스냅 tick` | 신규 |
| **스냅 도착 간격 avg/max** | 송신 케이던스 건강도 | 스냅 배치 수신 시각 | 신규 |
| Recon last/avg/max · Lead · RTT · 입력타이밍(d·prune·seqGap) · 스냅샷 수 | 판정의 대조군 | 기존 | 있음 |

**측정 원천 = `EntitySnapsToC.Tick`, 기록 지점 = 기존 틱당-1회 dedupe 자리.**

- `UserEntitySnapToC`는 **tick 필드가 없다**(HP·MP·레벨·스탯만). 여기서 tick을 얻으려면 proto에
  필드를 새로 박아야 하는데, 그건 5절에서 기각한 경로다.
- `EntitySnapsToC`는 **내 캐릭터를 포함한 전 엔티티**를 담는다(내 것은 `reconciler.AddServerSnap`으로
  분기). 따라서 적이 0마리인 기준선 조건에서도 내 캐릭터 때문에 **매 틱 도착한다** — 원래 우려했던
  "엔티티가 없으면 값이 죽는다"는 성립하지 않는다.
- MTU 서브셋 청킹으로 한 틱에 여러 메시지가 오는 문제는 이미 해결돼 있다.
  `GameEntityMessageHandler`가 `entitySnapsToC.Tick > lastRecordedArrivalTick` 가드로 **틱당 1회만**
  기록해 보간 시계를 먹인다. 우리 통계도 **같은 가드 안**에 넣는다.

## 5. 구조 — 어디에 무엇이 사는가

### GameFramework (신규 1개, 테스트 대상)

- **`GameFramework.Netcode.SnapshotArrivalStats`** — 스냅 도착을 `(서버tick, 도착시각)`으로 받아
  **최신 tick · 도착 간격 avg/max**를 노출하는 순수 계산 홀더. `Reset()` 보유.
  - **왜 GameFramework인가:** 앱 비종속(도착 간격 통계)이고 순수 계산이라 EditMode 단위 테스트가
    가능하다. 클라 코드는 전부 Assembly-CSharp라 asmdef 참조가 불가능해 EditMode 테스트를 못 붙인다.
    이미 짝이 되는 `InterpolationDelayEstimator`가 같은 폴더에 산다.
  - 도착 간격 계산은 **틱당 1회**만 기록하는 호출자 규약을 전제한다(중복·역순 tick은 무시).

### 클라 (배선)

| 파일 | 변경 |
|---|---|
| `GameEntityMessageHandler` | 스냅 배치 수신부의 **기존 틱당-1회 dedupe 블록 안**에서 `SnapshotArrivalStats.Record(tick, now)` 호출 (보간 시계 기록 바로 옆) |
| `DebugHudViewModel` | FPS · 엔티티수 · 쿠션 · 서버틱지연 · 도착간격 getter 추가 (+ `EntityRegistry`·`SnapshotArrivalStats`·`RemoteInterpolationClock` 주입) |
| `RemoteInterpolationClock` | 쿠션 읽기 프로퍼티 노출 (내부 estimator 값) |
| `DebugHud.uxml` / `DebugHudView` | 줄 추가 + **[리셋] 버튼** |
| `GameLifetimeScope` | `SnapshotArrivalStats` 등록 |

**리셋이 왜 필수인가:** `ReconciliationStats.Max`는 **누적 최대**다. 한 번 튀면 세션이 끝날 때까지
남으므로, 조건을 바꿔 가며 비교하는 실험에서 부하 조건의 max가 기준선 조건의 잔재일 수 있다.
조건 전환마다 리셋한다. 리셋 대상 = Recon 통계 + 도착 간격 통계.

### 서버 (신규 2개, 진단 전용)

둘 다 `LOPGame.unity`의 **기존 DebugHud GameObject**에 붙인다.

- **`DebugEnemySpawner`** — `[ContextMenu]`로 "적 N마리 즉시 스폰" / "적 전부 제거".
  - Unity 관용구(인스펙터 우클릭)라 **Game 뷰 포커스가 필요 없다.** 에디터 포커스로 인한 입력 소실에
    데인 적이 있어 키 입력 방식을 피했다.
- **`TickHealthLogger`** — 몇 초마다 한 줄:
  `tick=X 기대=Y 밀림=Y−X 프레임=Zms 예산=Wms 엔티티=N`.
  - **기본 꺼짐**(직렬화 필드). 평소 서버 로그를 오염시키지 않는다.
  - "기대 tick" = `elapsedTime / interval`. 실제 tick과의 차가 곧 밀림이다.

**왜 서버는 HUD가 아니라 로그인가:** 눈에 보이는 문제는 클라 쪽이라 주 계기판은 클라 HUD다.
서버는 원인 A를 *확증*할 한 줄만 남기면 된다. 와이어(proto)에 진단용 필드를 영구히 박는 대안은
판정력이 같은데 비용(MessageId 재생성 위험 + 영구 필드)만 더 든다 — 기각.

## 6. 부하를 만드는 수단

현재 서버는 **10초에 1마리, 상한 100마리**로만 적을 스폰한다(`GameRuleSystem`). 즉 "엔티티 많은
상태"를 만들려면 **16분을 기다려야** 하고, 줄일 방법은 없다.

`DebugEnemySpawner`가 이걸 즉시 조절 가능하게 만든다. **이것이 이 설계의 성패를 가른다** —
06-24에 판정을 못 낸 구조적 이유가 "조건을 같은 세션 안에서 바꿔 볼 수 없었다"였기 때문이다.
조건이 서로 다른 실행이면 그사이 프레임·네트워크 상태가 달라져 "엔티티 때문인가"를 가릴 수 없다.

## 7. 실험 프로토콜

**엔티티 수만 바꾸고 나머지는 전부 고정한다.**

| 단계 | 조건 | 하는 일 |
|---|---|---|
| 0 | 준비 | 서버 로거 켜기 · 클라 HUD 열기 · 주변에 아무것도 없는 빈 좌표로 이동 |
| 1 | **기준선** (엔티티 최소) | 리셋 → 제자리 점프 ×10 → HUD 스크린샷 + 서버 로그 |
| 2 | **부하** (+50) | `Spawn 50` → 30초 안정 → 리셋 → **같은 자리 같은 점프 ×10** → 기록 |
| 3 | **되돌리기** | `Despawn all` → 30초 안정 → 리셋 → 같은 점프 ×10 → 기록 |
| 4 | (선택) | 부하 조건에 지연 150ms를 주입해 반복 — 갭 증폭 여부 |

**3단계가 이 설계의 핵심이다.** 값이 기준선으로 돌아와야 "엔티티가 원인"이라고 말할 수 있다.
안 돌아오면 원인은 엔티티가 아니라 **시간 경과·세션 누적**(누수 등)이고, 그건 완전히 다른 조사다.

> 로컬 2-에디터는 RTT가 와이어 지연이 아니라 프레임/스로틀 지연이다. 4단계(지연 주입)는 그래서
> *선택*이다 — 주 실험의 변수는 엔티티 수 하나로 유지한다.

## 8. 판정표

**결론은 `Recon max`(리셋 이후 누적)로 읽는다.** `Recon avg`는 **약 1.2초 이동평균**(60샘플 × 50Hz)이라
점프가 끝난 뒤 화면을 보면 세 조건 모두 0에 수렴한다 — 그걸로 판정하면 러버밴딩이 있어도
"재현 안 됨"으로 떨어진다.

| FPS | 서버틱 지연 / 도착간격 · 쿠션 | **Recon max** | 판정 |
|---|---|---|---|
| 급락 | 정상 | 증가 | **B — 클라 프레임 저하.** 대응 후보: AoI, 렌더/보간 비용 |
| 정상 | 증가·요동 | 증가 | **A — 서버 틱 밀림.** 확증 = 서버 콘솔의 `[TickUpdater] catch-up capped` 경고. 대응 후보: 서버 틱 예산 최적화 |
| 급락 | 증가·요동 | 증가 | **A+B 동시.** 서버부터 — 서버가 밀리면 클라 수신 패턴이 바뀌지만 그 반대는 아니다 |
| 정상 | 정상 | 증가 | **제3의 원인.** `Prune`·`SeqGap`을 먼저 본다 |
| 정상 | 정상 | **정상** | **재현 안 됨.** 07-09 키네마틱 이행이 이미 해소한 것으로 보고 파킹 항목을 닫는다 |

**원인 A의 확증은 `lag > 0`이 아니다.** `lag`은 서버 프레임이 느려지기만 해도(캐치업 상한에 안 걸리고
정상적으로 몰아 처리해도) 양수로 자란다. "못 따라가 영구히 밀림"과 "뭉쳐서 처리함"은 대응이 다르므로,
상한에 실제로 걸릴 때만 뜨는 `catch-up capped` 경고를 판별자로 쓴다.

**각 지표의 한계 (실험 해석 시 감안):**

| 지표 | 한계 |
|---|---|
| `Snap gap` | 한 틱의 **청크 하나만 도착해도** 최신 tick이 전진한다 → 부하로 청크가 늘수록 오히려 둔감. 대역폭 의심은 `Prune`·`SeqGap`으로 |
| `Cushion` | **100.0ms에서 포화**(상한 = 송신간격 × 5). 그 값이 찍히면 측정값이 아니라 천장 |
| `Snap lag` | 누산기가 없는 순간값이라 ±1틱으로 깜빡인다. 다만 밀림은 영구 누적이라 순간값으로도 판정은 된다 |
| 되돌리기 조건 | 디스폰이 실험 전 자동 스폰분까지 지우므로 **기준선보다 엔티티가 더 적다.** 방향이 보수적이라 귀속 논리는 유지되지만, 조건마다 실제 `Entities` 값을 기록할 것 |

**"재현 안 됨"이 나올 가능성은 낮지 않다.** 06-24 관찰은 이동이 다이나믹 PhysX이던 시절이다.
그 경우에도 계측기는 남으므로 손해가 아니다.

### 실측으로 바로잡은 판정 기준 (2026-08-06, 구현 중 확인)

| | 처음 생각 | 실제 |
|---|---|---|
| 서버 `lag`의 건강한 값 | `0` | **`-1`이 평평하게 유지.** `tick`은 "다음에 처리할 틱", `processibleTick`은 "지금 처리 가능한 틱"이라 한 칸 차이가 구조적으로 남는다. 볼 것은 절대값이 아니라 **`-1`에서 양수로 자라는가** |
| `frameMaxMs > budgetMs` | 원인 A의 확증 | **확증이 아니다.** 캐치업 여유가 `8 × interval`(≈160ms)이라 유휴 에디터도 예산(20ms)을 넘긴다(실측 37~40ms). 이걸 기준으로 쓰면 **기준선에서부터 원인 A로 오판**한다 |
| 입력 타이밍 4개(`d`/`prune`/`seqGap`) | 리셋 버튼이 지움 | **못 지운다.** 서버가 보낸 최신 요약을 덮어쓰는 홀더라 값의 주인이 서버다. **조건 간 차이**로 읽어야 한다 |

## 9. 테스트 · 검증

| 대상 | 방법 |
|---|---|
| `SnapshotArrivalStats` | **EditMode TDD** (GameFramework) — 간격 평균·최대, 리셋, 중복/역순 tick 무시 |
| 서버 두 컴포넌트 | 로직이 거의 없다(스폰 호출·로그 포맷) → 수동 확인 |
| HUD 표시 | 수동 |
| 컴파일 | GameFramework는 `file:` 공유라 즉시. **클라 `Assets/` 코드는 워크트리에서 검증 불가** — 에디터가 main 체크아웃을 본다. 머지 후 UnityMCP로 클·서 각각 force refresh + compile이 진짜 관문 |
| **기능** | **7절 프로토콜을 실제로 수행하고 8절 표로 판정, 결과를 ROADMAP에 기록.** 계측기만 깔고 끝내지 않는다 |

## 10. 알려진 위험

| | 위험 | 대응 |
|---|---|---|
| 1 | ~~**서버 MonoBehaviour의 DI 경로**~~ — **확인 완료(계획 단계).** 서버 `DebugHudHost`가 `[SceneInjectMonoBehaviour]` + `[Inject]` 필드 주입으로 이미 게임 스코프의 `IRunner`를 받고 있다. 신규 두 컴포넌트도 같은 GameObject·같은 방식이면 그대로 성립 | 위험 해소. 같은 속성·같은 GameObject를 쓴다 |
| 2 | 스폰 50마리가 서버·클라 어느 쪽도 흔들지 못해 **아무 신호도 안 나올 수 있다** | 마릿수를 인자로 받게 해 100·200까지 올려 본다. 상한(현재 100)도 디버그 스폰에는 적용하지 않는다 |
| 3 | 지표가 전부 정상인데 **육안으로는 튄다**고 느껴질 수 있다 | 그 자체가 결과다 — "제3의 원인"으로 분류하고 렌더 보정(`RenderCorrectionSmoother`) 쪽을 다음 후보로 남긴다 |
| 4 | 서버 씬 변경(컴포넌트 추가)이 커밋에 포함된다 | 서버 `LOPGame.unity` 변경은 의도된 것으로 커밋. 로컬 픽스처(`GameRuleSystem` 스폰 수 등)와 섞이지 않게 분리 |
| 5 | **매치 5분 자동 종료가 실험을 자른다.** 서버가 경과 5분에 매치를 끝내는데 3조건 프로토콜이 3~5분이다. 3단계(되돌리기)가 잘리면 귀속 판정이 불가능해 실험이 무효가 된다 | HUD의 `Elapsed`를 보며 진행. 여유가 없으면 방을 새로 만들고 시작 |
| 6 | **기존 버그 — 세션 0개일 때 디스폰이 서버 틱을 죽인다.** `EntitySpawner.FlushDespawns`의 `GetAllSessions().DefaultIfEmpty()`가 `null` 하나를 내고 `session.Send()`가 터진다. 이 예외가 틱 코루틴 안에서 나므로 **코루틴이 죽어 서버 틱이 통째로 멈춘다.** 이 브랜치가 만든 게 아니고 여기서 고치지 않는다 | **디스폰은 클라가 접속한 상태에서만.** 실험 종료 시 디스폰 먼저, 클라 내리기 나중. 별건으로 수정 검토 |

## 11. 산업 표준 매핑

- **`SnapshotArrivalStats`(도착 간격·지터 통계)** — Fiedler의 snapshot interpolation 계열이 표준적으로
  재는 값이다. 우리 `InterpolationDelayEstimator`(적응형 쿠션)가 이미 같은 원리를 쓰고 있어 이름·자리를
  그 짝으로 맞춘다.
- **서버틱 지연을 클라에서 관측** — Unity Netcode for Entities의 `ServerCommandAge`(서버가 잰 값을
  클라에 되먹여 클럭을 조정)와 같은 발상이되, 방향이 반대다. 우리는 *클라가 스스로* 벽시계 기준
  서버틱 추정과 실제 스냅 tick을 대조한다. 서버 코드 0으로 같은 사실을 얻기 위한 선택이다.
- **`[ContextMenu]` 디버그 액션** — 에디터에서 런타임 액션을 거는 Unity 관용구. 별도 디버그 UI를
  짓지 않고 인스펙터를 쓰는 표준 방식.
- **부하 실험의 되돌리기(3단계)** — 성능 조사에서 조건을 원위치시켜 값이 복귀하는지 보는 것은
  인과 귀속의 기본 절차다(A/B/A 디자인).
