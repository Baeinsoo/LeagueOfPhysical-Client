# 매치 시작 틱 정렬 — 출발선을 제 위치에 놓는다

> 08-09 3층 작업 중 발견. 매치 시작 직후 입력 **162개가 통째로 폐기**되고, 그동안 서버 캐릭터는
> 원점에 정지해 있었다(클라 화면에서는 걷고 있었다).
>
> **개정 이력**: 초판은 "클라가 낡은 `gameInfo`를 받아서"를 원인으로 지목했으나 **틀렸다.**
> 코드를 확인하니 맵 로딩은 `gameInfo` 수신 *전에* 끝나고 `StartGameAsync`는 바로 다음 줄이다.
> 진짜 원인은 서버가 보내는 값이 그 순간 **자기모순**이라는 것 하나다.

## 1. 증상

접속 직후 창에서:

```
timing[dAvg=142.4 dMax=208 prune=162 seqGap=0]
srvPos=(0.00, 0.00, 0.00)      ← 서버 캐릭터가 안 움직임
predPos=(-0.14, 0.00, -0.14)   ← 클라는 이미 걷고 있음
```

`d = serverTick − inputTick`이 **+142**(≈2.8초). 클라 입력이 서버가 이미 지나간 틱을 가리켜 전량
폐기된다. **사용자에게는 "게임 시작 직후 몇 초간 조작이 안 먹는다"로 보인다.**

## 2. 원인 — 서버가 자기모순인 값을 보낸다

### 서버가 매치 시작에서 하는 일

```csharp
runner.Run(0, TICK_INTERVAL, 0);        // 틱 0, 경과시간 0
...
elapsedTime = networkTime.ServerNow;    // 매 프레임. = Mirror.NetworkTime.time = 프로세스 가동 시간
```

시드는 0인데 다음 프레임에 `elapsedTime`이 **프로세스 가동 시간**으로 덮인다. 서버가 33초 떠
있었다면 `processibleTick = 1680`인데 `tick`은 0이다. 틱 루프는 프레임당 최대 8틱만 따라잡으므로
**매치 시작 직후 3.5초를 8배속으로 질주**한다.

즉 **`Run`에 넘긴 0은 한 프레임 만에 무의미해진다.** 틱의 실질 원점은 "매치 시작"이 아니라
"서버 프로세스 가동 시각"이다.

### 그 모순이 클라로 복사된다

```csharp
Tick        = runner.tickUpdater.tick,          // 질주 중이라 낮음 (예: 200)
ElapsedTime = runner.tickUpdater.elapsedTime,   // 이미 최종값 33.6초 (= 1680틱)
```

같은 순간에 읽은 두 값이 **서로 맞지 않는다.** 클라는 이걸 충실히 따른다:

```csharp
runner.Run(201, interval, 33.6);
//         ↑ 틱 201        ↑ 이 시각이면 1680이어야 함
```

받는 즉시 1479틱 뒤처진 걸 발견하고 클라도 질주한다.

> **클라의 "서버가 준 틱 다음부터 시작한다" 설계 자체는 멀쩡하다.** 받은 값이 모순이라 따라간
> 것뿐이다. 클라는 피해자다.

> **로컬 아티팩트가 아니다.** 로컬은 에디터 서버 가동 시간이 길어 과장될 뿐, 실환경도 룸 컨테이너
> 부팅~매치 시작만큼 같은 일이 난다.

## 3. 개념 정리 — 앞서는 것과 오차 보정은 다른 장치다

이 슬라이스를 이해하는 열쇠다.

| | 무엇 | 어떻게 |
|---|---|---|
| **앞서는 것** | 클라가 서버보다 앞선 시각에서 달림 | **출발선을 앞에 놓는다** (오프셋) |
| **오차 보정** | 살짝 어긋난 걸 되돌림 | **속도를 ±5% 조절** (`ClockDilator`) |

**클라의 틱 레이트는 서버와 같다.** 빨리 달려서 앞서는 게 아니라 시작점이 앞이다
(`netcode-redesign.md` §4.1: "클라 tick rate ≠ 빨라지는 게 아님. 시작점이 앞쪽일 뿐").

```
서버 지금:   틱 1680
편도 지연:   +5틱
앞서갈 여유: +5틱
클라 시작:   틱 1690   ← 처음부터 10틱 앞

클라 1690에 발사 ──5틱 비행──▶ 서버 1685에 도착 ──5틱 여유──▶ 서버 1690에 사용
```

**지금 버그의 본질**: 출발선을 뒤에 놓고, 오차 보정 장치(속도)로 그걸 메우려 한다. 그 장치는
최대 5%라 0.4초 격차를 닫는 데 8초가 걸린다 — 원래 그런 용도가 아니다.

## 4. 해법 — 양쪽 다 자기 시계에서 유도한다

```csharp
// 서버 (LOPRoom) — 자기모순 제거
double now = networkTime.ServerNow;
runner.Run((long)(now / TICK_INTERVAL), TICK_INTERVAL, now);

// 클라 (LOPRoom) — 출발선을 제 위치(앞쪽)에
double target = networkTime.PredictedTime + leadState.AheadMargin;
runner.Run((long)(target / gameInfo.Interval), gameInfo.Interval, target);
```

`predictedTime`이 이미 "서버 시각 + 편도지연"이므로 `+ AheadMargin`이 §3의 계산 그대로다.

### 서버만 고치면 안 되나 — 잔여가 남는다

서버만 고치면 1차 원인은 사라진다. 그러나 클라는 여전히 `gameInfo.ElapsedTime`(= 보낸 시점)에서
출발하는데 목표는 `predictedTime + margin`(= 지금 + 여유)이다. 차이 ≈ **왕복지연 + 여유
(0.3~0.4초 = 15~20틱)**. `ClockDilator`는 0.5초 미만이면 snap하지 않고 5%씩만 좁히므로 수렴에
몇 초가 걸리고, 그동안 입력이 늦게 도착한다.

> 얄궂게도 지연이 더 큰 환경(0.5초 초과)에서는 snap이 걸려 즉시 해결된다. 애매하게 좋은 환경이
> 제일 오래 걸린다.

## 5. 산업 표준 — 확인 완료

Unity Netcode for Entities 공식 문서:

> "The network time system calculates an **initial estimate of the server time based on the round
> trip time and latest received snapshot** from the server."

> "When the client receives an initial estimate, it makes **small changes to the time progress**
> rather than doing **large changes to the current time**."

| | DOTS | 우리 (현재) |
|---|---|---|
| 시작 시각 출처 | **왕복지연 + 받은 스냅샷**에서 계산 | 입장 메시지의 `gameInfo.Tick` |
| 그게 언제 값인가 | **지금** | 보낸 순간(과거) |
| 이후 조정 | 진행 **속도**만 | 같음 |
| 서버 피드백 미세조정 | ✅ command-age | ✅ `InputTimingToC` |

**세 줄 중 두 줄은 이미 같다.** 다른 건 첫 줄뿐이고, DOTS의 순서는 **①첫 추정치로 위치를 잡고 →
②그 뒤로는 속도만**이다. 우리는 ①을 건너뛰고 ②로 다 하려 한다.

우리가 쓰는 **Mirror에도 "입장 시 시작 틱을 받는다"는 개념이 없다** — `NetworkTime`은 계속
동기화되는 추정치일 뿐이다. `gameInfo.Tick`은 LOP가 따로 만든 것이다.

## 6. 검토한 대안 — 매치 기준 원점(틱 0 = 매치 시작)

개념적으로 깔끔하고 로그도 읽기 쉽다. **기각 이유**: 매치 시작 시각(epoch)을 양쪽이 공유해야 해서
새 와이어 필드와 전파 경로가 생기는데, 얻는 건 *숫자의 가독성*뿐이다. 틱을 키로만 쓰는 코드(§7)에는
차이가 없다. 리플레이·관전이 실제로 필요해지면 그때 도입한다 — 그 경우에도 "틱은 시계에서 유도"
원칙은 유지되고 시계만 바뀐다.

## 7. 영향 범위 — 실제로 확인한 것

틱 번호의 *크기*에 기대는 코드가 있는지 확인했다.

| | 결과 |
|---|---|
| `SequenceBuffer` (스냅샷·입력 히스토리) | ✅ 무관. `((tick % cap) + cap) % cap` + 병렬 틱 배열로 stale 판별 |
| `SnapshotHistory` | ✅ 위에 위임 |
| `Reconciler` 앵커 · 서버 `PruneBefore` | ✅ 상대 비교만 |
| 결정론 RNG (틱을 키에 씀) | ✅ 양쪽이 같은 틱을 보면 됨 — 이 변경이 그 일치를 *개선*한다 |
| `gameInfo.Tick` / `ElapsedTime` | ⚠️ **아무도 안 읽게 된다** |

**`GameInfo`의 나머지 필드는 계속 필요하다** — 스냅샷이 대체하지 못한다:

| 필드 | 왜 필요한가 |
|---|---|
| `Interval` | 틱 간격은 서버가 정하는 **설정값**. 시계만으론 알 수 없다 |
| `MatchSeed` | 결정론 RNG 시드 |
| `EntityId` | **"어느 게 내 캐릭터냐"** — 스냅샷은 상태만 담고 소유를 안 알려준다 |
| `EntityCreationDatas` | 스냅샷은 매 틱 바뀌는 값만 담는다. 캐릭터 코드·외형 같은 *생성 정보*는 없다 |

## 8. 위험

| | 위험 | 대응 |
|---|---|---|
| 1 | 접속 직후 `NetworkTime`이 아직 수렴 중이면 시작 틱이 어긋난다 | ⚠️ **이게 실제로 일어났고, 클라 쪽 진짜 원인이었다.** 아래 §8.1 |
| 2 | 서버 틱 번호가 프로세스 가동 시간에 비례해 커진다 | `long`이라 오버플로 없음. 키로만 쓰여 무해(§7) |
| 3 | `gameInfo.Tick`을 나중에 누가 다시 읽으면 낡은 값을 믿는다 | "쓰지 않는다" 주석. 필드 제거는 proto 정리 슬라이스 |
| 4 | 질주가 사라지며 가려져 있던 다른 시작 문제가 드러날 수 있다 | 드러나면 그게 이득. 별도로 다룬다 |

### 8.1 위험 1이 현실이 됐다 — 시계가 맞기 전에 시작하고 있었다

초판에서 "시작 시점엔 이미 접속 후 몇 초라 수렴 후다"라고 넘겨짚었는데 **틀렸다.**
`StartGameAsync`는 `JoinRoomServerAsync` 바로 다음 줄이고, 그건 접속 직후다.

Mirror 소스가 확인해 준다:

```csharp
public static double predictedTime
    => NetworkServer.active
        ? localTime                                // 서버: 자기 시계
        : localTime + predictionErrorUnadjusted;   // 클라: 자기 시계 + 서버가 알려준 오차
```

클라의 `localTime`은 **서버 시간이 아니라 자기 프로세스 가동 시간**이고, 보정값
`predictionErrorUnadjusted`는 EWMA 20샘플 × 100ms = **약 2초**에 걸쳐 수렴한다. 수렴 전에
출발하면 시계가 뒤늦게 제자리를 찾으며 점프하고(실측 5.7초), `ClockDilator`가 0.5초 초과라 snap →
`processibleTick`이 점프 → 틱이 **284개를 8배속으로 갈아 넘긴다**. 그게 시작 시 드르륵이다.

**시드 출처는 무관했다.** `gameInfo`든 `TargetTime`이든 *목표 자체가 출발 후에 움직이므로*
결과가 같다 — 실측 288 ↔ 284.

**대응(§4에 추가): 시계가 안정될 때까지 기다렸다 시작한다.** 보정값이 3연속 10ms 미만으로
움직이면 수렴으로 보고 출발, 5초 타임아웃(못 기다려도 시작 — 막으면 매치가 안 열린다).
DOTS도 동기 전에는 시뮬을 돌리지 않는다.

### 8.2 시도했다가 되돌린 것 — snap-forward (짓지 말 것)

"격차가 크면 시뮬 없이 틱만 점프한다"를 만들어 **실제로 동작까지 확인**했다(313틱 건너뜀).
그런데 **표준이 아니고 필요도 증명되지 않아 되돌렸다.** 다시 짓기 전에 아래를 볼 것.

**① 표준이 아니다 — Unity는 오히려 걷어냈다.**

> "previously, the server would **skip ticks** if batching wasn't enough, while now it'll
> **do its best to catch up** on those missing ticks on the subsequent frames if time allows."
> — Netcode for Entities 1.8.0 changelog

밀렸을 때 표준이 쓰는 방법은 **배칭**이다 — 두 틱을 각각 dt로 돌리는 대신 한 틱을 2×dt로.
버리는 게 아니라 묶는 것이다. 클라 쪽 표준도 건너뛰기가 아니라 롤백 후 재시뮬이다.

> 되돌리기 전 근거로 "락스텝은 못 하지만 서버 권위는 건너뛸 수 있다"고 적었는데, 그건 출처 없는
> 추론이었다. 실제 서버 권위 엔진의 답은 배칭 또는 따라잡기다.

**② `ClockDilator`가 이미 점진 구간을 덮는다.**

작은 오차는 ±5% 속도 조절로 슬금슬금 맞춘다 — Unity가 말하는 "small changes to the time
progress"가 정확히 이것이다. 틱은 그걸 자연히 따라오므로 **점진 구간엔 손댈 게 없다.**
문제는 오직 `ClockDilator`가 **점프(0.5초 초과)** 할 때뿐이다.

**③ 그 점프를 A가 막는다.** 시작 직후가 유일하게 큰 점프가 나던 자리였고, A가 그걸 없앴다.
남는 건 게임 중 0.5초 이상 멈춤인데, 멈춰 있는 동안엔 플레이어도 입력을 못 하므로 잃을 게 없다.

**더 정교하게 다뤄야 할 일이 생기면 `ClockDilator` 쪽을 고도화한다** — 정책을 시계와 틱 두 층에
나눠 두지 않는다(그 불일치가 원래 문제였다).

### 8.3 최종 — 클라 쪽 원인은 시계가 아니라 **클라가 멈춰 있던 것**

§8.1의 "시계 수렴 전 시작"도 **틀린 진단이었다.** 계측이 뒤집었다.

출발 시점과 3초 뒤 값을 대조했더니:

```
출발:   predErr=-169.359  localTime=272.382  rtt=4.616
3초후:  predErr=-172.730  localTime=281.696  rtt=2.240
```

**`UniTask.Delay(3000)`을 걸었는데 `localTime`이 9.31초 흘렀다** — 그 사이 클라 에디터가
**6.3초 멈춰 있었다.** `rtt=4.616`(설정은 150ms)도 pong을 처리 못 하고 있었다는 같은 증거다.

즉 시계가 뒤늦게 움직인 게 아니라 **클라가 멈춰 있었고**, 그동안 실제 시간이 흘러
`processibleTick`이 300틱 앞서간 것이다. 옛 대기(2.8초)가 통했던 이유도 시계를 기다려서가 아니라
**그 시간 동안 로딩 부하를 흘려보냈기** 때문 — 우연이었다. 그래서 "제대로 고친" 새 기준
(첫 pong = 0ms)은 아무것도 못 막았다.

**결론: 클라 시작 드르륵은 넷코드 문제가 아니라 시작 시 멈춤이다.**

- **메인 에디터만 겪는다** — MPPM 2번 클라는 로딩도 빠르고 부드럽다
- 빌드에서 멈춤이 1초 이하로 줄면 50틱이라 7프레임(≈0.1초)에 소화돼 **대책 없이 해결**된다
- **빌드에서 재보기 전에는 넷코드를 더 손대지 않는다**

> **이 절에서 배운 것:** 이 슬라이스에서 추론으로 세 번 단언하고 세 번 틀렸다
> (EWMA 수렴 3.1초 / 서버 권위면 건너뛰기 가능 / 첫 pong이면 충분). 코드를 읽고 계산까지
> 맞춰봐도 빗나갔고, **계측 한 번**이 전부 갈랐다. 시작할 때 이 로그부터 붙였어야 했다.
