# 다이브 충전 대시 설계

프로토타입에만 있던 **다이브 충전 대시**를 넷코드 게임으로 옮긴다. 떨어질수록 게이지가 빨리
차고, 가득 차면 버튼이 활성화되며, 누르면 0.2초 동안 전진 2배로 수평 직선을 그린다.

> 상위 기획은 `2026-08-05-flappy-multiplayer-concept-design.md`. 이 문서는 그 기획의 **대시 부분만**
> 실제 넷코드 구조에 맞춰 확정한 것이다. 같은 기획의 **추격자**는 다음 슬라이스다.

## 1. 왜 지금 이것인가

**지금 이 게임은 실력이 반영될 통로가 실수 감점뿐이다.** 전진 속도가 상수라 x가 오직 틱의
함수이고, 등수를 가르는 것은 충돌(스턴 40틱 = 8.8m)과 스침(틱의 일부)밖에 없다. 2026-09-01
라이브에서 **서로 다른 높이에서 다른 경로로 난 두 새가 같은 틱·같은 깊이로 공동 1위**가 나온 것이
그 증거다 — 우연이 아니라 구조가 그렇다.

대시는 그 구조를 깬다. **전진 속도가 처음으로 조작의 결과가 된다.** 그리고 게이지가 다이브로
차므로, 빨라지는 방법이 "위험하게 낮게 나는 것"이 된다 — 리스크와 보상이 한 숫자로 붙는다.

## 2. 규칙

| | 값 · 규칙 |
|---|---|
| 버튼 | 게이지가 **가득 찼을 때만** 활성화. 누르면 **전부** 소비(부분 사용 없음) |
| 대시 지속 | **0.2초** |
| 대시 중 전진 | **2배** |
| 대시 중 세로 | **속도 0 + 중력 없음** → 완전한 수평 직선 |
| 기본 충전 | 초당 **0.13** |
| 다이브 충전 | 낙하 속도에 비례해 최대 **+1.2**/초 |
| 시작 게이지 | **0.6** (첫 대시를 오래 기다리지 않게) |
| 대시 중 플랩 | **무시.** 수평 직선이 깨지면 대시가 아니다 |
| 대시 중 충돌 | **평소와 동일하게 스턴.** 대시는 그 자리에서 끝나고 게이지는 이미 없다 |
| 스턴 중 충전 | 막지 않는다. 다만 멈춰 있어 낙하가 없으므로 기본 속도로만 찬다 |
| 박치기 | **없음.** 새끼리 충돌 자체가 없다 |

### 충전 식

```
add    = 기본 + (떨어지는 중이면  다이브계수 × min(낙하속도, 최대낙하) / 최대낙하  아니면 0)
게이지 = min(1, 게이지 + add × dt)
```

낙하 속도를 **최대낙하로 나눠 정규화**하는 것이 핵심이다. 프로토타입과 지금 게임은 물리값이
다른데(프로토타입 중력 24·최대낙하 16, 현재 70·30), 정규화 덕분에 "최고 속도로 떨어지면 최대
충전"이라는 감각이 값과 무관하게 그대로 옮겨진다.

체감으로는 이렇다:

| 상황 | 가득 차는 데 |
|---|---|
| 안 떨어지고 수평 유지 | 약 **7.7초** |
| 최고 속도로 계속 낙하 | 약 **0.75초** |

### 대시 중 충돌을 특별 취급하지 않는 이유

대시가 **도박**이어야 하기 때문이다. 무적으로 두면 "막히면 대시로 뚫는" 탈출 카드가 되어, 누를
자리를 고르는 판단이 사라진다. 평소와 같은 스턴이면 *앞이 뚫린 것을 보고* 눌러야 하고, 눈감고
누르면 2배 속도로 벽에 박는다. **언제 쓰느냐가 실력이 된다.**

부수 효과로 새 규칙이 하나도 안 늘어난다 — 충돌 처리 코드는 대시를 알 필요가 없다.

## 4. 상태와 시스템

### `FlappyDash` (컴포넌트, Anemic)

```
float Charge          0~1. 1이면 발동 가능
float DashRemaining   대시가 끝날 때까지 남은 초. 0이면 대시 중 아님
```

데이터만 갖는다. 판단과 변경은 전부 시스템에 둔다 — `FlappyStun`과 같은 짝이다.

### `FlappyDashSystem`

`FlappyStunSystem`과 같은 모양의 무상태 로직 클래스다.

- `bool IsDashing(entity)` — 대시 중인가
- `bool TryActivate(entity)` — 게이지가 가득이고 대시 중이 아닐 때만 발동. 게이지 0, 남은시간 = 지속
- `void Cancel(entity)` — 남은시간 0. 스턴에 들어갈 때 부른다
- `void Tick(entity, dt)` — 남은시간 감소, 게이지 충전

스턴과 마찬가지로 **부동소수점 잔여를 Epsilon으로 0 취급**한다. 그러지 않으면 마지막 한 틱이
남아 대시가 한 틱 더 지속된 것처럼 보인다.

### 틱 순서 (`FlappyWorld.Mutation`)

```
① 스턴 틱                     남은 시간 감소
② 스턴 중이면 속도 0으로 두고 이 새는 여기서 끝
③ 대시 발동 판정 + 대시 틱     입력에 dash가 있으면 TryActivate, 그다음 남은시간 감소·충전
④ 이동 (FlappyMoveSystem)      대시 중이면 x 2배 · vy 0 · 중력 없음
⑤ 맵에 막히며 이동             부딪히면 스턴 진입 + 대시 Cancel
```

**③이 ④보다 앞이어야 한다.** 뒤에 두면 누른 틱의 중력을 한 번 먹고 나서 대시가 시작돼, 완전한
수평 직선이 아니라 살짝 처진 선이 된다. 플랩이 중력 *뒤에* 와야 하는 것과 같은 이유이며, 그
근거는 `FlappyMoveSystem`에 이미 주석으로 남아 있다.

**⑤에서 Cancel**한다 — 스턴은 이동을 멈추는데 대시 타이머만 계속 흐르면, 스턴이 풀렸을 때 남은
대시가 되살아나 "맞고 나서 갑자기 튀어나가는" 그림이 된다.

## 5. 와이어

### 입력

`InputCommand`에 `bool dash = 10`을 더한다. Skydive가 `posture`/`glide`/`posing`을 같은 자리에
얹은 것과 같은 패턴이라 새 메시지를 만들지 않는다.

### 스냅

```
int64 dash_end_tick = 20;   // 대시가 끝나는 절대 틱. 0 = 대시 중 아님
float dash_charge   = 21;   // 0~1
```

**남은시간이 아니라 "끝나는 절대 틱"으로 보낸다.** 스냅이 늦게 도착해도 값이 낡지 않기
때문이며, 스턴이 이미 그렇게 한다. 변환은 `FlappyTickDuration` 한 곳에만 두고 양쪽이 쓴다 —
같은 식을 두 번 적으면 **올림 때문에 한 틱을 더 세는 실수**가 재발한다(스턴에서 실제로 겪었고,
받는 쪽만 한 틱 더 얼어 있게 만들었다).

게이지는 0~1의 연속값이라 그냥 `float`으로 보낸다.

## 6. 서버 권위와 보정

**대시 발동 자격의 권위는 서버다.** 클라는 예측하고, 서버가 아니라고 하면 되돌린다.

- 내 새는 `Simulated`이므로 클·서가 **같은 `FlappyDashSystem` 구체 코드**를 돌린다. 입력이 같으면
  결과가 같다 — 예측을 따로 짜지 않는다.
- 어긋남은 `FlappyServerCorrectionHandler`가 잡는다. 지금 스턴만 비교하는 자리에 **대시 켜짐/꺼짐**
  비교를 더한다. 남은 시간의 미세한 차이는 다음 틱이 좁히므로 켜짐/꺼짐만 본다(스턴과 동일).
- 남의 새는 시뮬 대상이 아니다. `dash_end_tick`으로 **연출만** 받는다.

### `TryGetSavedStun` → `TryGetSavedState`

보정 핸들러는 "앵커 틱에 내가 그때 예측했던 값"을 꺼내 서버 값과 비교한다. 지금은 스턴 전용
접근자가 하나 있는데, 대시용으로 하나 더 만들면 나란한 함수가 둘이 된다. **저장된 상태를 통째로
돌려주는 하나로 바꾸고** 핸들러가 거기서 스턴과 대시를 같이 읽는다.

### 게이지를 굳이 보내는 이유

게이지는 세로 속도에서 파생되는 결정론적 값이라 "안 보내도 스스로 수렴한다"고 볼 수 있다. 그러나
**입력이 하나 유실되면 갈린 채로 남는다** — 그러면 내 화면엔 가득인데 눌러도 안 나가는 상태가
되고, 원인이 화면에 전혀 안 보인다. 스턴에서 정확히 그 문제를 겪고 서버 권위로 바꾼 자리다.
매 틱 float 하나는 그 재발을 막는 값으로 싸다.

## 7. 되감기

`FlappySavedState`에 `Charge`와 `DashRemaining`을 더한다. 위치·속도는 `WorldBase`가 이미 담으므로
게임 고유 상태만 담는 그 struct의 원칙 그대로다.

되감기가 이 둘을 안 담으면, 재생 구간에서 대시가 다시 발동되거나 반대로 사라져 **라이브와 재생이
갈린다.** 그 상태로는 보정이 자기 자신과 싸운다.

## 8. UI

```
flap-root
├── flap-surface     전체 화면. 누르면 날갯짓
├── dash-button      그 위. 오른쪽 아래(엄지 자리)
└── flap-hint
```

**버튼이 곧 게이지다.** 별도 막대를 두지 않고 버튼 자신이 차오른다 — 가득 차기 전엔 흐리고 안
눌리며, 차면 밝아지고 눌린다. "지금 쓸 수 있나"를 한 곳만 보고 알게 하는 것이 목적이다.

**버튼을 누른 것이 날갯짓으로 새어 나가지 않게** 이벤트를 버튼에서 끊는다. 안 그러면 대시할
때마다 같이 날아오른다. 데스크톱은 Shift/D도 받는다(프로토타입과 동일).

**게이지 값은 R3가 아니라 매 프레임 읽는다.** 아키텍처 가이드라인이 정한 대로 *월드의 연속
상태는 pull, 이산 사건만 event*다. 매 틱 변하는 값에 프로퍼티 변경 이벤트를 거는 것은 그
자체가 낭비다. `FlapPadView`는 이미 매 프레임 키보드를 폴링하므로 붙일 자리가 있다.

## 9. 튜닝값

`#FlappyConfig.xlsx`에 네 열을 더하고 Luban으로 굽는다.

| 열 | 값 | 뜻 |
|---|---|---|
| `dash_mult` | 2 | 대시 중 전진 배수 |
| `dash_duration` | 0.2 | 대시 지속(초) |
| `dash_charge_base` | 0.13 | 초당 기본 충전 |
| `dash_charge_dive` | 1.2 | 최고 속도 낙하 시 더해지는 초당 충전 |

시작 게이지 0.6은 컨피그로 빼지 않는다 — 튜닝 대상이 아니라 "첫 대시를 오래 기다리지 않게"
하는 초기값이고, 늘리면 컨피그가 그만큼 커진다. 필요해지면 그때 뺀다.

## 10. 테스트

시뮬은 순수 C#이므로 EditMode로 덮는다.

- 안 떨어지면 기본 속도로만 찬다 / 최고 속도로 떨어지면 최대 속도로 찬다 / 1을 넘지 않는다
- 가득 차야만 발동한다 · 발동하면 게이지가 0이 된다 · 대시 중에는 재발동하지 않는다
- 대시 중에는 전진이 2배이고 세로 속도가 0이며 중력이 안 먹는다
- 대시 중 플랩 입력은 무시된다
- 지속이 지나면 정확히 원래 속도로 돌아온다 (한 틱 더 가지 않는다)
- 스턴에 들어가면 대시가 즉시 끝난다
- 저장·복원이 게이지와 남은시간을 왕복시킨다
- 남은시간 ↔ 끝나는 틱 변환이 한 틱을 더 세지 않는다

**전부 일부러 깨뜨려 빨강을 확인한다.** 이 저장소에서 "통과하지만 아무것도 안 지키는 테스트"가
한 슬라이스에 여섯 개 나온 적이 있다.

## 11. 범위 밖

- **추격자** — 같은 기획의 다음 슬라이스. 대시가 버는 "여유거리"라는 통화가 먼저 있어야 의미가 생긴다
- **대시 박치기** — 뺐다. 새끼리 충돌 자체가 없다
- **스타트 부스트**(`FlappyRaceStart`의 타이밍 보너스) — 대시와 같은 경로를 쓰지만 별개 기능이다
- **대시 연출**(`FlappyDashFx`: 잔상·스피드라인·화면 흔들림) — 프로토타입에 있고, 규칙이 선 뒤에 얹는다
- **부스트 존**(`FlappyBoostZone`) — 지형 보상. 별개 축

## 12. 열린 항목

- **대시가 등수를 실제로 가르는가** — 넣고 나서 두 클라로 재 봐야 안다. 안 갈리면 배수나 지속을
  올리는 것이 아니라 **충전 속도**를 먼저 본다. 자주 쓸 수 있어야 차이가 쌓인다
- **대시 중 결승선 통과** — 2배 속도로 넘으면 한 틱에 더 깊이 넘는다. 지금 등수 규칙은 틱이
  먼저이고 깊이는 동틱 타이브레이크라 문제가 없지만, 실제로 그 장면이 나오면 다시 본다
