# Flappy 맵 — 무너지는 고층 도시

Flappy Race 맵의 세계관·아트 방향. 그레이박스로 검증이 끝난 코스에 **옷을 입히고 60초→90초에
이야기를 넣는다.** 관문 기하는 손대지 않는다.

> 앞선 문서: [2026-09-15 판정면 정렬과 층 가르기](2026-09-15-flappy-map-25d-depth-alignment-design.md)가
> ①(렌더러만 당겨 판정면 정렬)·④(시각 정직성 검사)를 실었고, **②(층 가르기)를 열린 채로 남겼다.**
> 이 문서가 그 ②를 잇는다. 읽는 규칙은 그 문서에서 물려받는다.

## 1. 왜 이 일을 하나

코스 구조는 2026-09-19에 검증이 끝났다 — 원본 플래피의 난이도를 창(4.36m)·박자(1.67초)·전진
속도(6.8m/s)·카메라(20m)로 옮겨 왔고, 봇 클린런으로 통과 가능함이 증명됐다. 남은 것은 **보이는
것**이다. 세 가지가 비어 있다.

- **전부 회색 박스다.** 파이프 70개·바닥·천장이 재질 하나(`FloorNeutral`)를 같이 쓴다.
- **깊이에 아무것도 없다.** 게임 평면(z=0)과 배경(z=62) 사이 **60m가 통째로 비어 있다.**
  2.5D가 안 읽히는 이유는 깊이가 없어서가 아니라 깊이에 아무것도 없어서다.
- **추격자에 정체가 없다.** `FlappyChaserView`의 주석이 그대로 말한다 —
  *"추격자의 정체는 아트 단계 몫이라 지금은 붉은 판으로 자리만 잡는다."* 그 단계가 지금이다.

## 2. 잰 것

카메라는 `FlappyCameraFollow.fixedZ = -20`, 세로 FOV 40°. 게임 평면은 z=0.

```
거리 d에서 화면이 담는 세로 = 2·d·tan(20°) = 0.728·d
가로는 16:9에서 세로 × 1.778
```

| | 카메라에서 | 화면 세로 | 비고 |
|---|---|---|---|
| 게임 평면 z=0 | 20m | **14.56m** | 통로 14.56m와 정확히 맞다 |
| (비어 있는 자리) | 20~82m | — | **여기가 문제** |
| 배경 도시 z=62 | 82m | **59.7m** | 그런데 건물 높이가 1~6.4m뿐 |

**배경 도시는 화면 세로의 10%만 채운다.** 큐브 64개가 x −10~557m에 깔려 있지만 높이가 작아
화면 아래쪽 자잘한 덩어리로 보인다. 스카이라인이 아니라 자갈이다.

화면 가로는 **약 25.9m**다. 이 값이 §3.6에서 추격자 판단을 뒤집는다.

## 3. 결정

### 3.1 읽는 규칙 — 이 문서의 상위법

09-15에서 물려받는다: **"선명하고 테두리가 밝으면 닿는 것."**

깊이에 무엇을 채우든 이 규칙이 먼저다. 아래 모든 결정은 이것에 종속되고, 충돌하면 이것이 이긴다
(§3.5가 실제 충돌 사례다).

### 3.2 세 층으로 가른다

```
카메라 ●
  │   20m           34m                        82m
  │    ↓             ↓                          ↓
  │ ┌───────┐   ┌──────────┐            ┌────────────────┐
  │ │ 게임  │   │  중간층  │            │   배경 도시    │
  │ │ 평면  │   │  (신설)  │            │   (키운다)     │
  │ └───────┘   └──────────┘            └────────────────┘
  │   z=0          z≈14                       z=62
  │ 화면 14.6m    화면 24.8m                 화면 59.7m
  │ 콜라이더 O    콜라이더 X                 콜라이더 X
```

| 층 | 무엇 | 처리 | 왜 |
|---|---|---|---|
| **게임 평면** | 슬래브·철골 (파이프) | 선명 · 따뜻 · 윗면 밝게 | 유일하게 닿는 것 |
| **중간층** *(신설)* | 무너진 건물 골조 실루엣 | 채도↓ · 어둡게 · 안개 조금 | **2.5D를 만드는 층** |
| **배경** | 기존 큐브 64개 | 안개로 거의 씻김 · 차가운 청색 | 높이 6m → 40~60m, x를 612m까지 |

중간층·배경은 게임 평면 **뒤**에 있으므로 새를 절대 가리지 못한다. 원근 때문에 화면상 통로
안쪽으로 파고들어 보이는데(`h·d/(C+d)` — 중간층은 높이의 41%, 배경은 76%), **그 파고듦이 곧
"깊이가 보인다"의 정체다.** 씻겨 있으면 배경으로 읽히고 선명하면 함정이 되므로 §3.1이 먼저다.

**콜라이더는 게임 평면에만.** 검사로 강제한다(§5).

### 3.3 구간 셋 — 90초에 이야기를 넣는다

경기 길이의 기본을 **90초**로 올린다. 런타임에 60초를 가정하는 곳은 없다 —
`RaceSeconds`는 빌더의 생성 입력(`FlappyClassicCourseBuilder.cs`)이고 경기는 결승선 통과로
끝난다(Archery의 `MatchDurationTicks` 같은 제한이 Flappy엔 없다). **맵마다 다른 길이 = 맵마다
다른 결승선 x**로 이미 표현되므로 90초는 기본값일 뿐이다.

| | 60초 (종전) | **90초 (기본)** |
|---|---|---|
| 코스 길이 | 419m | **612m** |
| 관문 | 35개 | **약 53개** |
| 구간 하나 | 140m · 20.6초 · 12관문 | **204m · 30초 · 18관문** |

구간 경계는 **코스 길이의 ⅓·⅔로 계산한다** — 미터를 박지 않는다(길이가 바뀌면 따라 움직여야
한다. 4.912가 문서에 남아 거짓말을 했던 일의 재발 방지).

| | 구간 1 `0~204m` | 구간 2 `204~408m` | 구간 3 `408~612m` |
|---|---|---|---|
| 이름 | 아직 서 있는 사무실 | 반쯤 무너진 중층 | 붕괴 한가운데 |
| 게임 평면 | 온전한 콘크리트 · 유리 | 깨진 슬래브 · 노출 철근 | 그을린 철골 · 잔불 |
| 중간층 | 멀쩡한 골조 | 휘어진 골조 · 기울어짐 | 무너진 더미 · 연기 기둥 |
| 하늘 · 안개 | 서늘한 아침빛, 옅음 | 먼지 섞인 회색 | 주황 먼지빛, 짙음 |

**박자(11.4m / 1.67초)와 통로(14.56m)는 불변이다.** 같은 규칙을 더 길게 깔 뿐이므로 난이도
재검증이 아니라 봇 클린런 재확인이다.

### 3.4 안개 하나가 세 층을 알아서 가른다

이 설계에서 제일 싼 부분이다. `ExponentialSquared` 안개는 거리의 **제곱**으로 먹으므로
(`씻김 = 1 − exp(−(밀도·거리)²)`), 층이 20/34/82m로 떨어져 있으면 **한 값이 세 층을 다르게
씻긴다.**

| 안개 밀도 | 게임 평면 20m | 중간층 34m | 배경 82m |
|---|---|---|---|
| 0.009 (구간 1) | **3.2%** 선명 | 8.9% | 42.0% 씻김 |
| 0.016 (구간 3) | **9.7%** 아직 선명 | 25.6% | **82.1%** 거의 사라짐 |

**층별로 재질 채도를 따로 만들 필요가 없다** — 거리가 그 일을 한다. 재질은 *색조*만 구간별로
나눈다. 위 두 값은 시작점이고 에디터에서 눈으로 보고 정한다(Skydive가 같은 방식으로 3000m
스케일에서 0.0013을 정했다 — `2026-09-03-skydive-atmosphere-design.md` §3.1).

### 3.5 ⚠️ 밝기는 낮추지 않는다 — 규칙 충돌을 여기서 해소한다

"뒤로 갈수록 어두워진다"를 그대로 하면 **제일 어려운 구간에서 관문이 제일 안 보인다.**
난이도를 아트로 몰래 올리는 셈이라 정직하지 않고, §3.1을 정면으로 위반한다.

**구간이 진행돼도 게임 평면의 밝기·대비는 낮추지 않는다.** 그을음은 *색조*로만 표현하고,
잔불 발광이 오히려 윗면 테두리를 더 밝게 만든다. 어두워지는 것은 **하늘 · 중간층 · 배경**뿐이다.

### 3.6 추격자 = 붕괴 전선 — 그리고 안 보인다는 사실

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 모양 | 2m×300m×2m 붉은 큐브 | z로 **앞으로** 8~10m 늘린 날 — 다가오는 면이 보인다 |
| 색 | 단색 빨강 | 어두운 먼지벽 + 앞 가장자리 잔불 발광 |
| 효과 | 없음 | 벽 앞으로 흘러나오는 먼지 파티클 |

앞으로 늘리는 것은 **공짜다**(09-15 §③). 뒤로 뻗으면 틈을 좁아 보이게 만들지만 앞은 아니고,
추격자는 애초에 콜라이더가 없다(판정은 서버의 x 비교뿐).

**그런데 잘 날면 이 벽은 화면에 한 번도 안 나온다.** 재 봤다:

| | 값 |
|---|---|
| 새 | 6.8 m/s |
| 추격자 | 4.33에서 출발 → 39.9초에 최대 **6.18** m/s |
| 결승선 시점의 간격 | 60초 코스 112m → **90초 코스 130m** |
| 화면 가로 | **25.9m** → 벽은 **5개 화면 뒤** |

그래서 허구의 무게를 옮긴다:

- **허구는 벽이 아니라 세계가 진다.** 앞의 도시가 무너지는 중이라는 것은 구간 1→3의 변화가
  보여 준다. 이것은 항상 화면에 있다.
- **벽은 실패의 얼굴이다.** 멈칫하거나 스턴을 먹었을 때만 등장한다 — 그때 "먼지벽이 화면을
  덮으며 다가온다"가 제값을 한다. 잘 날면 안 보이는 것이 맞다.
- 허구 요약: **붕괴는 양쪽에서 온다.** 앞의 건물도 무너지는 중이고(그래서 구간 3이 최악),
  뒤의 벽은 이미 무너진 자리다. 새는 그 사이 좁아지는 띠를 지난다. 잘하든 못하든 항상 참이다.

## 4. 어디에 사는가

| 만드는 것 | 레포 |
|---|---|
| 재질 (구간 3종 · 중간층 · 배경 개정 · 추격자 벽) | **Art** (`Assets/Art/Environment/FlappyRace/`) |
| 중간층·배경 오브젝트 | **Art** (`Scenes/FlappyRaceMap.unity`) |
| 코스 빌더 확장 (612m · 구간별 재질 · 중간층/배경 굽기) | 클라 `Assets/Scripts/Editor/FlappyClassicCourseBuilder.cs` |
| 구간 경계 규칙 (순수 C#) | 클라 `Assets/Scripts/MapTools/CourseSection*.cs` |
| 진행 대기 — 안개·하늘을 x로 보간 | 클라 `Assets/Scripts/Game/FlappyAtmosphere.cs` |
| 추격자 벽 모양·재질 | 클라 `FlappyChaserView.cs` + Art 재질 |
| 층 규약 검사 | 클라 `Assets/Scripts/MapTools/` + `Editor/FlappyMapPlayabilityCheck.cs` |
| **LOP-Shared / 서버** | **손대지 않는다** |

> **불변식:** 시뮬(Shared)이나 서버를 건드려야 할 일이 생기면 설계가 틀렸다는 신호다.
> 이 슬라이스는 전부 프레젠테이션이다. (Skydive 대기 슬라이스와 같은 불변식.)

> **⚠️ 안개는 씬에 두지 않는다 (2026-09-20 추가 — Skydive가 이미 당한 것).** 맵 씬은
> **additive로 로드된다**(`LOPGameFactory`). 유니티는 **활성 씬의 `RenderSettings`만** 적용하므로,
> 맵 씬에 `m_Fog: 1`을 저장해도 활성 씬(`m_Fog: 0`)이 이겨서 안개가 안 켜진다.
> 그래서 **안개 on/off·모드·색·밀도는 전부 `FlappyAtmosphere`가 런타임에 쓴다.** 씬의
> `RenderSettings`는 에디터에서 눈으로 보려고 맞춰 두는 값일 뿐 런타임 진실원본이 아니다.
> (`SkydiveAtmosphere.Apply`의 주석이 같은 말을 한다.)

`FlappyAtmosphere`는 `SkydiveAtmosphere`와 짝을 맞춘 이름이다 — 같은 일(안개·하늘을 매 프레임
갱신)을 **고도(y) 대신 진행(x)** 으로 한다. 월드에서 읽기만 하는 pull이다.

## 5. 검증 — 무엇을 기계가 지키나

아트는 유닛테스트가 안 된다. 시험할 수 있는 것만 정직하게 나눈다.

**기계가 지키는 것**

1. **층 규약 검사 (새로 만든다)** — 씬의 렌더러를 z대역으로 분류하고 셋을 확인한다.
   - 게임 평면(새의 z대역 `[-0.45, +0.45]`와 겹치는 것)에만 콜라이더가 있다
   - 중간층·배경에는 콜라이더가 **없다**
   - 게임 평면 블록은 게임 평면 재질만 쓴다(배경 재질을 쓰면 실패)

   이 검사가 **이 작업에서 나올 수 있는 최악의 두 버그**를 구조적으로 막는다 —
   *배경인데 부딪힌다* / *장애물인데 배경처럼 보인다.*

2. **시각 정직성 검사 (이미 있다)** — 판정면 뒤 두께. 중간층·배경은 대상에서 빠져야 한다
   (`BlockDepthScan.IsGameplayBlock`이 대역 겹침으로 이미 거른다 — 새 층을 넣고 재확인한다).

3. **구간 경계 규칙 (EditMode 테스트)** — ⅓·⅔ 계산, 경계가 어느 구간에 속하는지, 길이가
   바뀌면 경계가 따라 움직이는지. 순수 C#이라 씬 없이 돈다.

4. **봇 클린런** — 612m·53관문에서 ① 클린런이 유지되는지(`FlappyMapPlayabilityCheck`).

**눈으로만 판정하는 것**: 색·대비·안개 값. 에디터에서 보고 정한다.

## 7. 리스크 — 미리 박제

- **맵 씬과 재질은 `Assets/Art` 서브모듈에 있다.** Art에서 따로 커밋·머지·푸시하고 클라의
  포인터가 그 뒤를 따라야 한다. **콘텐츠 빌드는 그 push 뒤에** 돌려야 한다(어기면 마커가
  missing script로 구워진다).
- **씬에 저장한 안개는 안 켜진다** — 맵이 additive라 활성 씬이 이긴다(§4 참고).
- **안개는 전역 상태다.** `RenderSettings`를 칠하면 다음 게임모드로 샌다.
  `SkydiveAtmosphere`가 시작값을 기억해 `Dispose`에서 되돌리는 이유이고, `FlappyAtmosphere`도
  같은 처리를 반드시 해야 한다.
- **스카이박스 재질을 그대로 칠하면 서브모듈 파일이 더러워진다.** 플레이할 때마다 `.mat`이
  수정된다. `SkydiveAtmosphere`처럼 **처음 한 번 복제본을 만들어 그것만** 칠한다(실증된 함정).
- **오브젝트 수가 는다** (파이프 106 + 중간층 + 배경). 박스 + 재질 4~6종이면 SRP Batcher가
  묶는다. 단 중간층을 너무 잘게 쪼개지 말 것.
- **612m 재생성 시 마커 구출.** `FinishLine`/`SpawnPoint`를 `ComposedMap` 밖으로 옮긴 뒤
  지워야 한다(`RescueMarkers` — 한 번 지워 본 적 있다).
- **씬을 열어 둔 채 씬 파일을 되돌리지 말 것.** 외부 변경 대화상자가 메인 스레드를 막아
  모든 파이프라인 명령이 10분간 멈춘 적이 있다.
- **배경 x가 557m에서 끝난다.** 612m 코스의 마지막 55m에 배경이 없다. 키울 때 같이 늘린다.

## 8. 산업 표준 매핑

- **세 층(게임 평면 / 중간층 / 배경)** = 2.5D 횡스크롤의 표준 층 구성. 업계 용어로
  gameplay plane · **midground** · background (Trine, Ori, Limbo). "중간층"은 midground다.
- **거리로 층을 가르기** = 대기 원근(aerial perspective). 프로젝트 안 짝은 Skydive 대기
  슬라이스이고, 같은 수단(빌트인 거리 안개 + 앰비언트 + 스카이박스)을 쓴다.
- **구간별 색조 진행, 기하 불변** = 시각적 진행을 기계적 진행과 분리하는 표준 기법.
- **`FlappyAtmosphere` ↔ `SkydiveAtmosphere`** = 같은 개념의 짝 일관 명명(축만 y→x).
- **`CourseSection`** = 선형 코스의 구간을 가리키는 통용어(section/segment). MapTools의
  기존 명명(`GateRhythmRule`, `ClassicCourseRule`, `ObstaclePlacementRule`)과 맞춰
  `CourseSectionRule`로 둔다.

## 9. 열린 결정

- **추격자가 실제로 압박이 되는가.** 지금은 잘 날면 5개 화면 뒤에 있어 존재하지 않는 것과
  같다. 최대 속도(6.18)를 새(6.8)에 더 붙일지, 아니면 "실패할 때만 보이는 것"으로 둘지는
  플레이해 보고 따로 묻는다. 이 슬라이스는 후자를 가정한다.
- **중간층 z를 14로 둘지.** 20~30m 사이 어디든 되고, 값이 커지면 시차가 커지지만 화면을
  채우려면 더 커야 한다(34m에서 24.8m, 50m에서 36m). 에디터에서 보고 정한다.
- **중간층을 빌더가 굽는지 씬에 손으로 두는지.** 612m를 덮어야 하니 빌더 쪽이 유력하나,
  실루엣은 손맛이 필요할 수도 있다.
- **잔불 발광을 재질 emission으로 할지 광원으로 할지.** 모바일이라 emission이 유력하다.
