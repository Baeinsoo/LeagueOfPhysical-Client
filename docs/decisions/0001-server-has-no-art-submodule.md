# 0001. 서버 프로젝트는 Art 서브모듈을 갖지 않는다. 맵은 어드레서블 콘텐츠로 받는다

- 상태: Accepted
- 날짜: 2026-06-21
- 관련: LeagueOfPhysical-Server 커밋 `6a4554d` (URP 전환 커밋에 함께 들어감) · [0005](0005-addressables-independent-append-only.md)

## 맥락

그림·모델·맵 씬 같은 아트 파일은 별도 레포 `LeagueOfPhysical-Art`에 있고, 클라이언트와 서버가 둘 다 이것을 서브모듈(다른 git 레포를 폴더 하나로 끼워 넣는 기능)로 달고 있었다.

두 프로젝트는 같은 Art 레포를 가리키면서도 서로 다른 커밋에 고정돼 있었다(서버 쪽 마지막 포인터는 `f18fcee`). 아트를 고칠 때마다 두 곳의 포인터를 따로 올려야 했고, 안 올리면 둘이 조용히 어긋났다.

그런데 서버는 헤드리스(화면 없이 도는 프로그램)라 아무것도 그리지 않는다. URP 전환(2026-06-21)을 하면서 서버 쪽 머티리얼을 정리하다 보니, 서버 코드와 에셋 중 Art 폴더를 참조하는 곳이 하나도 없었다.

## 결정

- 서버 레포에서 Art 서브모듈을 뺀다. Art 서브모듈은 클라이언트에만 둔다.
- 서버가 판을 돌리는 데 필요한 맵 씬(맵 모양과 `SpawnPoint`·`FinishLine` 같은 마커)은 레포로 가져오지 않고, **클라이언트가 빌드해 S3에 올린 어드레서블 콘텐츠를 실행 중에 받아서** 연다.
  - 어드레서블: Unity가 에셋 묶음(번들)과 그 목록(카탈로그)을 빌드 밖에 두고 필요할 때 내려받게 하는 기능이다.
  - 클라 레포의 `content-deploy` 워크플로가 서버용 대상(`StandaloneLinux64`)으로 번들을 구워 S3에 올린다. 서버는 같은 S3 경로를 원격 카탈로그로 보고, 맵 id로 씬을 연다.
- 게임 모드 씬(`FlappyRace.unity`처럼 룰과 스코프를 담는 씬)은 서버 코드와 한 몸이라 서버 빌드 안에 그대로 둔다. 아트가 들어 있는 것은 맵 씬 쪽이다.

## 결과

- 쉬워지는 것: 아트 포인터를 한 곳(클라)만 관리한다. 서버 빌드가 아트 파일 크기와 무관해지고, 서버 클론·CI 체크아웃이 가볍다. 맵 모양만 바꾼 경우에는 서버를 다시 빌드하지 않고 콘텐츠만 다시 올리면 된다(새 마커 스크립트가 필요하면 Shared와 서버도 함께 올라가야 한다).
- 어려워지는 것:
  - 서버가 **S3 콘텐츠에 실행 시점에 의존**한다. 콘텐츠가 안 올라갔거나 깨졌으면 서버는 멀쩡해도 방이 뜨지 않는다. 그래서 레포 간 푸시·배포 순서(Shared → Art → Client → content-deploy → Server)가 지켜야 할 약속이 된다.
  - 맵 씬의 마커 스크립트는 Shared 패키지에 있어야 한다. 클라가 콘텐츠를 구울 때의 Shared 버전이 서버가 기대하는 버전과 맞아야 번들이 깨지지 않는다.
  - 서버를 로컬 에디터로 띄워 시험할 때도 맵은 S3에서 받아 온다. 해당 플랫폼용 콘텐츠가 올라가 있어야 한다.
- 버린 대안:
  - **서버에도 서브모듈을 계속 단다**: 쓰지 않는 파일을 받고, 두 포인터가 어긋나는 문제가 그대로 남는다.
- 다시 검토할 조건: 서버가 무언가를 그려야 하게 되거나(예: 서버에서 리플레이 렌더), S3 없이 완전히 오프라인으로 서버를 돌려야 하는 요구가 생길 때.
