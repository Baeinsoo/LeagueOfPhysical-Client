# 0002. 백엔드는 lop-backend 모노레포 하나로 합치고, Prisma 스키마는 `@lop/database` 하나만 가진다

- 상태: Accepted
- 날짜: 2026-07-05
- 관련: `infrastructure/docs/specs/2026-07-05-deployment-system-design.md` §3 · [0003](0003-gitops-argocd-sha-tags.md)

## 맥락

백엔드는 로비·매치메이킹·룸 서버와 DB 관리 도구(db-admin)가 레포 네 개로 흩어져 있었다.
실제 DB 테이블은 db-admin의 스키마로 만들어졌는데, 서버 셋은 **각자 들고 있는 스키마 사본**으로
DB 접근 코드(Prisma 클라이언트)를 만들고 있었다. 이 사본들은 이미 서로 달라져 있었다.
즉 "서버가 믿는 테이블 모양"과 "실제 테이블 모양"이 어긋날 수 있는 구조였다.

같은 시기에 배포 자동화(버튼 하나로 빌드·배포)를 새로 짜야 했다. 레포가 넷이면 빌드 방식,
의존성 버전, Dockerfile, CI 설정도 넷을 따로 맞춰야 한다.

## 결정

- 네 레포를 **`lop-backend` 모노레포** 하나로 합친다(한 저장소 안에 여러 앱을 둔다).
  pnpm workspaces로 패키지를 묶고, Turborepo로 "바뀐 것만 빌드·테스트"한다.
- 앱은 `apps/{lobby,matchmaking,room}-server`, 스키마는 `packages/database`(`@lop/database`)에 둔다.
- **Prisma 스키마와 마이그레이션은 `@lop/database`만 가진다.** 서버들은 자기 사본을 지우고 이 패키지를
  가져다 쓴다. db-admin의 역할은 이 패키지가 이어받는다.
- DB 마이그레이션은 이 패키지로 만든 별도 이미지(`lop-db-migrate`)가 배포 직전에 돌린다.
- 옛 레포들은 지우지 않고 아카이브(읽기 전용)로 남긴다.

## 결과

- 스키마 사본이 갈라지는 문제가 구조적으로 사라진다. 스키마를 바꾸면 그 변경을 쓰는 서버 코드와
  **같은 커밋**에 들어가고, 타입이 안 맞으면 빌드에서 바로 드러난다.
- CI 워크플로·Dockerfile 패턴·의존성 버전을 한 곳에서 관리한다. 서버별 이미지는 여전히 따로 굽고
  따로 배포할 수 있다(앱마다 Dockerfile 유지).
- 대가: 서버 하나만 고쳐도 레포 전체를 받는다. 이미지 태그가 모노레포 커밋 SHA라서, 한 앱만
  배포해도 태그 값은 레포 전체의 시점을 가리킨다.
- 버린 대안
  - **레포는 그대로 두고 스키마만 공유 패키지로 뽑아 배포(npm 등)**: 스키마를 바꿀 때마다 패키지 버전을
    올리고 서버 넷을 따로 올려야 해서, 사본이 갈라지던 문제가 "버전이 갈라지는" 문제로 바뀔 뿐이다.
  - **서버마다 사본을 유지하고 수동으로 맞추기**: 이미 실패한 방식이다.
- 다시 볼 조건: 서버를 다른 팀·다른 언어로 떼어 내야 할 때.
