# 0004. CI 러너 배치: 백엔드는 GitHub 호스티드, Unity 빌드는 개발 맥의 셀프호스트 러너(서버용·클라용 분리)

- 상태: Accepted
- 날짜: 2026-07-06 (클라 전용 러너는 2026-07-09)
- 관련: `infrastructure/docs/specs/2026-07-05-deployment-system-design.md` §4 · [0003](0003-gitops-argocd-sha-tags.md) · [0006](0006-gameserver-il2cpp-multiarch.md) · [0007](0007-nuget-restore-in-ci.md)

## 맥락

CI(자동 빌드)는 두 종류다. 하나는 Node 백엔드 이미지 빌드이고, 다른 하나는 Unity 빌드(게임서버,
클라 앱, 어드레서블 콘텐츠)다. 처음 설계는 "전부 맥의 셀프호스트 러너 한 대"였다.

- Unity batchmode 빌드에는 Unity 라이선스와 설치된 빌드 모듈이 필요하다. GitHub가 빌려주는 러너에는 없다.
- 백엔드 빌드는 그런 제약이 없고, amd64와 arm64 두 아키텍처 이미지를 함께 구워야 한다.
- 개인 계정이라 GitHub의 조직 공유 러너를 쓸 수 없다. 셀프호스트 러너는 **레포 하나에만** 붙는다.

## 결정

- **백엔드(lop-backend)는 GitHub 호스티드 러너(`ubuntu-latest`)** 에서 멀티아치 이미지를 굽는다.
- **Unity 빌드는 개발 맥의 셀프호스트 러너**에서 돌린다. 맥에 활성화된 라이선스를 그대로 쓴다.
- 러너는 **서버 레포용과 클라 레포용을 따로** 둔다(개인 계정에서는 한 러너를 두 레포가 나눠 쓸 수 없다).
- Unity 프로젝트가 `file:` 경로로 참조하는 형제 패키지 레포(GameFramework, Shared, MasterData)는
  CI가 러너 옆에 따로 받아 온다. 기본은 각 레포의 `main`이다.

## 결과

- 백엔드 CI는 맥이 꺼져 있어도 돈다.
- Unity CI는 **맥이 켜져 있어야** 돈다. 그리고 개발 중인 에디터와 CPU·메모리·라이선스를 나눠 쓴다.
  에디터가 떠 있는 상태로 빌드하면 Burst 컴파일 단계에서 네이티브 크래시가 나는 일이 실제로 있었다
  (코드 문제가 아니며 재시도하면 대개 통과한다).
- 러너가 레포마다 한 대라 Unity 빌드는 동시에 하나씩만 돈다(워크플로가 자동으로 줄을 선다).
- 형제 패키지는 기본으로 `main`을 받으므로, 피처 브랜치에서만 바꾼 패키지는 그냥 돌리면 CI에 보이지
  않는다. 여러 레포에 걸친 브랜치를 배포할 때는 워크플로의 `package_ref` 입력으로 브랜치를 지정한다
  (2026-09-06 추가).
- 버린 대안
  - **Unity도 GitHub 호스티드 러너 + 라이선스 활성화(GameCI 등)**: 라이선스 관리와 긴 콜드 빌드 비용이
    든다. 1인 개발에서는 맥에 이미 있는 환경이 싸다.
  - **백엔드도 맥 러너**: 멀티아치 빌드와 가용성 면에서 이득이 없다.
  - **러너 한 대를 여러 레포가 공유**: 개인 계정에서는 불가능하다.
- 다시 볼 조건: 조직 계정으로 옮기거나, 맥 없이도 Unity 빌드가 돌아야 할 때.
