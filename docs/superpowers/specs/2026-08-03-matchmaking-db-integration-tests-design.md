# 매치메이킹 동시성 — DB 통합 테스트 하니스 설계

진짜 Postgres를 띄워 **확정과 취소가 같은 순간에 부딪히는 상황**을 자동으로 재현하는 테스트를 만든다.

## 1. 왜

**지금 이 코드의 안전성은 "주석에 적힌 논증"이다.** `MatchDaoPostgres.saveWithRounds`와
`MatchmakingTicketDaoPostgres.deleteByIdIfUnconsumed`의 docblock은 DB가 어떻게 행동할지를 길게
설명하지만 — 그게 실제로 그런지 **한 번도 실행해서 확인한 적이 없다.**

그리고 이 자리는 사람이 머리로 판단하면 틀리는 자리임이 이미 드러났다. 매치메이킹 표준화 트랙에서
**태스크 리뷰를 전부 통과한 뒤 최종 리뷰가 Critical을 세 번 잡았고, 그중 둘은 앞선 수정이 만든
것**이었다(하나를 막으며 다른 하나를 열었다).

**그리고 다음 작업의 검증 수단이다.** 남은 경합 둘(§7의 B·C)을 고칠 때, 이 틀이 없으면 또 코드를
읽고 논증하는 방식으로 돌아간다.

## 2. 착수 전 실측 — 주장은 성립한다

계획을 세우기 전에 실제 Postgres를 띄워 두 방향을 손으로 재현했다. **둘 다 성립한다.**

**① Director가 선점한 채 커밋 전인데 취소가 들어옴**

```
[   6ms] director  : 티켓 선점 1건, 붙들기 시작
[ 409ms] canceller : 조건부 삭제 시도          ← 여기서 블록
[1518ms] director  : 커밋
[1527ms] canceller : 삭제 0건                  ← 재평가 후 0
```

삭제가 **1.1초 동안 실제로 막혀 있다가** 조건(`matchId: null`)을 다시 보고 0건이 됐다. docblock의
주장 그대로다.

**② 취소가 먼저 커밋된 뒤 Director가 확정 시도**

```
던진 에러  : Ticket claim failed. required: 2, claimed: 1
매치 행 수 : 0        라운드 수 : 0
남은 티켓  : [{"id":"T2","matchId":null}]
```

매치·라운드가 통째로 롤백되고, 함께 묶였던 애꿎은 티켓은 `matchId=null`로 풀에 남았다.

> **그러므로 이 작업은 "고치는 일"이 아니라 "맞다는 걸 고정하는 일"이다.** 지금은 누가 이걸
> 깨뜨려도 알 방법이 없다.

## 3. 하니스

| 요소 | 선택 | 실측 |
|---|---|---|
| DB 프로비저닝 | **`@testcontainers/postgresql`** | 기동 8.3초, 랜덤 포트 할당, 자동 정리 확인 |
| 스키마 | `prisma migrate deploy` | 마이그레이션 7개 정상 적용 확인 |
| 테스트가 부르는 것 | **실제 DAO** (`MatchDaoPostgres` 등) | — |

**testcontainers를 고른 이유.** 손으로 `docker run` + 마이그레이션을 돌리는 것도 됐다(§2가 그
방식이다). 하지만 그러면 포트 충돌·기동 대기·고아 컨테이너 정리를 우리가 짜야 하고, **로컬과 CI에
서로 다른 설정이 생긴다.** 이 저장소는 "앱 빌드 경로가 셋인데 의존 처리가 달라 CI만 죽는" 일을
이미 겪었다 — 한 코드 경로가 양쪽에서 도는 값이 라이브러리 하나보다 크다.

**⚠️ 로직을 다시 짜지 않는다.** §2의 프로브는 SQL을 손으로 재현했다. 진짜 테스트는 배포되는 코드를
지켜야 하므로 **실제 DAO 메서드를 호출**한다. DAO는 `@lop/server-core/postgres`의 모듈 수준
`prismaClient`를 쓰고 그 접속 URL은 `process.env`에서 조립되므로, **모듈이 로드되기 전에 env를
컨테이너 쪽으로 세팅**하면 실제 배선 그대로 컨테이너를 보게 된다(jest `setupFiles`가 그 자리다).

**⚠️ "테스트를 트랜잭션으로 감싸 롤백"하는 패턴(`jest-prisma` 등)을 쓰면 안 된다.** 널리 쓰이지만
**우리 경우엔 검증 대상을 가린다** — 커넥션 둘이 서로의 커밋을 봐야 하는데 그 패턴은 그걸 막는다.
같은 이유로 테스트는 워커 1개로 직렬 실행한다.

## 4. 무엇을 테스트하나

| | 시나리오 | 기대 |
|---|---|---|
| ① | Director 선점 중(커밋 전) 취소 요청 | 삭제가 **블록됐다가** 0건. 유저는 "취소 실패"를 받는다 |
| ② | 취소가 먼저 커밋된 뒤 확정 시도 | 확정이 던지고 **매치·라운드까지 롤백**. 함께 묶였던 티켓은 풀에 남는다 |
| ③ | 같은 유저의 여분 티켓이 있는 정상 매치 | **성공해야 한다** — 넓히기 단계는 개수를 비교하지 않는다 |
| ④ | 이미 소비된(`matchId` 찍힌) 티켓 취소 | 0 반환 |

①②는 §2에서 성립을 확인했다 — 테스트는 그것을 **영구 회귀 가드로** 박는 것이다.
③은 리뷰어가 인메모리로만 확인했던 것이다(개수 비교를 잘못 넣으면 정상 매칭이 통째로 롤백된다).

## 5. 인터리빙을 어떻게 만드나

①은 "Director가 선점한 채 아직 커밋 안 한 상태"를 만들어야 한다. Prisma의 인터랙티브 트랜잭션은
콜백을 받으므로, **콜백 안에서 promise를 await해 트랜잭션을 열어 둔 채로 붙든다.** 그 사이에 다른
커넥션이 취소를 시도한다.

- **Prisma 기본 트랜잭션 timeout은 5초**다. 붙드는 테스트는 `timeout`/`maxWait`를 올려야 한다.
- **"막혔다"는 시간으로 증명한다** — 취소가 완료된 시각이 Director 커밋 이후여야 한다. 단순히
  결과가 0건인 것만으로는 "블록됐다"를 증명하지 못한다(애초에 못 찾았을 수도 있다).
- 붙드는 시간은 짧게(수백 ms) 두되, 판정은 절대 시각이 아니라 **커밋과 삭제의 순서**로 한다.

## 6. jest 분리와 CI

**유닛과 섞지 않는다.** 통합 테스트는 컨테이너 기동 때문에 느리고 Docker를 요구한다. 별도
설정(`jest.integration.config.js`) + 별도 스크립트(`test:integration`)로 두어 유닛 테스트의
빠른 반복을 지킨다.

**배포 워크플로에 별도 단계로 넣는다.** 지금 `backend-deploy.yml`은 이미지 빌드 전에
`turbo run test`를 돌린다 — 그 옆에 통합 테스트 단계를 둔다. 비용은 **배포가 Docker-in-CI에
묶이는 것**이고, 넣지 않을 때의 비용은 **아무도 안 돌려서 서서히 썩는 것**이다. 후자가 더 크다
(만들어 놓고 잊히면 이 문서의 목적 자체가 사라진다).

## 7. 다음 단계(B·C)가 요구할 것 — 하니스를 이 모양으로 짓는 이유

이 하니스의 목적 절반은 **아직 안 고친 경합 둘**을 고칠 때 쓰는 것이다.

**B — 로비 자가치유의 lost-update** (`UserLocationService.verifyUserLocation`)
읽고 → HTTP 왕복 → 쓰는 구조라, 그 사이 Director가 위치를 `GameRoom`으로 써도 **옛 객체로
`None`을 덮어쓴다.** 게임에 들어가야 할 사람이 로비로 튕긴다.
→ 이 테스트는 **lobby-server** 쪽이고, 위치 저장소가 `CacheCrudRepository`(Postgres + Redis)라
**Redis 컨테이너도** 필요하다. 그리고 **lobby-server에는 jest 설정 자체가 없다** — 그때 만들어야 한다.

**C — 티켓 발급이 유저당 유일하지 않다**
matchmaking-server + Postgres만 있으면 된다(이 하니스로 충분).

→ 그래서 컨테이너 기동 코드는 **Postgres 전용으로 박지 말고** 나중에 Redis를 더할 수 있는 모양으로
둔다. 단 이번에 Redis를 실제로 띄우지는 않는다(YAGNI).
