# 매치메이킹 남은 경합 둘 — 설계

대기표가 두 장 생기는 문제(C)와 로비 자가치유가 남의 쓰기를 덮는 문제(B)를 고친다.

## 1. 무엇을 고치나

둘 다 같은 모양이다 — **확인하고 → 그 사이에 세상이 바뀌고 → 옛 판단으로 쓴다.**

| | 어디 | 사용자가 겪는 일 |
|---|---|---|
| **C** | 티켓 발급 (`MatchmakingService.requestMatchmaking`) | **혼자서 2인 매치가 잡힌다.** 게임방은 만들어지는데 상대가 영영 안 온다 |
| **B** | 로비 자가치유 (`UserLocationService.verifyUserLocation`) | **게임에 들어가야 할 사람이 로비로 튕긴다** |

## 2. 착수 전 실측

### C — 혼자서 2인 매치가 실제로 성립한다

U1 한 사람의 대기표 두 장으로 매칭 함수를 돌린 결과:

```
제안 수: 1
  티켓: [ 'T1', 'T2' ]
  playerCount: 2        ← 혼자인데 2명으로 셈
```

`buildGroup`이 **티켓 id로만 중복을 거르고 사람으로는 안 거른다**(`playerCount += candidate.userIds.length`,
`remaining.filter(t => !pickedIds.has(t.id))`).

> ⚠️ ROADMAP에 적혀 있던 *"확정 트랜잭션이 참가자의 다른 티켓까지 함께 소비해 막고 있다"* 는
> **두 장이 서로 다른 매치로 갈 때만** 통한다. **한 매치 안에 같이 들어가는 경우는 아무것도 막지 않는다.**

### B — 치유가 없는 경로에서도 덮어쓴다

`verifyUserLocation`은 치유할 게 없어도 **매번 행 전체를 다시 쓴다**(`timestamp` 갱신). 즉
`읽기 → HTTP → 행 전체 쓰기`가 **모든 조회마다** 돈다. 클라가 1초마다 폴링하므로 상시 벌어진다.

그리고 `UserLocation.timestamp`는 **아무도 읽지 않는다** — 매퍼가 실어 나르기만 하고 어떤 판단에도
쓰이지 않으며 클라도 보지 않는다.

## 3. 왜 트랜잭션이 아닌가

**둘 다 읽기와 쓰기 사이에 HTTP 호출이 낀다.**

- B: 위치 읽기 → *matchmaking/room-server로 HTTP* → 쓰기
- C: 위치 확인 → *lobby-server로 HTTP* → 티켓 생성 (확인이 **다른 서비스**에 있다)

그 상태로 트랜잭션을 붙들면 네트워크 대기 내내 DB 잠금을 쥔다 — 커넥션 고갈·데드락, 게다가 **외부
호출은 롤백되지 않는다.** 업계에서 이름 붙여 경계하는 안티패턴이다.

**그래서 아래 해법은 "트랜잭션이 안 돼서 우회한 것"이 아니라 이 모양의 정석이다.**

## 4. C — 대기표 유일성

### 조회로는 못 막는다

지금도 발급 전에 위치를 조회해 확인한다. 그런데 **조회한 순간과 만드는 순간 사이의 틈**에 다른
요청이 조회하면 그쪽도 통과한다. 두 요청 다 정직하게 조회하고 둘 다 옳은 답을 받았는데도 두 장이 생긴다.
**조회를 더 정확히·자주 해도 이 틈은 안 없어진다.**

### 규칙을 기본키로 만든다

```prisma
model MatchmakingTicketUser {
  //  이 컬럼이 기본키인 것 자체가 규칙이다: "한 유저는 열린 티켓을 하나만 가진다".
  //  조회로 확인하는 방식은 확인과 생성 사이의 틈 때문에 원리적으로 막지 못한다.
  userId   String @id
  ticketId String
  ticket   MatchmakingTicket @relation(fields: [ticketId], references: [id], onDelete: Cascade)
}
```

실험으로 확인한 동작:

| 상황 | 결과 |
|---|---|
| 파티 티켓 발급 (U1, U2) | ✅ 성공 |
| **U2가 낀 다른 파티 (U2, U3)** | ✅ **거부** — 파티 겹침까지 덮인다 |
| 티켓 삭제 | ✅ 딸린 행 자동 삭제(cascade) |
| 정리 후 U2 재발급 | ✅ 가능 |

> 배열(`userIds`)에 직접 제약을 거는 길은 **막혀 있다.** 실험 결과 `text[]`에는 gist 연산자 클래스가
> 없어 겹침 제외 제약을 만들 수 없고, `btree_gist`를 깔아도 마찬가지다.

### 유지보수 부담

**쓰는 곳은 발급 한 군데뿐이다.** 취소·매치 확정 후 정리는 티켓을 지우면 cascade가 따라온다.
매치가 잡혀 표시만 된 구간에는 행이 남는데 — 그게 맞다. 그 사람은 다시 큐에 서면 안 된다.

### 발급 동작

티켓 생성과 `MatchmakingTicketUser` 삽입을 **한 트랜잭션**으로 한다. 제약에 걸리면(이미 열린 티켓이
있으면):

- 그 티켓이 아직 미소비면 → **기존 티켓을 그대로 돌려준다**(멱등). 버튼을 두 번 눌러도 정상으로 보인다
- 이미 소비됐으면(matchId 있음) → 이 사람은 매치에 잡혀 있으므로 `INVALID_TO_MATCH_MAKING`

> **트리거를 쓰지 않는 이유:** DB 트리거로 자동 채우면 앱이 뭘 하든 우회 불가지만, **TypeScript
> 코드를 아무리 읽어도 안 보인다.** 이 저장소는 "왜"를 코드 주석으로 남기는 방식이라 결이 다르다.
> 발급 경로가 한 곳뿐이라 명시적 트랜잭션으로 간다. 빠뜨려도 피해는 그 티켓에 한정된다(기본키는 계속 산다).

## 5. B — 로비 자가치유

> `verifyUserLocation`은 레거시이고 자유롭게 고쳐도 된다는 확인을 받았다(2026-08-04). 그래서
> 최소 패치가 아니라 **읽기/쓰기 책임을 가르는 정리**로 간다.

### ⓪ 자가치유를 읽기 경로로 옮긴다

지금은 **쓰기 경로(`updateUserLocation`)에서도 자가치유가 돈다.** 그런데 이 API를 부르는 곳은 셋뿐이고
**전부 자기가 방금 만든 것을 기록한다**:

| 호출자 | 기록하는 내용 |
|---|---|
| `MatchmakingService.requestMatchmaking` | "매칭 중" + 방금 만든 티켓 |
| `MatchmakingService.cancelMatchmaking` | "없음" |
| `assignment.ts` (Director 확정) | "게임방" + 방금 만든 방 |

즉 쓰기 경로의 검증은 **방금 만든 것을 다시 물어보는 낭비**이고, 더 나쁘게는 **room-server가 느리거나
잠깐 실패하면 Director의 확정을 조용히 `None`으로 무효화**한다. 쓰기가 자기 자신을 되돌린다.

→ **쓰기 경로에서 자가치유를 뺀다. 요청받은 값을 그대로 쓴다.** 안전망은 읽기 경로에 남으므로
잘못된 상태가 저장돼도 다음 조회에서 고쳐진다. 덤으로 **확정 경로에서 HTTP 왕복이 하나 사라져**
다른 경합의 창도 함께 줄어든다.

### ① 바뀐 게 없으면 쓰지 않는다

읽기 경로에서 치유할 게 없으면 **아무것도 쓰지 않는다.** `timestamp`만 갱신하려고 행 전체를 덮던
것을 없앤다(§2에서 확인했듯 아무도 안 읽는다).

이것만으로 **가장 흔한 경로의 덮어쓰기가 사라지고**, 폴링마다 나가던 쓰기도 없어진다.
부수 효과로 `timestamp`의 의미가 "마지막으로 조회된 시각"(무의미)에서 **"마지막으로 위치가 바뀐 시각"**
으로 바뀐다 — 디버깅에 쓸모가 생긴다.

### ② 치유할 때는 조건부 쓰기

*"내가 판단 근거로 삼은 그 상태가 아직 그대로일 때만 치유한다"*:

```
UPDATE ... SET location = None
WHERE id = ? AND location = <읽은 값> AND locationDetail의 대기표/방 id = <읽은 값>
```

0행이면 그 사이 누가 바꿨다는 뜻이므로 **치유를 포기하고 최신 값을 다시 읽어 돌려준다.**
스키마 변경이 없고, 의도가 조건문에 그대로 드러난다.

> 버전 컬럼(낙관적 잠금)이 교과서적 대안이지만 마이그레이션 + **모든 쓰기 경로** 수정이 필요하다.
> 여기서 지켜야 할 것은 "치유 판단의 전제가 아직 유효한가" 하나뿐이라 조건부 쓰기로 충분하다.

## 6. 순서 — C 먼저

| | 새로 필요한 것 |
|---|---|
| **C** | 없음 — 지금 통합 테스트 하니스로 바로 검증된다 |
| **B** | lobby-server에 **jest 설정 신설**(현재 테스트 0개) + **Redis 컨테이너**(위치 저장소가 캐시를 쓴다) |

C를 먼저 해서 증명하며 가고, B는 테스트 기반을 깔고 들어간다.

## 7. 검증

- **C**: 같은 유저로 동시 발급 2회 → 티켓 1장 + 두 응답 모두 같은 ticketId / 파티 겹침 발급 → 거부 /
  티켓 삭제 시 cascade 정리 / 매칭 함수에 같은 유저 티켓 2장을 넣던 프로브가 **더 이상 재현 불가**
- **B**: 치유 판단 중 다른 쓰기가 끼어들면 치유가 취소되고 최신 값이 반환 / 바뀐 게 없으면 **쓰기가
  일어나지 않음**(호출 횟수로 확인) / **쓰기 경로가 이웃 서비스에 묻지 않음**(HTTP 호출 0회) 및
  **요청받은 값이 그대로 저장됨**(이웃 서비스가 실패해도 무효화되지 않음)
- 마이그레이션: 기존 데이터에 같은 유저의 열린 티켓이 둘 이상이면 **오래된 것 하나만 남기고 정리**
- 로컬 docker 빌드 3종 → 배포 → 2클라 E2E(매칭·취소를 여러 번 섞어서)

## 8. 산업 표준 매핑

| 우리 것 | 표준 |
|---|---|
| B의 조건부 쓰기 | **낙관적 동시성 제어(Compare-And-Update)** — "읽은 값이 그대로일 때만 쓴다, 0행이면 누가 바꾼 것" |
| C의 기본키 제약 | **제약 > 앱 레벨 잠금.** DB 제약은 원자적이고 우회 불가. 자문 잠금은 새 경로가 빠뜨리면 무력화된다 |
| 트랜잭션을 안 쓰는 이유 | **"Never call APIs inside database transactions"** — 잠금을 네트워크 대기 동안 쥐게 되고 외부 호출은 롤백 불가 |

## 9. 범위 밖 / 후속

- **매칭 함수의 사람 기준 중복 제거** — 티켓이 두 장 생기지 않게 되면 필요 없다. 증상 대응이라 안 넣는다
- **`userIds` 배열과 `MatchmakingTicketUser`의 이중화** — 배열은 읽기용으로 남는다. 파티를 실제로
  도입할 때 완전 정규화를 재검토
- 버려진 티켓 만료(별건, 목록에 있음) · MongoDB 제거 · `ResponseCode` 5중 복제
