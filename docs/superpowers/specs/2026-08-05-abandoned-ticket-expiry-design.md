# 버려진 매칭 대기표 만료 설계

**한 줄 요약:** 대기표가 없어지는 길이 *취소*와 *매치 성사* 둘뿐이라, 클라가 죽으면 대기표가 영원히
남아 **유령 플레이어가 낀 매치**를 만든다. 여기에 두 가지 만료를 붙인다 — **신호가 끊기면**(죽은 클라)
과 **너무 오래되면**(살아있지만 못 잡힌 사람).

---

## 1. 문제

대기표(`MatchmakingTicket`)를 지우는 경로는 지금 둘뿐이다.

1. 유저가 **취소**를 누른다
2. **매치가 성사**되어 가져간다

**셋째 길이 없다.** 매칭서버에는 스케줄러도 만료 개념도 없다(실측 확인). 그래서:

> 유저가 매칭을 걸어놓고 게임을 끄거나, 네트워크가 끊기거나, 기기가 꺼진다
> → 취소를 누른 적이 없으니 대기표는 그대로 남는다
> → Director는 그게 죽은 사람 것인지 알 방법이 없어 계속 매칭 후보로 본다
> → **유령 플레이어가 낀 매치**가 만들어지고, 나머지는 안 오는 사람을 기다린다

한 번으로 끝나지도 않는다. 서버가 오래 켜져 있을수록 죽은 대기표가 쌓이고, 매칭 품질이 서서히
나빠지는데 **로그에 원인이 남지 않는다.**

방(`Room`)에는 이미 청소부가 있다 — `lastHeartbeat` 컬럼 + 60초 임계값 + 2초마다 도는 스케줄러.
**방에는 있는 것이 대기표에는 없다.**

## 2. 기획 결정 — 무한 대기 + 아주 긴 상한

| 선택지 | 결정 |
|---|---|
| A. 무한 대기 (본인이 취소할 때까지) | |
| B. N분 뒤 "매칭 실패"로 돌려보냄 | |
| **C. 평소엔 계속 기다리되, 아주 오래면 그때 돌려보냄** | **✅ 채택** |

C를 고르면 **상한만으로는 부족하다.** 상한을 길게 잡을수록 죽은 대기표가 그만큼 오래 버티기
때문이다. 그래서 **"최근에 살아있었나"를 따로 봐야 한다.**

상한 값은 **큐별 설정**으로 뺀다 — 서비스 상황에 따라 조절하고, 인원이 적을 땐 길게, 매칭이 잘 되면
일괄로 줄인다. (elo별 차등은 지금 쓰지 않으므로 만들지 않는다.)

## 3. 살아있음을 무엇으로 아는가 — 이미 오는 요청을 쓴다

**신호는 이미 매칭서버에 도착하고 있다. 아무도 기록하지 않을 뿐이다.**

```
클라 (1초마다)  ──"나 어디 있어?"──▶  로비서버
                                        │  위치가 Matchmaking이면
                                        │  "이 대기표 아직 있나?" (HTTP)
                                        ▼
                                     매칭서버   GET /matchmakingTicket/:id
```

즉 **대기 중인 유저 한 명당 초당 1회 요청**이 매칭서버에 꽂힌다. 클라가 죽으면 폴링이 멈추고,
따라서 이 요청도 멈춘다 — 그대로 생사 신호다.

검토한 대안:

| | 방식 | 왜 안 골랐나 |
|---|---|---|
| **A** | **이미 오는 요청에 "방금 봤음" 시각을 찍는다** | **✅ 채택** — 클라 변경 0, 진실이 DB 한 곳 |
| B | Redis 키 + TTL (presence 표준) | 티켓은 DB·생사는 Redis로 갈라진다. Redis가 잠깐 죽으면 전원 사망 판정 — 그 안전장치를 또 설계해야 해서 지금 규모엔 과하다 |
| C | 클라가 별도 하트비트 전송 | 클라 변경 + 폴링 하나 추가. A로 되는 걸 굳이 |

**A의 비용은 "읽기 경로가 쓰기를 한다"** 는 점이다. 로비 자가치유에서 그걸 없앤 게 직전 슬라이스였다
(`read-modify-write-across-http`). 다만 그때 문제는 *행 전체를 덮어써서 남의 쓰기를 지운 것*이고,
여기서는 **컬럼 하나만 갱신**하므로 그 사고는 나지 않는다. 남는 것은 순수 쓰기 부하뿐이고, 대기 중인
사람 수만큼이라 현 규모에서 미미하다. 동접이 커지면 A → B로 옮길 수 있고, 옮겨도 대기표 구조는
바뀌지 않는다.

## 4. 데이터 모델

```prisma
model MatchmakingTicket {
  ...
  createdAt   DateTime @default(now())   //  이미 있음 — 상한 판정
  lastSeenAt  DateTime @default(now())   //  신규 — 신호 판정
}
```

**마이그레이션 시 기존 행은 배포 시각으로 채워진다**(`@default(now())`). 이게 중요하다 — 안 그러면
배포하는 순간 그때 대기 중이던 사람들이 전부 "신호 없음"으로 몰살당한다.

## 5. 신호 기록 — 어디서 찍나

**로비가 부르는 `GET /matchmakingTicket/:id` 그 자리에서만** 찍는다.

**저장소의 모든 조회가 아니다.** Director가 매칭하려고 티켓을 읽는 것까지 신호로 치면 *자기가 읽고
자기가 살아있다고 판단하는* 꼴이라 아무도 죽지 않는다. 신호는 **바깥에서 들어온 것**이어야 한다.

조회와 갱신을 **한 쿼리**로 처리한다 — `lastSeenAt`을 갱신하면서 그 행을 돌려받고, 행이 없으면
"없음"으로 응답한다.

**이 갱신을 기존 `findMatchmakingTicketById`에 넣지 않는다.** 그 메서드는 취소 판정 등 매칭서버
내부에서도 쓰이므로, 거기에 넣으면 "바깥에서 들어온 신호"라는 구분이 무너진다. **컨트롤러가 부르는
전용 메서드**를 따로 두고, 그 메서드만 `lastSeenAt`을 갱신한다.

명명은 방(Room)의 어휘에 맞춘다 — 방이 `heartbeat` / `lastHeartbeat`을 쓰므로 같은 개념에 다른
단어를 만들지 않는다.

## 6. 쓸어담기 — Director 틱 안

**별도 스케줄러를 만들지 않고 Director 틱 안에서, 풀을 읽은 직후에** 판정·삭제한다.

근거:

- 우리가 원하는 보장은 **"Director가 죽은 티켓을 매칭하지 않는다"** 이다. 같은 틱 안에서 지우면 그
  보장이 확실하다. 별도 스케줄러는 틱과 경합해 "지우는 중에 매칭됨"이 생긴다
- 틱은 **이미 시작할 때 잔재 청소**(소비 표시만 남은 티켓)를 한다 — 자연스러운 이웃이다
- 움직이는 부품(스케줄러·워치독)이 늘지 않는다

**트레이드오프:** Director가 멈추면 청소도 멈춘다. 다만 Director가 멈추면 매칭 자체가 안 되므로
유령 매치도 안 생긴다 — 이 작업이 막으려는 피해는 발생하지 않는다.

판정은 **순수 함수**로 분리한다(이 코드베이스가 `ticketRequestValidation`·`matchmakingCancelPolicy`
에서 쓰는 방식과 동일 — 테스트가 쉽다).

```
버릴 것 = 신호가 60초 넘게 끊긴 것
        또는 만든 지 큐의 ticket_ttl_seconds 를 넘긴 것

단, matchId 가 있는 티켓은 절대 건드리지 않는다
    (이미 매치가 가져간 것 = 그 사람은 게임 중이고, 별도 정리 경로가 있다)
```

삭제는 기존 `deleteAllMatchmakingTicketsById`를 그대로 쓴다.

**삭제 이후는 이미 있는 배관이 처리한다 — 클라 변경 0:**

```
대기표 삭제
  → 다음 폴링에서 로비 자가치유가 "대기표가 없네" → 위치를 None 으로
  → 클라의 InMatchmaking 이 None 을 보고 로비(Idle)로 복귀
```

## 7. 안전장치 — 신호가 통째로 끊겼을 때

이 설계에서 가장 위험한 지점이다.

> 로비서버가 죽거나 로비↔매칭서버 사이가 끊기면 **아무도 신호를 못 보낸다**
> → 전원 사망 판정 → **대기자 전멸**

3절에서 Redis 방식을 물렸던 이유와 **같은 함정이 A에도 있다.**

**가드: "최근에 신호를 받은 티켓이 하나라도 있을 때만" 신호 기반 삭제를 한다.**

여기서 "최근"은 **신호 끊김 임계값(60초)과 같은 값**이고, 판정 대상은 **이번 틱이 읽은 대기 풀
(소비 표시가 없는 티켓 전체)** 이다. 즉 *"풀 안에 60초 안에 신호를 준 티켓이 한 장이라도 있는가"* 를
묻는다.

- 하나도 없으면 = 개인의 죽음이 아니라 **신호 계통 장애** → 신호 기반 삭제를 건너뛰고 로그만 남긴다
- **상한 기반 삭제는 신호와 무관하므로 그대로 수행한다** — 진짜 오래된 것은 계속 정리된다
- 대기자가 1명일 때 그 1명이 죽으면 건너뛰게 되지만 상한이 잡는다. **n=1에서는 "장애"와 "죽음"을
  구분할 수 없으므로 보수적인 쪽이 옳다**

임의의 비율(예: "절반 이상 살아있을 때만")을 도입하지 않는다 — 근거 없는 숫자가 하나 늘 뿐이고,
"하나라도"만으로 대량 삭제는 이미 막힌다.

## 8. 값

| 값 | 시작값 | 어디에 | 근거 |
|---|---|---|---|
| **신호 끊김 임계값** | **60초** | 매칭서버 코드 상수 | 신호가 1초마다 오므로 60번 연속 실패해야 함. **방(Room)의 `HEARTBEAT_THRESHOLD`와 같은 값** — 새 기준을 만들지 않는다. 롤링 재시작(10~20초)에 죽지 않는다 |
| **절대 상한** | **600초(10분)** | `TbQueue.ticket_ttl_seconds` (큐별) | Open Match `assignedDeleteTimeout`(10분)과 같은 눈금 |

**임계값을 더 짧게 잡으면 위험하다.** 백엔드 배포마다 파드가 갈리면서 신호가 몇 초 끊긴다. 임계값이
5초쯤이면 **배포할 때마다 대기 중인 유저가 전부 튕겨 나간다.**

**이름 주의 — `TbQueue`에 이미 `max_wait_seconds`가 있다**(Casual 10초 / Ranked 60초). 그건 *"기다린
만큼 요구 인원을 낮춰 최소 인원까지 내려가는 시간"* 이지 포기 시간이 아니다. `max_queue_seconds`
같은 이름을 붙이면 한 글자 차이로 뜻이 정반대가 되므로, 확실히 다른 `ticket_ttl_seconds`를 쓴다
(Open Match·GameLift가 쓰는 "ticket TTL / ticket timeout" 어휘).

## 9. 설정값이 흐르는 길 — 저장소 4개

```
infrastructure/table/Datas/#Queue.xlsx   ← ticket_ttl_seconds 열 추가 (그룹 m)
        │  gen.sh
        ├─→ LeagueOfPhysical-MasterData-Client   (.cs + .bytes)
        ├─→ LeagueOfPhysical-MasterData-Server   (.cs + .bytes)
        └─→ lop-backend/apps/matchmaking-server  (src/masterdata/schema.ts + master_data/tbqueue.json)
                                                  ← 실제로 읽는 곳
```

매칭서버만 읽는 값이므로 **그룹은 `m`만** 준다(클라 빌드에 매칭 전용 컬럼을 싣지 않는다 — ROADMAP의
"마스터데이터 그룹 좁히기" 방침).

⚠️ `gen.sh`가 출력 폴더를 `rm -rf` 하는데 **Unity `.meta`도 함께 지운다**(알려진 문제). 클라·서버
패키지 쪽 `.meta`가 새로 생기는지 확인이 필요하다.

## 10. 테스트

| 무엇 | 어떻게 |
|---|---|
| 판정 규칙 | 순수 함수 유닛 — 신호끊김 / 상한초과 / 멀쩡 / 가드 발동 |
| 조회가 신호를 찍는가 | 통합 — 조회 후 `lastSeenAt`이 올라간다 |
| 조용한 티켓이 지워지는가 | 통합 |
| **방금 본 티켓은 안 지워지는가** | 통합 — **반대 방향도 봐야 진짜 테스트다** |
| `matchId` 있는 티켓은 안 지워지는가 | 통합 |
| 신호 전멸 시 건너뛰는가 | 통합 |

각 테스트는 **일부러 되돌려 실제로 실패하는지 확인**한다(이 프로젝트에서 세 번 값을 한 절차).

## 11. 산업 표준 매핑

| 우리 것 | 대응 |
|---|---|
| `ticket_ttl_seconds` (대기표 제한 시간, 설정값) | **AWS GameLift FlexMatch `RequestTimeoutSeconds`** — *"대기표가 처리 중으로 남을 수 있는 최대 시간"*, 유효 범위 1초~43,200초(12시간). 상용 매치메이커의 1급 파라미터 |
| 10분 시작값 | **Open Match `assignedDeleteTimeout: 10m`** 과 같은 눈금 |
| 60초 신호 임계값 | **Open Match `pendingReleaseTimeout: 1m`** 과 같은 눈금 + **우리 `Room.HEARTBEAT_THRESHOLD`(60초)** |
| `lastSeenAt` + 임계값 + 주기적 청소 | **우리 `Room.lastHeartbeat` 패턴** 그대로. 새 개념을 만들지 않았다 |

**의도적으로 다르게 간 것 — 유령 플레이어의 주된 방어선.** LoL·도타·오버워치는 **매치 수락 팝업**
("수락하시겠습니까? 10초")으로 잡는다. 큐에서 미리 거르는 게 아니라 **매치 성사 시점에** 잡는 방식이다.
둘은 경쟁이 아니라 보완이며(큐 청소는 수락 창이 죽은 사람으로 채워지는 것 자체를 줄인다), 수락 팝업은
클라 UI + 해체·복귀 흐름이라 훨씬 크다. **지금은 큐 청소만 한다.**

> [Open Match values.yaml](https://github.com/googleforgames/open-match/blob/main/install/helm/open-match/values.yaml) ·
> [PlayFab Matchmaking — error cases](https://learn.microsoft.com/en-us/gaming/playfab/features/multiplayer/matchmaking/error-cases)

## 12. 범위 밖 (후속으로만 기록)

| | 왜 미루나 |
|---|---|
| **"매칭 실패" 알림** | 지금은 아무 설명 없이 로비로 복귀한다(취소와 구분 안 됨). 이유를 실어 나를 배관이 필요하고, 그건 **유저 위치 전반 재정비 트랙**에서 어차피 손볼 영역이다 |
| **매치 수락 팝업** | AAA 표준 방어선이지만 클라 UI + 해체·복귀 흐름 = 큰 작업 |
| **elo별 상한** | 지금 쓰지 않는 구조를 미리 만들지 않는다 |
| **파티 일부만 죽은 경우** | 파티 티켓은 구성원 누구의 신호로도 살아난다. 한 명이 죽어도 티켓은 유지되고, 그 처리는 수락 팝업이 들어올 때 함께 볼 문제 |

## 13. Open Decisions

- [ ] 동접이 커져 초당 쓰기가 부담이 되면 신호 저장을 Redis+TTL(3절 B안)로 이전
