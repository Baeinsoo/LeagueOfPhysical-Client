# 문턱 아래 잔류 오차 제거 — 재조정 문턱 교정 설계

> 08-06 진단이 찾아낸 원인에 대한 **대응 슬라이스 1**. 원인 자체(입력 미스)를 줄이는 작업은
> 이 슬라이스가 아니다 — 그건 별도다.

## 1. 배경 — 무엇이 문제인가

`Reconciler`는 서버 스냅이 오면 **그 틱에 내가 예측했던 값**과 **서버가 말하는 값**을 비교하고,
충분히 가까우면 아무것도 하지 않는다. 그 "충분히 가까우면"의 기준이 **6cm**다.

```csharp
private const float Threshold = 0.06f;
...
if (positionClose && statusMatches)
{
    return;        // 롤백도 재생도 하지 않음
}
```

08-06 진단에서 확인된 실제 동작:

- 입력이 한 틱 비면 서버가 그 틱을 "무입력 = 제동"으로 처리해 **4cm** 어긋난다
- 4cm는 6cm 문턱 **아래**라 보정이 스킵된다
- 그 오차는 **줄어드는 경로가 아예 없다** — 45틱 연속 동일한 `delta=(0.039, 0, -0.008)` 관측,
  플레이어가 **정지한 동안에도**, 네트워크가 정상으로 돌아온 뒤에도 그대로였다

**즉 문턱 아래는 "천천히 고친다"가 아니라 "영원히 방치"다.** 이것이 이 슬라이스가 닫는 구멍이다.

### 왜 이게 이동 문제로 끝나지 않는가

서버는 플레이어가 보는 곳과 **다른 자리에 그가 있다고 믿는다.** 히트 판정·충돌·어빌리티 범위가
전부 그 어긋난 위치로 해소된다. 이동에서는 4cm가 안 보여도 **전투 판정에서 드러난다.**

눈에 보이는 러버밴딩은 2차 효과다 — 이런 사건이 쌓여 6cm를 넘는 순간 스냅 보정이 걸린다
(관측 중 `err=0.063` 건이 실제로 있었다).

## 2. 표준은 무엇인가

client-side prediction의 표준 알고리즘은 epsilon을 기준으로 **스냅 / 점진 보간**을 가른다:

> "check each visible object's client-side location to see if it is **within some error epsilon** of its
> server-side location." … "If not, the client-side's information is **updated to the server-side
> directly (snapped)**." … "However, if the client-side location is not too far, **a new position
> between the client-side and server-side is interpolated**."
> — [Client-side prediction, Wikipedia](https://en.wikipedia.org/wiki/Client-side_prediction)

| 오차 | 표준 | 우리 현재 |
|---|---|---|
| 큼 | 즉시 스냅 | 즉시 스냅 ✅ |
| 작음 | 조금씩 보간해 수렴 | **아무것도 안 함** ❌ |

**표준에 "방치 구간"은 없다.** 문턱은 *스냅이냐 점진이냐*를 가르는 선이지 *고치느냐 마느냐*가 아니다.

### 우리 구조에서 "점진"은 렌더가 맡는다

위 표준 서술은 시뮬과 렌더가 한 몸인 단순 모델을 전제한다. 우리는 둘이 분리돼 있고,
**부드럽게 만드는 책임은 이미 렌더가 지고 있다** — `LocalEntityInterpolator`가 내 캐릭터를
`renderCorrectionSmoother.Target(simPos)`로 그리고 매 프레임 감쇠시킨다.

이는 언리얼 CMC의 **캡슐(시뮬) 스냅 + 메시(렌더) 스무딩** 분리와 같은 구조다.

따라서 우리가 취할 모양은:

```
시뮬  →  즉시 정확히 맞춘다 (권위 그대로)      ← 이번에 고칠 것
렌더  →  그 변화를 부드럽게 흡수한다            ← 이미 있음, 안 건드림
```

**시뮬에 점진 드리프트를 추가하지 않는다.** 그러면 같은 책임을 두 곳이 나눠 갖게 되고, 무엇보다
시뮬이 영원히 "수렴 중"이라 서버와 정확히 일치하는 순간이 없다 — 히트 판정이 동기였는데 반만 해결된다.

> 언리얼식 **client-trust**(서버가 허용 오차 안이면 클라 보고 위치를 채택)는 채택하지 않는다.
> `netcode-redesign.md` §6.4가 클라 보고 위치 사용을 금지한다(치팅).

## 3. 바꾸는 것 — 상수 하나가 본체다

```csharp
// Assets/Scripts/Netcode/Reconciler.cs
private const float Threshold = 0.06f;   →   0.01f
```

**근거:**

| | |
|---|---|
| 정상 구간 오차가 **정확히 `0.000`** | 같은 코드·같은 정밀도라 걸러낼 부동소수점 잡음이 사실상 없다. 문턱의 원래 용도(잡음 방어)가 우리 조건에선 거의 필요 없다 |
| 실제 사건의 오차는 **4cm** | 1cm면 확실히 잡히고, 잡음 수준(~1e-5)보다는 훨씬 크다 |
| 게임플레이 무의미 크기 | 캐릭터 반경 대비 1cm는 판정에 영향이 없다 |

### 잔류 오차가 유계가 된다

1cm 미만 차이는 여전히 보정되지 않는다. 그러나 **누적되지 않는다** — 새 사건이 4cm를 더하면
문턱을 넘어 **통째로 0으로 리셋**되기 때문이다. 상한이 6cm에서 1cm로 내려간다.

## 4. 렌더는 이번에 건드리지 않는다

`RenderCorrectionSmoother(tau: 0.1, minCorrection: 0.025, teleport: 3)` 유지.

- 4cm 보정은 `minCorrection`(2.5cm)을 넘으니 **지금도 부드럽게 흡수**된다
- 1~2.5cm 보정은 렌더가 스냅하는데, 그 크기가 실제로 보이는지는 **모른다**

**한 번에 하나만 바꾼다.** 문턱만 바꾸고, 플레이에서 톡톡 튀는 게 보이면 그때 조정한다
(이 트랙에서 조건을 여러 개 동시에 흔들어 무효 데이터를 만든 전례가 있다).

## 5. 계측 — 재생 빈도를 잰다

문턱을 낮추면 롤백·재생이 얼마나 늘어나는지 **짐작하지 말고 측정**한다.

`ReconciliationStats`에 **재생 횟수 카운터**를 추가하고 HUD·`Dump`에 노출한다. `Reset()`이 함께 비운다.

```
[HudDump] ... reconMax=… replays=3 …
```

> 재생 = 롤백 후 anchor+1 ~ 현재까지 `world.Tick` 재실행(현 lead 기준 7~8틱).
> 엔티티 하나라 절대 비용은 작지만, **빈도가 상시로 오르는지**는 확인해야 한다.

## 6. 성공 기준 — 반증 가능하게

이미 깔린 `[ReconSpike]` 로그가 그대로 판정 도구다.

| | 고치기 전 (실측) | 고친 후 (기대) |
|---|---|---|
| 같은 `delta` 반복 | **45틱 연속 동일** | **1~2회 찍히고 사라짐** |
| 정지 중 오차 | 그대로 유지 | 0 |
| 재생 빈도 | — | 사건당 1회 수준, 상시 아님 |
| 체감 | — | 조작감 변화 없음, 화면 톡톡 튐 없음 |

**단일 판정 기준: "같은 delta가 계속 찍히는 현상이 사라지는가."**

## 8. 위험

| | 위험 | 대응 |
|---|---|---|
| 1 | 재생이 예상보다 잦아 프레임 저하 | 5절 카운터로 측정. 문턱이 상수 하나라 되돌리기 쉽다 |
| 2 | 1~2.5cm 보정이 화면에서 톡톡 튐 | 4절 — 보이면 `minCorrection` 조정(별도 변경으로) |
| 3 | 롤백이 잦아지며 재생 억제(`WorldEventBuffer.Suppress`) 경로가 더 자주 돈다 | 원래 그 용도로 만든 것이라 무해할 것으로 보나, 플레이에서 연출 중복·누락을 확인 |
| 4 | 실환경(원격·다기기)에선 미세 오차가 상시 존재할 수 있어 재생 빈도가 달라진다 | 이 판단은 **로컬 조건 기준**임을 명시. 실환경 측정에서 달라지면 재조정 |

## 9. 산업 표준 매핑

- **시뮬 즉시 보정 + 렌더 스무딩 분리** = 언리얼 CMC의 캡슐/메시 분리(`NetworkSmoothingMode`,
  mesh translation offset). `RenderCorrectionSmoother` 주석이 이미 그 대응을 적고 있다
- **epsilon 기준 스냅/보간** = Wikipedia client-side prediction 표준. 우리는 "보간" 몫을 렌더가
  맡는 구조라 시뮬은 스냅만 담당
- **client-trust 미채택** = `netcode-redesign.md` §6.4
