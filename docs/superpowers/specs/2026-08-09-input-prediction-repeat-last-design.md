# 유실된 입력은 마지막 입력으로 메운다 — 입력 예측

> 표준 입력 파이프라인 3층의 마지막 층. [무입력 명시 전송](2026-08-09-explicit-idle-input-frames-design.md)이
> 전제이며, 그것 없이는 손 뗀 것을 유실로 오해해 캐릭터가 안 멈춘다.

## 1. 문제

서버는 틱 T를 굴리려면 그 틱의 커맨드가 **반드시 하나** 있어야 한다. 없으면 건너뛰는 게 아니라
뭔가로 메워야 한다. 지금은 0(= 아무 입력 없음)으로 메운다:

```csharp
inputBufferSystem.SetCurrent(buffer, new InputCommand());   // 수평 제동
```

`{0,0}`은 "제동하라"는 **능동적인 지시**다. 플레이어가 계속 키를 누르고 있는데 패킷 하나가
유실된 경우, 서버만 혼자 한 틱 제동해 정확히 `MaxAcceleration × dt = 2.00 m/s`,
위치로 **4cm**가 어긋난다(08-06 진단의 사슬).

## 2. 해법

빈 칸을 **마지막으로 받은 커맨드의 이동**으로 메운다.

| 서버가 보는 것 | 대응 |
|---|---|
| 커맨드 있음(`{0,0}` 포함) | **그대로 쓴다.** 추측 없음 |
| 커맨드 없음 | 마지막 이동을 이어 쓴다 |

**한 틱은 20ms다.** 사람이 키를 20ms만 누르고 떼지 않는다 — 직전 틱에 걷고 있었으면 이번 틱도
걷고 있을 확률이 압도적이다. 추측이 틀려도 한 틱치 오차이고 클라 롤백이 잡는다.

### 규칙 세 가지

1. **커맨드가 있으면 그대로** — `{0,0}`도 커맨드다
2. **이동축만 이어 쓴다** — 점프·어빌리티는 1회성이라 반복하면 **두 번 발동**한다
3. **연속 8틱까지** — 넘으면 중립. 8틱 = 160ms이고, 그보다 길게 비면 순간 유실이 아니라 연결
   문제이며 낡은 입력으로 계속 달리는 게 눈에 보이기 시작한다

예측값에는 **시퀀스를 물려주지 않는다** — 받은 커맨드가 아니므로 dedup(`LastProcessedSequence`)과
`seqGap` 기준을 흐리면 안 된다.

## 3. 구조

데이터는 컴포넌트, 로직은 시스템(Anemic).

| 위치 | 추가 |
|---|---|
| `InputBuffer` (LOP-Shared) | `LastReceived`, `PredictedTicks` |
| `InputBufferSystem.Consume` | 실제 소비 시 `LastReceived` 갱신 + `PredictedTicks = 0` |
| `InputBufferSystem.PredictMissing(buffer, maxTicks)` | 빈 칸 메우기 |
| `ServerInputSystem` | miss 분기가 `PredictMissing(buffer, MaxPredictedTicks=8)` 호출 |

**클라는 변경 없다.** 클라는 자기 입력을 항상 갖고 있어 예측할 빈 칸이 없다.

## 4. 감수하는 거래 — "손 뗌"이 유실되면

`{0,0}`과 그 복구 사본이 **전부** 유실되면 서버가 이동을 이어 써서 캐릭터가 잠깐 더 간다.
지금 구조에서는 이 경우가 *우연히* 맞게 처리되고 있었다(무조건 제동이라).

| | 빈도 | 지금 | 이후 |
|---|---|---|---|
| 누르는 중 유실 | 걷는 내내 후보 (수백 틱) | ❌ 4cm | ✅ 일치 |
| 손 뗀 틱이 유실 | 딱 한 틱, 사본 3장 전부 유실해야 함 | ✅ 맞음 | ❌ 1~2틱 더 감 |

흔한 쪽에서 맞고 드문 쪽에서 틀리는 교환이다. 그리고 드문 쪽도 20ms 뒤 다음 `{0,0}`이 도착하면
멎으므로 유계다.

## 5. 산업 표준 매핑 — **정직한 상태**

- ✅ **입력 예측 = 마지막 입력 반복**은 롤백 넷코드(GGPO 계열)의 확립된 표준 기법이다.
  다만 그건 **P2P 롤백에서 *상대* 입력을 예측**하는 맥락이다.
- ⚠️ **서버 권위 엔진이 서버 측에서 못 받은 클라 입력에 같은 처리를 한다는 근거는 확인하지
  못했다.** Unity Netcode for Entities 문서는 `GetDataAtTick`의 미스 시 동작을 적어 놓지 않았고,
  Source 자료의 "repeat the last known command"는 *클라이언트* 쪽 서술이었다.
- Unity 문서가 문서로 처방하는 건 미스 대응이 아니라 **미스 예방**이다 — redundancy(기본 4틱)와
  `TargetCommandSlack`(기본 2틱).

**따라서 이 슬라이스의 근거는 "업계 표준이라서"가 아니라:**

1. 빈 칸은 반드시 메워야 하고, 0은 흔한 경우에 *능동적으로 틀린* 값이다
2. 우리 `netcode-redesign.md` Phase 3이 **"옵션 A = miss 시 마지막 인풋 반복"** 을 이미 지목해
   두고 "실환경 prune율이 유의미해지면 재개" 조건을 달았으며, 08-06 진단이 그 조건을 충족시켰다

> 이 구분을 흐리지 말 것. 근거를 과장했다가 나중에 되돌리면 비용이 크다.

## 6. 검증

| 대상 | 방법 |
|---|---|
| `PredictMissing` | **LOP-Shared EditMode 테스트 5건** (반복/1회성 제외/상한/미수신/리셋) |
| 실동작 | 플레이 — 걷는 중 유실 시 4cm가 안 생기는지 |
| 계측 | `[ReconSpike]`에서 `predVel`이 반토막 나는 서명이 사라져야 한다 |

**단일 판정 기준: 걷는 중 `predVel` 속도가 정확히 2.00 줄어드는 스파이크가 사라진다.**

로컬 잡음 바닥(5틱) 때문에 빈도 비교는 못 한다 — *서명이 나오느냐*로만 본다.
