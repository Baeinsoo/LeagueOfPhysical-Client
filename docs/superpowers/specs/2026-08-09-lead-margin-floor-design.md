# lead 마진 바닥 — 중복 전송이 실제로 쓰이게 만들기

> 08-06 진단이 찾은 "입력 한 틱 누락"의 **원인 쪽 대응**. 08-07 슬라이스(문턱 6cm→1cm)가
> *결과*를 자가 회복시켰다면, 이건 *사건 자체*를 줄인다.

## 1. 무엇이 문제인가

유실된 입력은 중복 전송(`RedundancyWindow = 3`)으로 복구되게 되어 있다. 그런데 **복구 사본은
원본보다 늦게 출발한다.**

| 사본 | 실린 패킷 | 원본 대비 |
|---|---|---|
| 원본 | 틱 T | +0 |
| 복구 1 | 틱 T+1 | +1틱 |
| 복구 2 | 틱 T+2 | +2틱 |

그런데 서버는 지각을 **1틱도** 봐주지 않는다 (`ServerInputSystem.cs`):

```csharp
long targetTick = tick;                                    // 입력 지연 0
int pruned = inputBufferSystem.PruneBefore(buffer, targetTick);   // 과거 틱은 전부 폐기
```

여유는 전부 **클라 lead**에 있어야 한다. 그런데 `LeadController`의 마진 바닥이 `0.0`이었고,
축소 조건이 공격적이라(아래 3절) 평온할 때 마진이 0까지 깎였다.

**결과: 여유가 0인 순간 중복 전송이 조용히 무력화된다.** 유실 1건이 곧 입력 미스가 되고,
서버가 그 틱을 무입력=제동으로 처리해 4cm가 어긋난다.

관측된 서명이 정확히 이 모양이다 — `prune=1 dMax=+1 seqGap=1`, 그때 여유가 평소 `dAvg=-3.0`에서
`-1.8`로 얇아져 있었다.

### 유실률이 원인이 아니라는 근거

한 틱의 커맨드는 서로 다른 패킷 3개에 실린다. 셋이 다 유실돼야 진짜로 사라진다.

| 유실률 | 3연속 유실 확률 | 60초당 기대 |
|---|---|---|
| 20% | 0.8% | ~24회 |
| **2%** | **0.0008%** | **~0.02회** |

08-07 기준선 측정은 **`unreliableLoss: 2`** 였고 거기서 사건이 났다. 기대값과 두세 자릿수 차이라
"사본이 전부 유실됐다"로는 설명되지 않는다. **윈도우를 키워도 안 고쳐진다.**

## 2. 표준은 어떻게 하나

손잡이가 두 개고, **서로를 기준으로 정하지 않는다.**

| 손잡이 | 막는 것 |
|---|---|
| 버퍼(lead) 크기 | **지터** — 도착 시각의 흔들림 |
| redundancy 깊이 | **유실** |

redundancy는 유실을 *지각으로 바꿔줄 뿐*이라, 버퍼가 견디는 지각 한도를 넘는 사본은 낭비다.
올바른 짝은 **redundancy 깊이 ≈ 버퍼 허용 틱 + 1**. 우리 윈도우 3은 원래 2틱 버퍼를 전제한
값인데, 짝이 되는 버퍼를 안 준 상태였다.

버퍼 크기 자체는 실측 도착 분포로 정한다. 업계 기본값:

| 시스템 | 목표 |
|---|---|
| Unity Netcode for Entities | `TargetCommandSlack` 기본 **2틱** |
| Overwatch | 서버가 입력 버퍼 점유를 재서 클라 시계를 가감속, **1~2 command frame** 유지 |
| LOP (변경 전) | **0** |

그리고 대부분 **세 겹**으로 깐다: 버퍼(지터) → redundancy(유실) → 마지막 입력 반복(최후 보루).
옵션 A는 폐기가 아니라 *맨 아래 층*이며, 앞의 두 층이 제 역할을 하면 거의 안 불린다.

## 3. 바꾸는 것

`GameInputTimingMessageHandler`가 `LeadController`에 **1틱 바닥**을 준다.

```csharp
private const int MinMarginTicks = 1;
...
double interval = runner.tickUpdater?.interval ?? 0;
if (interval <= 0) return;                       // 아직 틱이 안 돌아 환산 불가
var leadController = new LeadController(minMargin: interval * MinMarginTicks);
```

**바닥을 상수로 박지 않는다.** 틱 간격은 서버가 정해 런타임에 들어오므로, 20ms를 하드코딩하면
틱레이트를 바꿀 때 조용히 틀어진다. `LeadController`는 설정만 든 순수 정책 객체(가변 상태 없음)라
피드백마다(0.5초 1회) 새로 만들어도 동작이 같고, 그래야 간격 변화를 자연히 따라간다.

### 왜 2틱이 아니라 1틱부터인가

윈도우 3을 다 살리려면 2틱이 맞고 DOTS 기본값도 2다. 그래도 1틱부터 가는 이유는 **이 트랙에서
조건을 여러 개 동시에 흔들어 무효 데이터를 만든 전례**가 있어서다. 한 번에 하나만 바꾸고 잰다.

## 4. 반응성 비용

본인 조작감은 **변하지 않는다** — 클라는 예측으로 즉시 움직인다. 늘어나는 건 월드가 권위적으로
반응하는 시점(남들 화면 기준)으로 **1틱당 20ms**다. 비대칭이 선택을 결정한다:

| | 대가 |
|---|---|
| 1틱 이르게 | 권위 반응 +20ms — 체감되지 않음 |
| 1틱 늦게 | 입력 폐기 → 4cm 어긋남 + 롤백 |

이미 깔고 테스트하는 지연이 150ms라 20ms는 잡음 수준이다.

## 5. 성공 기준

08-07과 **같은 절차**로 잰다: 환경 `local`, `latency: 150` / `unreliableLoss: 2`, 같은 빈 장소에서
60초 걷기. 측정 전 `Snap gap avg ≈ 20ms`와 `Entities` 일치로 유효성 확인(하나라도 어긋나면 버린다).

| | 08-07 수정 후 (현재) | 기대 |
|---|---|---|
| `[ReconSpike]` 건수 | 4건 | **줄어든다** |
| `prune` / `seqGap` | 간헐 발생 | **0에 가까워진다** |
| `reconMax` | 0.040 | 유지 또는 감소 |
| `corrections` | 4 | 줄어든다 |
| 조작감 | — | 변화 없음 |

**단일 판정 기준: `prune`·`seqGap`이 0으로 수렴하는가.** 이게 "복구본이 제때 쓰이고 있다"의 직접
증거다. `[ReconSpike]`는 그 결과일 뿐이라 후행 지표로 본다.

## 6. 실패 시 다음 용의자

바닥을 줬는데도 `prune`이 남으면, 다음은 **축소 조건**이다. `LeadController.Adjust`는

```csharp
else if (summary.SampleCount > 0 && summary.MaxD < looseBand)   // looseBand = -1
{
    margin -= smallStep;
}
```

`MaxD`(그 창에서 가장 늦게 온 입력)가 1틱보다 이르기만 하면 줄인다 — **꼬리를 마감선에 붙이는 것을
목표로 삼고 있다.** 표준은 *평균이 2틱쯤 이르게* 를 목표로 한다. 바닥을 줘도 목표가 꼬리-제로면
계속 바닥에 붙어 있게 되므로, 그때는 밴드를 옮긴다.

## 8. 1차 측정 결과 — 바닥만으로는 부족했다

**실패가 재현됐다.** 스파이크 로그가 그대로 남았다:

```
tick=10651 err=0.040
  predVel=(-3.96, 0, 0.54)   속도 4.00
  srvVel =(-1.98, 0, 0.27)   속도 2.00      ← 정확히 2.00 감소 = 1틱 제동
  timing[dAvg=-1.7 dMax=2 prune=2 seqGap=2]
```

`MaxAcceleration(100) × dt(0.02) = 2.00`이 정확히 맞고 오차도 정확히 `0.040`이다. 그 직전
스파이크는 속도 4.00 → **0.00**(2틱 연속 제동), 오차 `0.120`.

**`dMax=+2` — 입력이 2틱 늦게 도착했다.** 1틱 바닥으로는 못 막는다. 복구 사본 2번(+2틱)조차
경계에 걸린다.

### 계기가 거짓말을 하고 있었다

HUD 덤프의 `prune`/`seqGap`은 **최신 0.5초 창** 값이다(`InputTimingStats.Update`가 덮어씀).
사건이 지나간 뒤 찍으면 0이라 "실패 없음"으로 읽힌다 — 실제로 그렇게 읽고 성공으로 판단할
뻔했다. `Recon avg` 함정과 같은 종류다.

측정이 오염된 조건도 있었다: `catch-up capped (behind by 456)` = **9초 멈춤**, `entities=26`
(기준선은 2).

### 왜 1틱이 부족했나 — 평형점이 실패를 포함한다

`LeadController`의 옛 기본 밴드는 `tightBand=1, looseBand=-1`이라, **가장 늦게 온 입력이 1틱
지각하는 상태(`maxD=+1`)를 평형으로 용인**한다. 그 자리에서는 지터가 한 번만 튀어도 곧바로
폐기다. 표준은 꼬리를 마감선이 아니라 *이른 쪽*에 둔다.

## 9. 후속 변경 (같은 슬라이스)

**계기 (동작 아님):**

| 추가 | 이유 |
|---|---|
| `InputTimingStats`에 누적 `TotalPrune`/`TotalSeqGap`/`WorstMaxD` + `Reset()` | 창 값만으로는 판정 불가 |
| 덤프에 `margin` (`LeadState.AheadMargin`) | 이 트랙이 겨냥한 값인데 관측할 수단이 없었다 |
| `ITickUpdater`에 `catchUpCappedCount`/`maxTicksBehind`, 덤프에 `stalls`/`behindMax` | 멈춤이 낀 창은 버려야 하는데 경고가 에피소드당 1회라 지나가면 사라진다 |

**정책 — 데드존 밴드 이동:**

```
tightBand:  1 → -1     꼬리가 "1틱 이르게"보다 늦으면 키운다
looseBand: -1 → -3     꼬리가 3틱 이상 이를 때만 줄인다
```

평형점이 **`maxD ∈ [-3, -1]`(꼬리가 1~3틱 이르게)** 로 옮겨간다 — DOTS `TargetCommandSlack=2`와
같은 자리. 1틱 바닥은 그대로 둔다(무해한 안전장치이며, 밴드가 정상 동작하면 거의 안 닿는다).

GameFramework EditMode에 새 평형점 테스트 6건 추가.

### 2차 판정 기준

| | 1차 (실측) | 기대 |
|---|---|---|
| `worstD` (누적 최악 도착) | **+2** (2틱 지각) | **≤ -1** (항상 이르게) |
| `pruneTot` / `seqGapTot` | 2 / 2 | **0** |
| `margin` | 미관측 | 바닥(20ms)보다 위에서 안정 |
| `stalls` | 1 (9초 멈춤) | **0** — 아니면 그 창은 버린다 |
