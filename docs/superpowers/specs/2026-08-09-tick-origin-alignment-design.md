# 매치 시작 틱 정렬 — 틱은 그것을 굴릴 시계에서 유도한다

> 08-09 3층 작업 중 발견. 매치 시작 직후 입력 **162개가 통째로 폐기**되고, 그동안 서버 캐릭터는
> 원점에 정지해 있었다(클라 화면에서는 걷고 있었다).

## 1. 증상

접속 직후 창에서:

```
timing[dAvg=142.4 dMax=208 prune=162 seqGap=0]
srvPos=(0.00, 0.00, 0.00)      ← 서버 캐릭터가 안 움직임
predPos=(-0.14, 0.00, -0.14)   ← 클라는 이미 걷고 있음
```

`d = serverTick − inputTick`이 **+142**라는 건 클라가 찍은 틱 번호가 서버보다 142 낮았다는 뜻이다
(≈2.8초). 그 입력들은 서버가 이미 지나간 틱을 가리키므로 전량 prune된다.

**사용자에게는 "게임 시작 직후 몇 초간 조작이 안 먹는다"로 보인다.**

## 2. 원인 — 틱의 원점과 시드가 따로 논다

### 서버

```csharp
runner.Run(0, TICK_INTERVAL, 0);        // 틱 0, 경과시간 0에서 출발
...
elapsedTime = networkTime.ServerNow;    // 매 프레임. = Mirror.NetworkTime.time = 프로세스 가동 시간
```

시드는 0인데, 다음 프레임에 `elapsedTime`이 **프로세스 가동 시간**으로 덮인다. 서버가 33초 떠
있었다면 `processibleTick = 1680`. 틱 루프는 프레임당 최대 8틱만 따라잡으므로:

```
1680 ÷ 8 = 210프레임 ≈ 3.5초 동안 8배속 질주
```

즉 **`Run`에 넘긴 0은 한 프레임 만에 무의미해진다.** 틱의 실질 원점은 "매치 시작"이 아니라
"서버 프로세스 가동 시각"이다.

### 클라

```csharp
runner.Run(gameInfo.Tick + 1, gameInfo.Interval, gameInfo.ElapsedTime);
```

`gameInfo`는 **서버가 그 메시지를 만든 순간**의 스냅샷이다. 전송 + 맵 로딩 + 엔티티 스폰이 끼는
동안 서버는 계속 달리므로 클라는 낡은 번호에서 출발한다.

그런데 클라의 *시계*는 `ClockDilator`가 오차 0.5초를 넘으면 **즉시 snap**해 올바른 값으로 맞춘다.
결과: **시계는 맞는데 틱 번호만 뒤처진 상태** → 클라도 8배속으로 질주하며, 그 동안 보내는 입력에는
뒤처진 번호표가 붙는다.

> **로컬 아티팩트가 아니다.** 로컬은 에디터 서버를 오래 켜둬 가동 시간이 커서 과장될 뿐,
> 실환경도 룸 컨테이너 부팅~매치 시작만큼(몇 초) 같은 일이 일어난다.

## 3. 해법 — 틱을 시계에서 유도한다

원칙 한 줄: **틱은 그것을 굴릴 시계에서 유도한다.** 지금은 시드와 시계가 따로라 그 차이만큼
질주가 생긴다.

```csharp
// 서버 (LOPRoom)
double now = networkTime.ServerNow;
runner.Run((long)(now / TICK_INTERVAL), TICK_INTERVAL, now);

// 클라 (LOPRoom) — gameInfo 스냅샷 대신 살아 있는 시계에서
double target = networkTime.PredictedTime + leadState.AheadMargin;
runner.Run((long)(target / gameInfo.Interval), gameInfo.Interval, target);
```

따라잡을 격차가 애초에 없으므로 질주가 사라진다.

### 왜 이게 성립하나 — 양쪽이 같은 시계를 본다

| | `ServerNow` |
|---|---|
| 서버 | `Mirror.NetworkTime.time` (권위) |
| 클라 | `Mirror.NetworkTime.predictedTime − rtt/2` (같은 값의 추정) |

그래서 **틱 = 공유 시계 ÷ 간격**은 양쪽이 독립적으로 계산해도 같은 값이 된다. 시작 틱을
메시지로 주고받을 필요 자체가 없어진다. `tick = elapsedTime / interval`은 이미 `processibleTick`이
쓰고 있는 관계식이라 새 규칙도 아니다.

## 4. 검토한 대안 — 매치 기준 원점(틱 0 = 매치 시작)

개념적으로는 이쪽이 깔끔하다. 틱 번호가 "매치 시작 후 몇 번째"라는 뜻을 갖고, 로그를 읽기도 쉽다.

**기각 이유**: 그러려면 매치 시작 시각(epoch)을 양쪽이 공유해야 하므로 새 와이어 필드와 그 전파
경로가 생긴다. 얻는 건 *숫자의 가독성*뿐이고, 틱을 키로만 쓰는 코드(§5)에는 아무 차이가 없다.
YAGNI.

> 나중에 리플레이·관전처럼 "매치 내 시각"이 실제로 필요해지면 그때 도입한다. 그 경우에도 이
> 슬라이스의 "틱은 시계에서 유도" 원칙은 그대로 유지된다 — 시계만 바뀔 뿐이다.

## 5. 영향 범위 — 실제로 확인한 것

틱 번호의 *크기*에 기대는 코드가 있는지 확인했다.

| | 결과 |
|---|---|
| `SequenceBuffer` (스냅샷·입력 히스토리) | ✅ 무관. `((tick % cap) + cap) % cap` + 병렬 틱 배열로 stale 판별 — 음수·큰 값 모두 안전 |
| `SnapshotHistory` | ✅ 위에 위임 |
| `Reconciler` 앵커 | ✅ `snap.tick` 기준 상대 비교만 |
| 서버 `PruneBefore(tick)` | ✅ 상대 비교 |
| 결정론 RNG (틱을 키에 씀) | ✅ 양쪽이 같은 틱을 보면 같은 값. 이 변경이 그 일치를 *개선*한다 |
| `gameInfo.Tick` / `ElapsedTime` | ⚠️ **무용지물이 된다** — 아무도 안 읽게 된다 |

즉 실질 위험은 "양쪽 틱이 어긋나는 것"뿐이고, 이 변경은 그걸 줄이는 방향이다.

## 6. 위험

| | 위험 | 대응 |
|---|---|---|
| 1 | 클라 접속 직후 `NetworkTime`이 아직 수렴 중이면 시작 틱이 살짝 어긋난다 | 어긋나도 기존 dilation 경로가 흡수한다(지금은 2.8초, 그때는 수십 ms 수준). 시작 시점엔 이미 몇 초 접속돼 있어 수렴 후다 |
| 2 | 서버 틱 번호가 프로세스 가동 시간에 비례해 커진다 | `long`이라 오버플로 없음. 키로만 쓰여 무해(§5) |
| 3 | `gameInfo.Tick`을 나중에 누가 다시 읽으면 낡은 값을 믿게 된다 | 필드에 "쓰지 않는다" 주석. 제거는 proto 정리 슬라이스 |
| 4 | 8배속 질주가 사라지면서 그동안 가려져 있던 다른 시작 문제가 드러날 수 있다 | 드러나면 그게 이득. 별도로 다룬다 |

## 7. 검증 — 이건 로컬에서도 잴 수 있다

lead 튜닝과 달리 **효과 크기(142틱)가 로컬 잡음 바닥(5틱)보다 훨씬 크다.**

| | 지금 (실측) | 기대 |
|---|---|---|
| 매치 시작 직후 `dAvg` | **+142** | **음수**(정상 여유) |
| `prune` (시작 창) | **162** | **0 근처** |
| 시작 직후 서버 캐릭터 | 원점에 정지 | 클라와 함께 움직임 |
| `[TickUpdater] catch-up capped` | 시작 시 발생 | 시작 시 없음 |

**측정 절차가 기존과 다르다** — 지금까지는 warm-up 후 `Reset`했지만, 여기서는 **매치 시작 순간부터**
재야 한다. 입장 직후 바로 걷기 시작 → 10초 뒤 `Dump`.

**단일 판정 기준: 시작 직후 `prune`이 세 자릿수에서 0 근처로 떨어지는가.**

## 8. 산업 표준 매핑

- **틱 = 공유 시계에서 유도** — Overwatch/DOTS/Quantum 모두 클라·서버가 공통 시간 기준에서 틱을
  산출하고, 시작 틱을 별도로 주고받지 않는다. 시드 메시지로 시작 번호를 정하는 건 우리 관성이다.
- **catch-up 상한(프레임당 8틱)** — 이건 그대로 둔다. 프레임 히칭 대비 장치로 여전히 필요하고,
  이번 변경은 *상한에 걸릴 격차 자체*를 없애는 것이지 상한을 손대는 게 아니다.
