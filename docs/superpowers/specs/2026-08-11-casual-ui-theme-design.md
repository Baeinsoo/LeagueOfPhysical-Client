# 캐주얼 UI 테마 — 폴가이즈 톤 공통 스타일

프론트엔드·인게임 UI 전반에서 "덜 만든 티"를 걷어낸다. **새 이미지 에셋 0장**으로,
색·테두리·라운드·폰트만 손본다. 최종 아트가 아니라 **최종 아트가 와도 버려지지 않는 바닥**을
까는 작업이다.

## 1. 배경 — 왜 더미로 보이나

원인은 **아트가 없어서가 아니다.** 화면 8개의 USS를 전수 확인한 결과, 원인은 다섯이고 넷은
이미지 없이 해결된다.

| 원인 | 근거 |
|---|---|
| **버튼이 유니티 기본 스킨** | `.login-button`·`.lobbyhome-play`·`.matching-cancel`이 크기·폰트만 지정. `background-color`도 `:hover`/`:active`도 없어 회색 기본 버튼이 그대로 노출 |
| **폰트가 기본 폰트** | "상점"·"프로필"·"◀ 뒤로" 등 한글이 있는데 전용 폰트 미지정 |
| **색이 화면마다 복붙** | `rgb(18,18,24)` / `rgb(30,30,38)` / `rgba(20,20,28,0.92)` / `rgba(20,20,28,0.95)` — 거의 같은데 미묘하게 다름. `MatchResultView.uss`와 `MatchingWaitingView.uss`는 클래스 이름만 다르고 값이 100% 동일 |
| **톤이 게임과 반대** | 배경 PNG(치비·파티·고채도) 위에 검정 반투명 카드 = 다크 관리자 대시보드 톤 |
| **움직임 0** | 등장·눌림 전환 없음 |

즉 **스타일이 지정되지 않은 것**이지 에셋이 없는 게 아니다. 이 문서는 그 스타일을 채운다.

## 2. 결정 요약

| 결정 | 내용 |
|---|---|
| 톤 = **폴가이즈 쪽** | 플랫 고채도 + **네 방향 균일한** 두꺼운 흰 테두리. 그라데이션을 안 써서 순수 USS로 재현됨 (§4) |
| 브롤스타즈 톤 기각 | 그라데이션·광택이 USS에 없어 9-slice 스프라이트 5장+ 필요. 최종 아트 미정 단계라 보류 (§3-2) |
| Meshy 등 3D 생성 도구 기각 | UI는 3D 생성기의 산출물이 아님 (§3-1) |
| 배색 = **타이틀 로고에서 추출** | 주 CTA 주황 `#F5931E`. 로고와 UI가 한 세트로 보이게 (§5) |
| 색을 **토큰 한 곳**에 모음 | `Theme.uss`의 `:root` 변수. 화면 USS에는 레이아웃만 남김 (§6) |
| 적용 지점 = **PanelSettings의 TSS** | 화면마다 붙이지 않고 전역 1회 (§6) |
| 폰트 = **주아체 (Jua), SDF** | 글자 테두리·그림자가 SDF 폰트에서만 동작 (§9) |
| 입체감 | 시도했다가 폐기 — 테두리는 네 방향 완전 균일, 눌림 `translate`로만 표현 (§7) |
| DebugHud 제외 | 개발용이라 꾸미면 가독성이 나빠짐 (§9) |
| GamePad 아이콘 제외 | 이미지가 필요한 유일한 항목. 글자(DASH/JUMP) 유지 (§9) |

## 3. 검토 후 기각한 대안

### 3-1. Meshy 등 생성 AI로 UI 제작

**Meshy는 텍스트/이미지 → 3D 메시 생성기다.** 산출물이 `.glb`라 버튼 테두리·패널 프레임 같은
2D 부품이 나오지 않는다. 3D가 UI에 쓰이는 자리는 ①입체 아이콘을 렌더해 스프라이트로 굽기,
②로비 캐릭터 미리보기(RenderTexture) 둘뿐이고, 둘 다 이 작업의 범위가 아니다.

2D 이미지 생성 AI는 성립하지만 이 단계에선 ROI가 낮다 — 9-slice로 쓰려면 네 모서리가 정확히
대칭이고 알파 경계가 깨끗해야 하는데 생성 AI가 가장 취약한 종류라 수작업 보정이 붙는다.

### 3-2. 브롤스타즈 톤 (스프라이트 기반)

기각이 아니라 **보류**다. 목업으로 비교했고 화려함은 확실히 우위였다. 다만 재료가 USS에 없다:

| 재료 | UI Toolkit |
|---|---|
| 버튼 그라데이션 | ❌ USS에 `linear-gradient` 없음 |
| 요소 그림자 | ❌ `box-shadow` 미지원 |
| 금속 트림·광택 | ❌ |
| 글자 테두리 / 글자 그림자 | ✅ `-unity-text-outline-*` / `text-shadow` |

필요 에셋은 버튼 3종 + 패널 1 + 칩 1 + 아이콘 5~8. 9-slice라 버튼 1장이 모든 크기를 커버해
양 자체는 적지만, **최종 아트 방향이 정해지지 않은 지금 만들면 버려질 확률이 높다.**

> 나중에 올려도 손해가 없다. 이 문서의 구조·색·클래스는 그대로 두고 `background-image`만
> 추가하는 작업이라 **재작업이 아니라 덧칠**이다.

### 3-3. 어두운 톤 유지 / 반투명 유리판

- **어두운 톤**: 글자 가독성은 최고지만 배경 위에 어두운 막이 필요해 **애써 만든 배경이 죽는다.**
- **반투명 유리**: 유리 느낌의 핵심인 배경 흐림(blur)이 **UI Toolkit에 없다.** 반투명 흰 판까지가
  최대치이고, 그 결과물은 파티 톤이 아니라 모던·앱스토어 톤이다.

## 4. 확인된 UI Toolkit 능력 (설계 전제)

Unity `6000.3.16f1` 기준으로 확인했다.

| 기능 | 지원 | 이 설계에서 |
|---|---|---|
| USS 변수 `--x` + `var(--x)` | ✅ | 색·치수 토큰 |
| Theme Style Sheet(`.tss`) + PanelSettings | ✅ | 전역 적용 지점 |
| `-unity-text-outline-width` / `-color` | ✅ (SDF 폰트 한정) | 글자 테두리 |
| `text-shadow` | ✅ (SDF 폰트 한정) | 글자 그림자 |
| `border-*-width` 개별 지정 | ✅ | 시도(아래쪽만 두껍게) 후 폐기 — 최종은 네 방향 균일 두께(§7) |
| `translate` + `transition` | ✅ | 눌림 반응 |
| `linear-gradient` | ❌ | 안 씀 |
| `box-shadow` | ❌ | 자식 요소로 대체하려다 폐기 — 대체하지 않기로 결정(§7) |
| 배경 흐림(blur) | ❌ | 안 씀 |

> 변수 제약: `var()`를 다른 함수 안에 넣을 수 없고 연산도 안 된다. 파생값(예: 진한 버전)은
> 별도 토큰으로 둔다.

프로젝트 설정도 확인했다 — `UIPanelSettings.asset`이 `Scale With Screen Size` / 기준 해상도
**1920×1080** / `Match: 0`(가로폭 기준)이다. 따라서 **USS의 px 값은 1920×1080 좌표계**로 쓴다.

## 6. 구조 — 색은 한 곳, 화면은 얇게

```
UIPanelSettings.asset  (themeUss)
   └─ Assets/UI/Theme/LopTheme.tss
        ├─ @import url("unity-theme://default")   ← 필수. 빼면 기본 컨트롤이 깨짐
        └─ @import  Theme.uss
             ├─ :root { --lop-* }        ← 색·치수 토큰
             └─ .btn / .card / .title …  ← 공통 부품
```

- **전역 적용은 TSS 한 곳**에서 끝난다. 화면마다 `<Style src>`를 붙이지 않는다.
- TSS가 `@import`로 다른 USS를 참조하는 것은 유니티 문서가 명시한 표준 용법이다. 프로젝트 에셋을
  가리키는 정확한 URL 표기는 구현 시 UI Builder가 생성하는 형태를 따른다.
- **각 화면 USS에는 레이아웃(위치·크기·정렬)만 남긴다.** 색·테두리·라운드·폰트는 전부 공통 클래스로
  옮긴다. 이후 색 변경은 토큰 한 줄 수정 = 8화면 동시 반영.
- 중복인 `MatchResultView.uss` / `MatchingWaitingView.uss`는 공통 `.card` 계열로 흡수한다.

### 토큰

색은 §5 표를 `--lop-primary`, `--lop-primary-shade`, `--lop-secondary`, … 형태로 옮긴다.
치수 토큰은 1920×1080 기준의 시작값이며 **구현 중 눈으로 보고 조정한다.**

| 토큰 | 확정값 | 쓰임 |
|---|---|---|
| `--lop-border-s` | `8px` | 요소 흰 테두리 (버튼·카드 공통) |
| `--lop-radius-l` | `40px` (시작값 44px에서 조정) | 버튼 |
| `--lop-radius-m` | `36px` | 카드·패널 |
| `--lop-danger` | `#FF7878` | 위험/경고 글자 (로그인 에러 등) — Task 6에서 추가, 하드코딩 `rgb(255,120,120)` 토큰화 |

> **삭제된 토큰(Task 6)**: `--lop-bevel`/`--lop-bevel-s`/`--lop-radius-pill`는 §7의 "아래쪽만
> 두껍게" 입체감 방식이 폐기되면서 사용처가 0이 됐다. `--lop-border`(12px)도 리뷰에서 추가로
> 지적됨 — `.btn`/`.card` 모두 `--lop-border-s`만 쓰고 `--lop-border`는 정의만 되고 어디서도
> 참조되지 않았다. 넷 다 `grep -rn` 확인 후 정의 줄까지 삭제했다.

### 공통 부품

| 클래스 | 무엇 |
|---|---|
| `.btn` | 버튼 공통 — 흰 테두리(네 방향 균일), 라운드, 글자 테두리, 눌림 전환 |
| `.btn--primary` | 주황 CTA |
| `.btn--secondary` | 하늘파랑 (취소·뒤로·상점 네비 겸용) |
| `.btn--nav2` / `.btn--nav3` | 하단 네비 2·3번째 색 (1번째는 `.btn--secondary` 재사용) |
| `.card` | 크림색 패널 |
| `.title` | 큰 제목 글자 (테두리 + 그림자) |
| `.card-text` | 카드 안 본문 글자 |
| `.scrim` | 모달 뒤 어두운 막 |

> **`.pill`은 만들지 않았다.** 상단 재화·레벨 표시 UI가 어느 화면에도 아직 없어(§14 Open
> Decisions) 만들 대상이 없었다 — 죽은 코드를 미리 깔지 않았다.
>
> **`.btn__base`도 만들지 않았다.** §7 폐기와 함께 사라졌다.
>
> **`.btn--nav1`은 Task 6에서 삭제했다.** `.btn--secondary`와 배경색·아웃라인색이 완전히
> 동일한 중복 규칙이었다 — 상점 버튼(`LobbyHomeView.uxml`)을 `.btn--secondary`로 교체했다.
> 값이 같으므로 화면 결과는 바뀌지 않는다.

UXML도 함께 수정된다 — 예: `<ui:Button class="lobbyhome-play">` →
`<ui:Button class="btn btn--primary lobbyhome-play">`. 화면 USS의 `.lobbyhome-play`에는
위치·너비만 남는다.

## 7. 입체감 — 폐기됨, 테두리는 네 방향 균일로 확정

> **이 절은 실행 중 폐기된 설계다.** 아래는 원래 계획과 왜 바뀌었는지의 기록이다.

원래 계획은 "아래쪽 테두리만 두껍게" + 주 CTA는 "바닥면 역할의 자식 `VisualElement`"로 입체감을
내는 것이었다(`box-shadow`가 USS에 없어서 나온 우회). 구현 중 사용자가 **두 번** "테두리가
균일하지 않다"고 지적했다 — 흰 테두리 세 변 + 아래쪽만 다른 두께/색으로 처리하니 한 바퀴를
훑었을 때 "흰-흰-흰-어두움"으로 읽혀 의도한 입체감이 아니라 그냥 **불균일한 테두리**로 보였다.

**최종 결정: 테두리는 네 방향 완전 균일(`border-width: var(--lop-border-s)`, 색은
`--lop-outline` 흰색 하나), 입체감은 포기한다.** 대신 눌림 반응(§8)의 `translate` 움직임만으로
"눌리는 버튼"임을 전달한다. `.btn__base`(바닥면 자식 요소)는 만들지 않았다.

## 8. 눌림 반응

모바일이라 마우스 오버보다 **눌림이 중요**하다.

- `:active` 상태에서 `translate: 0 4px`로 버튼이 살짝 아래로 내려갔다가, 손을 떼면
  `transition`으로 원래 위치로 돌아온다. (§7 폐기로 "바닥 두께가 줄어든다"는 더 이상 없다 —
  순수 이동만으로 표현한다.)
- `transition-duration`은 짧게(70ms). 길면 조작이 굼떠 보인다
- `:hover`는 밝기만 살짝. PC 테스트용이고 모바일에선 안 보인다

전부 USS로 끝나고 C# 변경이 없다.

## 9. 폰트

**주아체(Jua)** 를 쓴다. Google Fonts에 OFL로 올라와 있어 상업 이용이 가능하고 한글을 지원한다.

- TTF → **Font Asset(SDF)** 으로 변환 후 `:root`의 `-unity-font-definition`에 지정
  - Unity `6000.3.16f1`의 실제 메뉴 경로는 `Assets > Create > Text > Font Asset`이 **아니다** —
    그 항목은 이 버전에 없다. 실제 경로는 **`Assets > Create > Text Core > Font Asset > SDF`**.
- **SDF여야 한다** — 유니티 문서상 글자 테두리·그림자 효과가 SDF 렌더 모드에서만 동작한다.
  비트맵으로 만들면 목업의 글자 테두리가 나오지 않는다
- 한글은 Font Asset을 **Dynamic 모드**로 만든다 — 한글 음절이 많아 전부 굽지 않고 필요한 글자만
  그때그때 아틀라스에 올린다 (Font Asset 자체의 설정이며, PanelSettings의 동적 아틀라스와는
  별개 항목이다)
- 주아체에 없는 글자를 대비해 **폴백 폰트**를 지정하려 했으나, 적합한 후보가 없어 **지정하지
  못했다** — 상세와 남은 위험은 §9-1 참고

### 9-1. 한글 커버리지 위험 — 미해소 (Task 6에서 재조사)

`Jua-Regular.ttf`의 cmap을 파싱한 결과 **한글 음절(가~힣) 커버리지는 2367/11172(약 21%)**다.
현재 UI가 실제로 쓰는 글자(상점·프로필·설정·뒤로 등 고정 라벨)는 전부 이 2367자 안에 있어
지금 화면들에서는 문제가 드러나지 않는다. 하지만 **플레이어 닉네임처럼 사용자가 입력하는
한글**은 이 21% 밖의 희귀 음절이 나올 수 있고, 그 경우 폴백 폰트가 없으면 두부(□)로 깨진다.

Task 6에서 `Jua-Regular SDF.asset`의 Fallback Font Assets에 넣을 만한 한글 폰트가 프로젝트에
있는지 다시 찾았다 — **없다.** 프로젝트에 있는 다른 SDF 폰트는 `LiberationSans SDF`(TextMesh Pro
기본, 라틴 전용)와 Mirror Edgegap 에디터용 폰트(`Spartan-*`, `UbuntuMono-R`, `BaronNeue` — 전부
라틴 전용)뿐이고, 서브모듈 `Assets/Art`에도 폰트 파일이 없다. 즉 **후보가 하나도 없어 폴백을
지정하지 못했다.** 새 폰트를 받아오는 것은 이번 태스크 범위 밖이라, 이 위험은 미해소 상태로
남긴다 — 사용자 입력 한글이 노출되는 화면(예: 닉네임 표시)을 만들 때 반드시 재검토할 것.

### 11-1. 인게임 육안 검증 — 미완

위 표는 프론트엔드 7화면 기준이다. **인게임 HUD(CharacterHud·GamePad·Nameplate·DamageFloater)의
육안 검증은 Task 6 시점까지 완료하지 못했다** — 매칭이 성사되지 않아 인게임 씬에 도달하지
못했다(에디터 2대 중 한쪽만으로는 매칭 상대가 없음). 다음 항목은 **사용자가 실제로 매칭에
들어가 직접 확인해야 한다**:

- HUD 패널이 크림 카드로 보이고 배경 위에서 읽히는지
- 액션 버튼 5개가 **완전한 원**으로 렌더되는지 — UI Toolkit `border-radius` 클램핑이 큰 값에서
  어떻게 동작하는지 이 프로젝트에서 실측하지 못했다
- 원형 버튼 안 글자가 수직 중앙에 오는지
- **`.action-button`(`GamePad.uss`)이 `.btn--primary`(`Theme.uss`)를 이기는지** — 둘 다 단일
  클래스 셀렉터(우선순위 동일)라 결과가 USS 로드 순서에 의존한다. 지면 원형이 아니라 둥근
  사각형으로 보인다
- 네임플레이트 흰 테두리 두께 / 데미지 숫자와 배경의 분리도

세로로 긴 비율(1080×2340)에서의 로비 하단 네비바 확인(§12 리스크)도 Task 6에서 실제로 시도했다
— 리플렉션으로 커스텀 Game View 크기(`Task6-Portrait`, 1080×2340)를 만들어 선택한 뒤
`capture_game_view source=screen`으로 재캡처했다. 결과: **두 캡처 모두 `width:1280,height:720`으로
동일하게 보고됐고, 이미지 내용도 화면비가 바뀌지 않은 채(가로 배치 그대로) 확대/스크롤 정도만
달라졌다** — Game View 크기 변경이 백버퍼 캡처 파이프라인에 반영되지 않는 것으로 보인다. 즉
**세로 비율에서 네비바가 잘리는지 여부는 이번에도 확정하지 못했다.** 확인 못 했다고 기록하고
이 위험은 미해소로 남긴다 — 실기기 또는 에디터의 실제 Game View 크기 드롭다운(수동 조작)으로
검증할 것.

## 15. 계획 결함 기록

- **`LoginView.uxml` 전체 교체본 계획이 `login-error` 라벨을 누락했었다.** `LoginView.cs:33`이
  `name="login-error"`로 이 라벨을 조회해 로그인 실패 메시지를 표시하는데, 초기 계획 문서의
  교체본에는 이 요소가 빠져 있었다. 구현자가 UXML을 교체하기 전 기존 파일을 대조해 발견했고,
  라벨을 보존한 채 테마 클래스만 입혔다. UXML 전체 교체 계획은 **`name` 속성이 코드에서 참조되는
  요소를 빠짐없이 옮겼는지 기존 파일과의 diff로 확인**해야 한다는 교훈이다.
