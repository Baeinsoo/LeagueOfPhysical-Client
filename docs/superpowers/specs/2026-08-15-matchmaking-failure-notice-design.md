# 매칭 실패 안내 — 취소와 실패를 구분한다

매칭 대기 중 화면이 **아무 설명 없이** 닫히고 로비로 돌아와, 유저가 *내가 취소한 것*인지
*사람이 안 모여 실패한 것*인지 알 수 없는 문제를 닫는다.

- 범위: **lop-backend + Unity 클라**. 게임서버 무관.
- 목표: 시간초과로 끝나면 안내가 뜨고, 취소로 끝나면 안 뜬다.

---

## 1. 문제

지금 대기 화면(`MatchingWaitingView`)은 `MatchmakingViewModel.IsMatching` 하나로만 여닫힌다.
그 신호는 **왜 끝났는지를 담지 않는다.** 그래서 세 경우가 화면상 구분되지 않는다:

| 실제로 일어난 일 | 유저가 보는 것 |
|---|---|
| 유저가 취소를 눌렀다 | 대기 화면이 닫힘 |
| 10분(큐별 `ticket_ttl_seconds`)이 지나 티켓이 버려졌다 | **대기 화면이 닫힘 (같음)** |
| 매치가 잡혀 게임으로 들어간다 | 대기 화면이 닫히고 로딩으로 |

두 번째가 이 슬라이스의 대상이다.

### 왜 지금 구조로는 그냥 안 되나

"매칭에서 벗어나면 클라가 사유를 조회한다"가 자연스러운 해법인데, **조회할 대상이 그 순간
이미 없다.** 인과가 이렇게 묶여 있기 때문이다:

```
티켓이 사라짐 ─→ 로비가 "티켓 없네" 판단 ─→ 출석부가 None으로 ─→ 클라가 알아챔
     ↑                                                              │
     └─────────── 이때 티켓을 조회하면 항상 "없음" ←────────────────┘
```

출석부가 바뀐 **이유 자체가 "티켓이 사라졌기 때문"**이라, 바뀐 것을 보고 티켓을 찾으면 100% 실패한다.
그러므로 필요한 것은 조회 경로가 아니라 **사라질 때 흔적을 남기는 것**이다.

## 2. 하지 않는 것 (검토 후 명시적 제외)

| 안 함 | 이유 |
|---|---|
| **티켓 축으로 전환** (클라가 티켓을 폴링) | 별도 트랙. 아래 §4 참조 — 이 슬라이스는 그 전환을 막지 않는다 |
| **티켓을 종단 상태로 남기기** | 잠금(유저당 티켓 1개)·로비 자가치유 두 곳이 딸려온다. §3에서 기각 |
| **`locationDetail` 타입 강화** | 로드맵의 별도 일감. 이번에 추가하는 칸도 그때 함께 정리된다 |
| **토스트/알림 인프라** | `Notification` 밴드는 이름만 있고 구현체가 없다. 만들면 이 슬라이스가 알림 인프라 작업으로 번진다 |
| **사유 종류 확장** | 지금 실재하는 둘(`User`/`Timeout`)만. 늘릴 때는 §4의 표준 이름 공간에서 고른다 |
| **취소 시 안내** | 본인이 누른 것이라 알린 이유가 없다. 이 슬라이스의 핵심이 그 구분이다 |

## 3. 결정 — 사유를 어디에 남기나

세 후보를 비교했다.

| | 어디에 | DB에 늘어나는 것 | 클라 추가 조회 | 딸려오는 일 |
|---|---|---|---|---|
| ① | 티켓을 안 지우고 종단 표시 | 끝난 티켓(보관기간 동안) | 있음 | **잠금 해제 + 로비 판정 수정 2곳** |
| ② | **출석부 메모(`locationDetail`)** | **없음** | **없음** | 시간초과 경로에 출석부 쓰기 신설 |
| ③ | "마지막 매칭 결과" 별도 1행 | 작은 표 1개(유저당 1행) | 있음 | 없음 |

**② 채택.**

- **저장소가 늘지 않는다.** 출석부는 유저당 1행이 이미 있고, 메모 칸(JSON)도 이미 있다.
- **클라가 추가 조회를 하지 않는다.** 이미 1초마다 출석부를 보고 있으므로 사유가 딸려온다.
- **취소 경로는 쓰기가 이미 있다.** `MatchmakingService.cancelMatchmaking`이 성공 후 출석부를
  `None`으로 직접 갱신한다 — 그 자리에 사유 한 칸을 채우면 끝이다.
- 출석부 축을 유지하기로 한 결정과 결이 맞다. 출석부가 이미 "매칭 중"을 말하고 있으니,
  "왜 끝났는지"도 같은 자리에서 말한다.

**①을 기각한 이유(중요 — 되살리려는 사람을 위해):** 티켓을 남기면 두 곳이 조용히 깨진다.
(a) `MatchmakingTicketUser`는 매핑이 아니라 **유일성 잠금**이라(기본키가 userId), 남으면 그 유저는
새 매칭을 영영 못 만든다. (b) 로비 자가치유의 낡음 판정이 *"티켓이 없으면 낡음"*이라, 남으면
"아직 매칭 중"으로 읽어 **유저가 대기 화면에 갇힌다.** 둘 다 해결 가능하지만(표준도 그렇게 한다),
②는 둘 다 건드리지 않는다.

**③을 기각한 이유:** ②와 값은 비슷한데 저장소와 조회가 하나씩 더 는다.

## 4. 산업 표준 매핑

| 우리 것 | 대응 | 비고 |
|---|---|---|
| 사유 필드명 `cancellationReason` | PlayFab **`CancellationReason`** | 이름을 그대로 쓴다 |
| 값 `User` / `Timeout` | PlayFab `CancellationReason`의 `User` / `Timeout` | 표에 있는 7개 중 실재하는 둘 |
| 사유를 **티켓과 별도 통로**로 나름 | GameLift **매칭 이벤트**(`MatchmakingTimedOut`/`MatchmakingCancelled`), Open Match **`AssignmentFailure`** | 티켓에 적는 방식만 표준인 것이 아니다 |
| 유저 위치(출석부) 자체 | Xbox **MPSD**, EOS **Presence** | 매칭 진행까지 여기서 보는 것이 우리 변형 |

**표준과 다른 지점(의도적):** PlayFab/GameLift는 **티켓**에 상태와 사유를 담고 클라가 티켓을 폴링한다.
우리는 매칭 진행을 출석부로 보므로 사유도 출석부에 싣는다. 그 결과 **매치 성공은 출석부가, 실패 사유도
출석부가** 답한다 — 한 곳에서 답이 나오는 것은 같고, 그 한 곳이 티켓이 아니라 출석부일 뿐이다.

> **티켓 축 전환과의 관계:** 클라가 티켓을 직접 보는 표준 구조로 옮기는 것은 별도 트랙이다
> (2026-08-14 `user-location-service` spec §2가 "안 함"으로 결정했고, 그 근거 중
> *"축을 바꿔도 표현할 게 늘지 않는다"* 는 이 슬라이스에서 **틀렸음이 드러났다** — 티켓 축은 종단
> 사유를 자연스럽게 표현한다). 이 슬라이스는 그 전환을 **막지 않는다**: 전환 시 사유의 출처만
> 출석부 → 티켓으로 바뀌고, 클라의 소비 지점(§7)은 그대로다.

## 5. 데이터 계약

### 사유 enum (백엔드 `@lop/server-core` + 클라 공통 개념)

```ts
export enum CancellationReason {
    User = 1,      // 유저가 취소함
    Timeout = 2,   // 큐 상한(ticket_ttl_seconds) 초과
}
```

**정수 값을 쓰는 이유:** 같은 와이어의 `Location`이 정수 enum이다. 한 응답 안에서 표현을 섞지 않는다.
(이름은 PlayFab 문자열 값에서 가져오되, 인코딩은 코드베이스 관례를 따른다.)

### 출석부 메모

`Location.None`일 때의 메모에 사유가 **선택적으로** 붙는다.

```jsonc
// 지금
{ "location": 0 }
// 바뀐 뒤 (사유를 아는 경우에만)
{ "location": 0, "cancellationReason": 2 }
```

클라 측 타입은 기존 짝(`MatchmakingLocationDetail`/`GameRoomLocationDetail`)에 맞춰 신설한다:

```csharp
[Serializable]
public class NoneLocationDetail : LocationDetail
{
    public CancellationReason cancellationReason;   // 0 = 사유 없음
}
```

`GetUserLocationResponse.Deserialize`에 `case Location.None:` 분기를 추가한다(지금은 `Matchmaking`과
`GameRoom` 두 분기뿐이라 `None`은 베이스 타입으로 남는다).

## 6. 백엔드 — 사유를 남기는 두 경로

### 6.1 공통 — 조건부 해제 API (lobby, 내부 전용)

두 경로가 같은 것을 필요로 한다: **"이 유저가 아직 이 티켓 때문에 매칭 중이면, 사유를 달아 로비로
돌려놔라."** 조건이 붙는 이유는 그 사이 유저가 **새 매칭을 시작했을 수 있기 때문**이다 — 조건 없이
쓰면 대기 중인 사람을 로비로 튕긴다(로드맵 🟠 "위치 일괄 정리가 무조건 쓰기"와 같은 종류의 사고).

```
PUT /internal/user/location/matchmaking-ended
body: { entries: [{ userId, ticketId, reason }] }
```

로비는 각 항목에 대해 **한 DB 연산**으로 조건부 갱신한다:

> `location == Matchmaking` **이고** `locationDetail.matchmakingTicketId == ticketId` 일 때만
> → `location = None`, `locationDetail = { location: None, cancellationReason: reason }`

조건이 안 맞으면 **아무것도 쓰지 않는다**(그 유저는 이미 다른 상태로 넘어갔다는 뜻).

**"한 연산"이 load-bearing이다.** 읽고 나서 판단하고 쓰면 그 틈에 새 매칭이 끼어 유저를 튕긴다.
로비에는 이미 같은 모양의 조건부 쓰기(`clearLocationIfUnchanged`, 자가치유가 씀)가 있으므로 그
확장으로 만든다. `locationDetail`이 jsonb라 Prisma 필터로 티켓 id 조건을 표현하기 어려우면
**raw SQL 한 문장**으로 내려간다 — 읽고-쓰기로 나누는 것만은 하지 않는다.

> 조건을 판본(`timestamp`)이 아니라 **티켓 id**로 거는 이유: 호출자(매칭서버)가 판본을 알려면 위치를
> 한 번 더 읽어야 한다. 티켓 id는 이미 손에 있고, "이 티켓 때문에 매칭 중이었나"가 우리가 실제로
> 묻고 싶은 조건 그 자체다.

### 6.2 취소 경로 (`MatchmakingService.cancelMatchmaking`)

지금 티켓 삭제 성공 후 출석부를 **무조건** `None`으로 덮는다. 이것을 6.1의 조건부 해제
(`reason = User`)로 **교체**한다.

부수 이득: 무조건 쓰기 하나가 조건부로 바뀌어, 위 🟠 위험이 이 경로에서 사라진다.

### 6.3 시간초과 경로 (Director 틱)

지금은 **티켓만 지우고 출석부는 건드리지 않는다** — 로비가 나중에 조회할 때 자가치유로 정리한다.
여기에 6.1 호출(`reason = Timeout`)을 **추가**한다. 이미 쓸어담은 티켓의 `id`와 `userIds`를 들고 있으므로
추가 조회가 없고, 한 틱의 쓸어담기 전체를 **한 번의 배치 호출**로 보낸다.

부수 이득: 지금은 시간초과된 유저가 *로비가 조회할 때까지* 대기 화면에 남아 있는데, 이 호출이
들어가면 **즉시 풀린다.**

실패해도 던지지 않는다 — **자가치유가 여전히 안전망**이다(사유 없이 로비로 돌아갈 뿐). 다만 조용히
넘어가면 원인을 못 찾으므로 로그는 반드시 남긴다.

### 6.4 건드리지 않는 것

- 티켓의 생애(생성·삭제 시점) — 그대로
- `MatchmakingTicketUser` 잠금 — 그대로
- 로비 자가치유(`healIfStale`/`isStale`) — 그대로. **안전망으로 남는다**

## 7. 클라 — 사유가 화면까지 오는 길

### 7.1 신호는 ViewModel이, 화면은 코디네이터가

아키텍처 규칙(작은 흐름=VM / 큰 흐름=코디네이터)에 따라, VM은 **도메인 신호만** 노출하고 팝업은
코디네이터가 띄운다. 대기 오버레이를 이미 `MatchmakingCoordinator`가 여닫으므로 주인이 같다.

```csharp
// MatchmakingViewModel
public Observable<CancellationReason> MatchmakingFailed { get; }
```

이름은 팝업(`MatchmakingFailedView`)과 짝을 맞춘다. 사유를 실어 보내므로, 나중에 사유가 늘어도
신호는 그대로 두고 코디네이터의 분기만 는다.

VM의 `OnStateChange(previous, current)`에서 **`previous is InMatchmaking && current is not InMatchmaking`**
일 때 현재 위치 메모의 사유를 읽어, `Timeout`이면 발행한다.

**순서는 결정적이다** — FSM이 `InMatchmaking`을 벗어나는 계기가 *위치 변화 구독*이므로, 상태가 바뀐
시점에는 `UserLocation.CurrentValue`가 이미 새 값(`None` + 사유)을 들고 있다.

### 7.2 세 경우가 자연히 갈린다

| 끝난 이유 | 사유 값 | 화면 |
|---|---|---|
| 시간초과 | `Timeout` | **"상대를 찾지 못했습니다" 팝업** |
| 유저 취소 | `User` | 없음 |
| 매치 성사 | (없음 — 위치가 `GameRoom`) | 없음 |

매치 성사를 따로 걸러낼 필요가 없다는 점이 이 배선의 이득이다.

### 7.3 팝업

```csharp
public class MatchmakingFailedView : UIPopup   // Popup 밴드 + 백드롭, AutoClose = true
```

`LoginView`(`UIPopup`)와 `MatchResultView`(코디네이터가 한 번 띄우고 닫음)의 선례를 따른다.
결과를 돌려줄 필요가 없으므로 `IResultView<T>`는 쓰지 않고 `OpenModalAsync`도 아니다 — 단순
`Open<T>` + [확인]으로 닫는다.

> 명명 주의: 기존 대기 오버레이가 `MatchingWaitingView`(옛 어휘)인데, 도메인 어휘는 **`Matchmaking`**이다
> (07-31 슬라이스 5에서 확정). 새 타입은 `Matchmaking*`을 쓰고, 기존 이름 정리는 이 슬라이스 범위 밖이다.

## 8. 사유가 유실되는 경우 (허용하는 열화)

| 상황 | 결과 | 판단 |
|---|---|---|
| Director의 6.1 호출이 실패 | 로비 자가치유가 나중에 사유 **없이** 정리 → 팝업 없음 | 지금과 같음(회귀 아님). 로그로 추적 |
| 유저가 로비를 아예 안 보는 사이 앱 종료 | 사유가 덮여 사라질 수 있음 | 다음 매칭에 영향 없음 |
| 위치 폴링을 연속 실패(`Faulted`) | FSM이 `Idle`로 안전 복귀, 팝업 없음 | 위치를 못 믿는 상태에서 실패라고 단정하지 않는다 |

**원칙: 사유가 없으면 아무 말도 하지 않는다.** 틀린 안내("상대를 찾지 못했습니다"인데 실은 서버 장애)를
띄우는 것이 침묵보다 나쁘다.

## 9. 테스트

| 층 | 무엇 |
|---|---|
| 백엔드 단위 | 조건부 해제 — 조건 일치 시 사유와 함께 비움 / **티켓 id가 다르면 아무것도 안 씀**(새 매칭 보호) / 위치가 이미 `None`이면 안 씀 |
| 백엔드 단위 | Director 틱 — 쓸어담은 티켓의 유저들이 `Timeout`으로 한 번에 전달됨 / 호출이 던져도 틱이 계속 돎 |
| 백엔드 단위 | 취소 — `User` 사유로 조건부 해제가 호출됨 |
| 백엔드 통합 | 상한 초과 → 출석부가 `None + Timeout`이 되는 것을 실제 DB로 |
| 클라 | **유닛 불가**(앱 코드가 `Assembly-CSharp`이라 asmdef 참조 불가). 컴파일 + 인게임으로 검증 |
| 인게임 | ① 상한을 짧게 조정해 시간초과 → 팝업 뜸 ② 취소 → 팝업 안 뜸 ③ 매치 성사 → 팝업 안 뜸 |

> 백엔드는 `pnpm build`가 테스트를 타입검사하지 않는다(`__tests__` exclude). 검증 명령 맨 앞에 빌드를 둘 것.
