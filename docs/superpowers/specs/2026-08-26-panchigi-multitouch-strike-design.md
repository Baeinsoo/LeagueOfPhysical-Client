# 판치기 — 손바닥 치기(멀티터치) 설계

> **한 문장**: 손가락 하나가 아니라 **손 전체**로 친다 — 손가락 수와 벌린 간격이 결과를 바꾼다.

## 1. 왜 지금 하나

슬라이스 3이 타격 입력을 옮길 때 **원본의 멀티터치를 조용히 떨어뜨렸다.**

원본 `InputController`(`workspace/panchigi/Assets/Scripts/InputController.cs`)는
`Dictionary<int, InputData>`로 **손가락마다(`fingerId`) 따로 추적**하고 `Input.touches`를 순회한다.
손가락을 뗄 때마다 그 손가락의 접촉점·드래그·누른 시간으로 `AddForce`를 부른다 — 즉
**4개로 치면 힘이 4번, 각자 자리에서** 들어간다.

슬라이스 3 spec은 "원본 조작을 유지한다 — 판 위 한 점을 누르고 끌고 뗀다"라고 적었는데,
그건 *손가락 하나의 제스처*만 옮긴 것이다. 여러 손가락을 동시에 추적하는 부분은 빠졌고,
구현은 `Pointer.current`(주 포인터 **하나**)로 굳었다.

**사용자 요구**: "컨트롤적인 측면만 보면 손가락 수와 간격이 결과를 바꾸면 좋겠어."
원본이 이미 그랬으므로 **되살리는 것**이지 새로 발명하는 것이 아니다.

## 2. 잠근 결정

### 2.1 한 번의 치기 = 손가락이 전부 떨어질 때까지

원본은 턴이 없어서 **손가락을 뗄 때마다 즉시** 힘을 줬다. 우리는 **한 턴에 한 번**이라
경계가 필요하다. **손가락이 전부 떨어진 순간**을 한 번의 치기로 본다.

- 실제 손바닥 치기와 가장 비슷하다 — 손가락이 미세하게 어긋나 떨어져도 한 방이다
- "한 턴 = 한 번의 치기"가 깨지지 않는다
- 대안이었던 "첫 손가락이 떨어지면"은 나머지 손가락이 잘려 나가고,
  "원본 그대로 손가락마다 즉시"는 한 턴에 4번 치는 셈이 되어 턴 개념과 충돌한다

### 2.2 손가락 수·간격이 결과를 바꾸는 방식 — 원본과 같다

**접촉점마다 독립된 힘을 계산해 합산한다.** 새 물리 모델을 만들지 않는다.

- **손가락 수** → 힘이 그만큼 여러 번 들어간다
- **간격** → 접촉점이 흩어지므로 영향 범위가 넓어진다. 모아 치면 한곳에 집중된다

서버 힘 커널(`PanchigiStrike`)은 **손대지 않는다.** 이미 "한 점 → 동전별 덮임·힘"을
계산하므로, 접촉점마다 돌려 더하면 끝이다.

### 2.3 마우스는 손가락 하나

PC/에디터에는 손가락이 하나뿐이다. 마우스 입력은 **접촉점 1개짜리 치기**로 보낸다 —
분기 없이 같은 경로를 탄다. (원본은 `#if UNITY_EDITOR / #elif UNITY_IOS||UNITY_ANDROID`로
갈랐고, 그 분기 때문에 데스크톱 빌드에서 입력이 통째로 죽었다. 그 실수를 되풀이하지 않는다.)

## 3. 와이어

접촉점을 **페이로드 타입**으로 뺀다. `@auto_generate`를 **붙이지 않는다** —
이 레포의 규칙상 그것이 곧 "MessageId를 받지 않는 payload"라는 뜻이고,
`EntitySnap`/`ProtoVector3`와 같은 취급이다. **기존 MessageId가 하나도 안 밀린다.**

```proto
// LeagueOfPhysical-Shared/Protos/PanchigiStrikeContact.proto
syntax = "proto3";
import "ProtoVector3.proto";

message PanchigiStrikeContact
{
    ProtoVector3 strike_point = 1;   // 판 위 월드 좌표
    ProtoVector3 drag_delta   = 2;   // 판 평면 변위 (y = 0)
    float        hold_time    = 3;   // 초. 클라가 이미 상한을 적용해 보낸다
}
```

```proto
// LeagueOfPhysical-Shared/Protos/PanchigiStrikeToS.proto  (기존 파일 교체)
syntax = "proto3";
import "PanchigiStrikeContact.proto";

// @auto_generate
message PanchigiStrikeToS
{
    // 신원은 연결에서 도출한다 — 클라가 적어 보내지 않는다.
    repeated PanchigiStrikeContact contacts = 1;
}
```

**호환성은 신경 쓰지 않는다** — 클·서가 같이 나가고 운영 중인 빌드가 없다.

## 4. 서버 — 검증과 적용

`PanchigiStrikeMessageHandler`는 지금 검증을 **한 점에 대해** 한다. 이제 **접촉점마다** 한다.

### 4.1 접촉점 개수 상한 (신규)

접촉점이 배열이 되면 **개수 자체가 새로운 공격면**이다. 지금 상한들(드래그 세기·누른 시간)은
전부 *접촉점 하나당* 걸리므로, 조작된 클라가 상한 안쪽 접촉점을 100개 보내면
힘이 100배가 된다. **마스터데이터에 `contact_max`를 둔다 — 값은 우선 4.**

값을 4로 두는 건 *지금의 선택*이지 물리적 한계가 아니다. 그래서 상수가 아니라 **컨피그**다 —
손가락을 더 허용하고 싶어지면 테이블 값만 바꾸면 되고, 코드는 상한을 값으로만 읽는다.

`TbPanchigiConfig`에 컬럼 추가:

| 컬럼 | 타입 | 값 | 뜻 |
|---|---|---|---|
| `contact_max` | int | 4 | 한 번의 치기가 가질 수 있는 접촉점 수 상한 |

### 4.2 거절 규칙 — 하나라도 어긋나면 치기 전체를 버린다

기존 규칙(판 밖 타격점 / 누른 시간 범위 / 세기 범위)은 **접촉점마다** 검사하되,
**하나라도 걸리면 치기 전체를 거절**한다. 일부만 버리고 나머지를 적용하면
조작된 값이 조용히 섞여 들어간다 — 슬라이스 3이 "클램프가 아니라 거절"로 잡은 것과 같은 이유.

추가 규칙:
- `contacts`가 **비어 있으면** 거절 (기록된 접촉점이 없는 치기는 성립하지 않는다)
- `contacts.Count > contact_max`면 거절

### 4.3 적용

```
foreach (접촉점) ApplyStrike(그 점, 그 드래그, 그 누른 시간)   // 커널 그대로, 힘이 누적된다
turnSystem.NotifyStruck(userId)                                // 치기 전체에 대해 한 번
```

**빈 탭 처리**: 지금은 `dragDelta == 0 && holdTime == 0`이면 스윕을 건너뛴다.
접촉점마다 그대로 유지한다 — 접촉점 하나가 빈 탭이어도 나머지는 힘을 준다.
**모든 접촉점이 빈 탭이어도 차례는 소모된다**(슬라이스 4의 판정 유지 —
그렇지 않으면 지연 전술이 된다).

## 5. 클라 — 손가락 추적

`PanchigiStrikeInput`이 `Pointer.current` 하나 대신 **손가락별로 추적**한다.
원본의 `Dictionary<int, InputData>`에 대응하되, LOP 규약대로 **New Input System**을 쓴다
(레거시 `Input.touches` 금지).

- `Touchscreen.current.touches`를 순회하며 `touchId`별로 상태를 든다.
  터치스크린이 없으면 `Mouse.current`를 **손가락 하나**로 취급한다.
- 손가락이 처음 닿을 때: 판에 레이캐스트해 접촉점을 잡는다. **판을 못 맞히면 그 손가락은 무시한다**
  (지금 `BeginAim`이 판 밖을 무시하는 것과 같다). 무시된 손가락은 **자리도 먹지 않는다**(§5.2).
- 손가락이 움직이는 동안: 그 손가락의 현재 점을 갱신한다.
- 손가락이 떨어질 때: **그 손가락의 결과를 확정해 보관**하고, 아직 눌린 손가락이 남아 있으면 기다린다.
- **눌린 손가락이 0이 되는 순간**: 보관한 접촉점들을 한 메시지로 보내고 비운다.

### 5.1 조준 UI — 손가락마다 보여준다

지금은 선 하나(`LineRenderer` 1개)다. **누르고 있는 손가락마다 자기 조준선을 그린다** —
어느 손가락이 어디를 얼마나 끌고 있는지가 각각 보여야 한다.

- 손가락마다 **별도 `LineRenderer`** 를 쓴다. 한 `LineRenderer`의 세그먼트를 나눠 쓰면
  선들이 이어져 보여서 안 된다.
- `LineRenderer`는 **`contact_max`개를 미리 만들어 두고 재사용**한다(풀). 치기마다
  생성·파괴하면 GC가 돈다.
- 손가락이 떨어지면 그 선은 **즉시 숨긴다** — 아직 눌린 손가락이 남아 있어도 마찬가지다.
  떨어진 손가락의 결과는 보관되지만, 화면에 남아 있으면 아직 조준 중인 것으로 읽힌다.
- 차례가 넘어가면 **전부 숨긴다**(§5.3).

### 5.2 상한을 넘겨 짚으면 — 먼저 닿은 순서로 `contact_max`개

**클라가 먼저 자른다.** 서버의 "초과면 거절"(§4.2)은 조작된 클라를 막는 방어선이지,
정상 플레이가 거기 걸리면 안 된다 — 5개로 친 플레이어가 아무 일도 안 일어난 채
차례만 날리고 이유도 모르게 된다.

기준은 **먼저 닿은 순서**다. 상한을 넘긴 손가락은 접수하지 않고, **조준선도 안 그린다.**

```
1번째 손가락 닿음 → 접수 (조준선 1)
...
4번째           → 접수 (조준선 4)
5번째           → 무시 (조준선 없음)
```

*왜 "먼저 닿은 순서"인가*: 닿는 **그 순간 결정**되므로 조준선이 즉시 답을 보여준다 —
플레이어는 선이 안 그려지는 것으로 "이 손가락은 안 센다"를 눈으로 안다.
"가장 세게 친 4개" 같은 기준은 뗄 때까지 알 수 없어 조준 중에 보여줄 수가 없다.

**손가락을 떼도 자리는 나지 않는다.** `contact_max`는 *동시에 눌린 손가락 수*가 아니라
**한 번의 치기가 모으는 접촉점 총 개수**다. 접수된 손가락을 떼면 그 접촉점은 보관되므로
자리가 비지 않고, 앞서 무시된 손가락이 승격되지도 않는다. 승격시키면 조준 중에
없던 선이 갑자기 생기고 "먼저 온 순서"라는 규칙 자체가 흔들린다.

### 5.3 차례가 아니면

지금과 같다 — 내 차례가 아니면 추적을 시작하지 않고, 조준 중에 차례가 넘어가면 전부 버린다.

## 6. 검증

`PanchigiVerification`(에디터 메뉴 `LOP/판치기 검증`)에 다음을 더한다:

- 접촉점 2개짜리 치기가 **각각의 힘을 합산**한다 (같은 점 2개 = 한 점 2배)
- 접촉점을 **벌리면** 영향 범위가 넓어진다 (멀리 있는 동전이 더 밀린다)
- `contacts`가 비면 거절
- `contacts.Count > contact_max`면 거절
- 접촉점 **하나만** 규칙을 어겨도 치기 **전체**가 거절된다
- 클라가 `contact_max`개까지만 접수한다 — 넘긴 손가락은 접촉점에도 조준선에도 안 들어간다
- 접수된 손가락을 떼도 자리가 나지 않는다 (앞서 무시된 손가락이 승격되지 않는다)
- 판을 못 맞힌 손가락은 자리를 먹지 않는다

실플레이 검증은 **터치 기기가 필요하다** — 에디터·PC는 손가락이 하나뿐이라
멀티터치 경로를 탈 수 없다. 단일 접촉점 회귀(마우스로 치던 게 그대로 되는지)만
PC에서 확인하고, 손가락 수·간격 효과는 **실기기 빌드**에서 본다
(`client-app-deploy` → QR). ⚠️ `-development` 빼면 평문 http가 막혀 전부 실패한다.

## 7. 범위 밖

- **손 모양 모델링**(손바닥 타원, 손가락 사이 압력 분포) — 접촉점 합산으로 충분한지 먼저 본다
- **동전 앞뒤 아트** — 별개 항목(지금 임시 실린더라 사람이 판을 못 읽는다)
- **전용 맵** — 판이 10m×10m라 대형(2.1m)에 비해 지나치게 넓다. 별개 슬라이스
