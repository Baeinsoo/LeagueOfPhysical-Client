# 키네마틱 이동 — 지면을 따라 움직이게 (경사 떨림 제거)

> 한 줄: 수평으로 밀 때 **검사하는 몸과 실제로 옮기는 몸이 달라서** 새가 오르막에 매 틱
> 파묻히고, 그 복구 반응이 떨림으로 보인다. 검사와 이동을 같은 자리에서 하고, 지면 위에 있을 땐
> 수평이 아니라 **지면 경사를 따라** 밀어 준다.

## 1. 무엇이 문제인가 (실측)

새 한 마리가 경사면을 스칠 때 매 틱 값이 두 상태를 오간다. 네트워크와 무관하고(클·서 동일),
다른 새도 필요 없다. EditMode에서 32° 경사 하나만 두고 재현했다:

```
t46  vel(6.65, +4.16)  dy 0.166
t47  vel(7.91, +2.76)  dy 0.091
t48  vel(6.13, +5.33)  dy 0.143
t49  vel(7.91, +3.93)  dy 0.101      ... 계속
```

**2틱 주기 = 25Hz.** 라이브에서도 같은 자리(x≈132.7, 32° 경사)에서 클·서가 똑같이 떨었다.

## 2. 원인

`KinematicMover.Move`의 수평 스텝은 캡슐을 `StepOffset`(0.1m) **들어올려 검사**하고,
**실제 위치는 안 올린 채** 옮긴다.

```csharp
CollisionHit hit = Cast(pos, StepOffset, dir, dist + SkinWidth, input, query);  // 0.1 올려서 검사
...
pos += dir * moveDist;                                                          // 안 올린 채 이동
```

평지에선 차이가 없지만 오르막에선 지면이 그 10cm 틈으로 들어온다:

```
수평 0.2m 전진 → 지면 0.2 × tan32° = 0.125m 상승
0.125 − 0.1 = 0.025m 파묻힘        (실측 0.027m)
```

파묻히면 다음 틱에 `FlappyWorld`의 `Depenetrate` + `ClearVelocityIntoSurface`가 발동해,
전진 속도 11m/s에서 경사로 파고드는 성분을 지운다. 그 결과 **세로 속도가 +4.16으로 튄다**:

```
(11, −2.8) 에서 법선 (−0.53, 0.848) 성분 제거 → (6.65, +4.16)     // 실측 t46과 일치
```

즉 **같은 일("표면으로 파고드는 속도 제거")을 하는 코드가 둘인데 답이 다르고**, 새가 매 틱
"파묻힘 / 안 파묻힘"을 오가며 두 코드를 번갈아 탄다. 그래서 떤다.

`FlappyMoveSystem`이 매 틱 `velocity.x = ForwardSpeed`로 다시 못 박으므로 이 에너지는
영원히 재주입된다 — 저절로 잦아들지 않는다.

## 3. 왜 들어올렸었나 (없애면 안 되는 이유)

`StepOffset`을 그냥 0으로 두면 원래 문제가 돌아온다. 발밑 바닥에 **딱 붙어 있는** 상태에서
수평 sweep을 쏘면 거리 0으로 맞고, `moveDist = max(0 − SkinWidth, 0) = 0`이라 한 발도 못 간다.
남은 이동을 바닥 평면에 투영해도 이미 수평이라 그대로여서, 반복해도 진전이 없다 — **제자리에 낀다.**

그래서 이 설계는 들어올리기를 *지우기만* 하지 않고, **바닥에서 살짝 띄운 상태를 유지**하는
표준 처리를 함께 넣는다.

## 4. 바꿀 것

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 순서 | 수평 → 수직 | **지면 찾기 → 지면 따라 수평 → 수직** |
| 수평 sweep 기준 | 0.1m 올린 캡슐 | **실제 몸 그대로** |
| 지면 위 이동 | 수평으로 밀고 부딪히면 미끄러짐 | **지면 평면에 투영해 경사를 따라** 이동 |
| 바닥과의 간격 | 붙어 있을 수 있음(밀어내기 직후) | **항상 `SkinWidth`만큼 띄움** |
| 턱 오르기 | 모든 이동에 0.1m 공짜 | **막혔을 때만** 위-앞-아래 3-sweep 시도 |
| 턱 높이 | 커널 상수 | **입력 파라미터** — Flappy=0, FlapWang=0.1 |

### 4.1 새 알고리즘

```
Move(input, query):
  pos = input.position

  # (0) 지면 찾기 — 무상태. 매 틱 발밑을 짧게 쓸어 본다.
  groundNormal = none
  hit = Cast(pos, lift: SkinWidth, dir: down, dist: SkinWidth + GroundProbe)   # GroundProbe = 0.05
  if hit and hit.Normal.y >= GroundNormalY:
      groundNormal = hit.Normal
      pos.y += 2*SkinWidth - hit.Distance     # 바닥에서 정확히 SkinWidth 띄운다

  # (1) 수평 — 지면 위면 경사를 따라. 단 수평 진행은 깎지 않는다.
  move = (vx, 0, vz) * dt
  if groundNormal:
      move.y = -(move.x*n.x + move.z*n.z) / n.y    # 수평은 그대로, 세로만 램프에 얹는다
  collide-and-slide(pos, move, lift: 0)      # 실제 몸 자리에서 검사
      막혔는데 그 면이 걸을 수 없고(stepOffset > 0)이면 → 턱 오르기 시도

  # (2) 수직 — 지금과 같음 (중력/점프)
```

> **`ProjectOnPlane`을 쓰지 않는 이유** (초안에서 틀렸던 곳이다): 이동 벡터를 지면 평면에
> 그냥 투영하면 **수평 성분이 cos²θ만큼 줄어든다.** 32° 경사에서 전진이 11 → 7.91 m/s가 되고,
> 오르막뿐 아니라 **내리막도 평지보다 28% 느려진다**(실측: 내리막 40틱에 옛 코드 x=7.80 →
> 단순 투영 x=5.39). 전진 속도가 상수인 레이스 게임에서 언덕만 감속 구간이 되는 건 규칙 위반이고,
> 내리막이 평지보다 느린 건 말이 안 된다. 게다가 반환 속도는 안 깎이므로 *보고하는 속도와 실제
> 변위가 어긋나* 외삽을 켜는 순간 경사에서 과예측이 된다.
> 수평 성분을 보존하고 세로만 얹으면 이동 벡터는 여전히 지면과 평행이라(`d·n = 0`) 파묻힘이 없고,
> 반환 속도가 실제 진행과 일치한다 — **단 수평 성분에 한해서다.** 세로는 D5대로 여전히 0을
> 보고하는데 몸은 `vx·tanθ`로 오른다(32°·11m/s면 6.87m/s). 지금은 두 게임 다 외삽 대상이 없어
> (Flappy·FlapWang 모두 예측 또는 보간) 아무 데도 안 터지지만, **외삽 정책을 되살리는 날
> 이 어긋남이 세로축에서 되살아난다.**

> **계수가 2인 이유** (한 번 틀렸던 곳이다): 탐침은 발밑이 아니라 `pos + up*SkinWidth`에서 쏜다.
> 그래서 `hit.Distance = (pos.y + SkinWidth) − 지면y` 이고, 목표는 `새pos.y − 지면y = SkinWidth`다.
> 둘을 연립하면 `새pos.y = pos.y + 2·SkinWidth − hit.Distance`. 계수를 1로 두면 몸이 지면에
> **딱 붙어(간격 0)** 버려서, 이 단계가 막으려던 바로 그 상황(붙은 채로 수평 sweep → 거리 0 →
> 한 발도 못 감)이 그대로 남는다.

### 4.2 잠긴 결정

- **D1 — 검사와 이동은 같은 자리에서.** 통짜 들어올리기 제거. 이 문서가 고치는 버그의 뿌리다.
- **D2 — 걸을 수 있는 면(`normal.y ≥ 0.7`) 위에서만 투영한다.** 그보다 급한 면은 지면이 아니라
  벽이므로 예전처럼 미끄러진다.
- **D3 — 접지 판정은 매 틱 다시 잰다(무상태).** 이전 틱 결과를 들고 있지 않는다 —
  롤백 재생에서 라이브와 같은 답이 나와야 한다.
- **D4 — 턱 높이는 입력 파라미터.** 나는 새에게 계단 오르기는 의미가 없다(Flappy는 0을 넘긴다).
  FlapWang만 0.1을 쓰고, 그때도 *막혔을 때만* 시도한다.
- **D5 — 경사를 올라도 세로 속도는 늘리지 않는다.** 지금 커널이 그렇게 동작하고
  (`horizVel.y`를 버린다) 그 감각으로 플레이해 왔다. 램프에서 튀어오르는 변화는 이 슬라이스가
  가져오지 않는다. 경사는 *위치*를 안내할 뿐이고 세로 속도는 중력·플랩이 소유한다.
- **D6 — 상수는 그대로.** `SkinWidth 0.02`, `GroundNormalY 0.7`, `MaxSlides 4`.
  새로 도입하는 건 `GroundProbe = 0.05`(발밑을 얼마나 아래까지 훑을지) 하나뿐이다. 이 값은
  "한 틱 낙하분(중력 70 × 0.02² ≈ 0.028)보다 넉넉히 크되, 공중에 뜬 새를 지면으로 오인하지 않을
  만큼 짧게"로 잡았다. 라이브에서 접지가 깜빡이면 먼저 조정할 값이다.

## 5. 산업 표준 매핑

- **언리얼 CMC** — `FindFloor`로 매 틱 바닥을 찾고, `AdjustFloorHeight`로 캡슐을 바닥에서
  일정 간격 띄워 유지하며, `ComputeGroundMovementDelta`로 이동을 램프에 맞춰 얹는다.
  통짜 들어올리기가 아니라 `StepUp`을 *막혔을 때만* 부른다.
  **주의 — 초안이 이 항목을 잘못 인용했다**: CMC의 기본값(`bMaintainHorizontalGroundVelocity = true`)은
  램프에서 **수평 속도를 보존**한다. 초안은 같은 함수를 근거로 들면서 정작 수평을 깎는
  단순 투영을 지시했다. §4.1이 그에 맞춰 정정됐다.
- **Photon Quantum KCC** — 접지 법선을 구해 이동을 그 평면에 투영(ground projection).
- 즉 이 설계는 새 발명이 아니라 **표준 컨트롤러 구조로 되돌리는 것**이다.

## 6. 범위 밖 (의도적)

- **새끼리 얹혀서 떠는 것** — 원인이 다르다(접촉 임펄스를 절반만 반영하는데, 아래 새는 땅에
  받쳐져 자기 몫을 못 쓴다 → 수렴 속도 2.07m/s가 `RestingSpeed 1.5`보다 항상 커서 안 멎는다).
  `ROADMAP.md`의 **접촉 반복 해석기** 몫이다. 한 슬라이스에 묶으면 문제가 생겼을 때 어느 쪽
  탓인지 못 가린다.
- **맵의 막다른 쐐기**(x≈132.75에서 통로가 16.65m → 1.15m → 막힘). 아트/레벨 쪽 수정이다.
  새는 후진을 못 하므로 *들어갈 수 있는데 나올 수 없는 자리*는 만들면 안 된다.

## 7. 위험

- **`KinematicMover`는 Flappy와 FlapWang이 함께 쓴다.** 두 게임의 이동이 같이 바뀐다.
  FlapWang은 계단·턱이 있어 D4(막혔을 때만 턱 오르기)가 체감으로 확인돼야 한다.
- **밀어내기와의 상호작용**: 지금은 `Depenetrate`가 바닥에 *딱 붙게* 밀어낸다. (0)단계가 매 틱
  `SkinWidth`를 되찾아 주므로 붙은 채로 수평 sweep을 쏘는 일이 없어진다.
- **`ClearVelocityIntoSurface`는 이 슬라이스에서 건드리지 않는다.** 파묻힘이 사라지면 거의
  발동하지 않게 된다. 다만 발동할 때의 규칙(경사에서 +세로 속도를 주입)이 D5와 어긋나므로
  아래 열린 항목으로 남긴다.

## 8. 어떻게 확인하나

EditMode(LOP-Shared). 반평면(바닥/벽/경사)을 주는 해석 쿼리로 커널을 직접 돌린다 —
이 방식으로 이미 버그를 재현했다.

**고치기 전에 빨간불을 봐야 하는 것** (실측으로 이미 확인한 두 가지):

| 테스트 | 지금 코드 |
|---|---|
| 경사를 오른 뒤 몸이 표면 밖에 있다 | ❌ 2.7cm 파묻힘 (실측) |
| 경사를 오르는 동안 세로 속도가 매 틱 교대하지 않는다 | ❌ 4.16 / 2.76 왕복 (실측) |

**깨지면 안 되는 것** (지금도 통과 — 회귀 방지용):

| 테스트 | 왜 필요한가 |
|---|---|
| 평지에서 전진한다 | 들어올리기를 없애는 변경이라 캐칭이 되살아날 수 있다 |
| 바닥에 딱 붙은(간격 0) 상태에서도 전진한다 | 지금은 들어올리기가 가려 주던 경우. 새 코드는 (0)단계 간격 확보로 막는다 |
| 수직 벽에 막힌다 | 미끄러짐 자체를 깨지 않았는지 |
| 공중에서 경사면에 부딪히면 미끄러진다 | 접지가 아닐 때의 경로 |

**새로 생기는 동작** (오늘은 테스트 자체를 쓸 수 없다 — 파라미터가 없다):

| 테스트 |
|---|
| `stepOffset = 0.1`이면 0.1m 턱을 오른다 |
| `stepOffset = 0`이면 0.1m 턱을 못 오른다 (Flappy) |

> **내리막 거동은 목록에서 뺐다.** 지금 코드가 계단식으로 내려가는지 재 보지 않았다 —
> 재지 않은 것을 "고쳐진다"고 적으면 안 된다. 구현 중에 측정해서 그때 추가한다.

라이브 확인(사람): 경사 구간에서 새가 떨지 않는지, FlapWang에서 턱·계단 오르내림이
예전과 같은지.

## 9. 열린 결정

- **O1 — `ClearVelocityIntoSurface`의 세로 속도 주입.** 드물게만 발동하게 되지만 커널의
  D5("경사는 세로 속도를 안 늘린다")와 규칙이 다르다. 통일할지, 통일한다면 어느 쪽으로 할지는
  이 슬라이스가 끝나 발동 빈도를 본 뒤 정한다.
- **O2 — 접촉 반복 해석기**(새끼리 얹힘). `ROADMAP.md` 항목 그대로.
- **O4 — 지면 탐침에 "걷는 중인가" 게이트가 없다 (Flappy 부작용).** 탐침은 `_hitTracker`를 지나는
  진짜 sweep이라, Flappy에서는 커널이 *지면을 찾으려고* 쏜 캐스트가 **"맵에 부딪혔다"로 읽혀 스턴을
  건다**(`FlappyWorld`가 `SawHit`으로 `Enter`를 부른다). 사거리는 발밑 5cm. 또 스냅이 몸을 최대 2cm
  **아래로** 당길 수 있다(언리얼 `AdjustFloorHeight`의 ground stickiness — CMC는 `bMovingOnGround`일
  때만 한다). 걷는 게임엔 정확히 맞고 **나는 게임엔 "안 닿아도 지면"이 5cm 생기는** 자리다.
  노출 구간은 좁다 — `vy ∈ (-1.4, 0]`, 즉 플랩 포물선의 꼭짓점 한 틱뿐이다.
  **라이브에서 먼저 본다**(지면을 스치며 플랩할 때 안 닿았는데 스턴이 걸리는지). 실제로 거슬리면
  처방은 (a) 커널이 탐침 캐스트를 구분해 알려주기 (b) Flappy만 `GroundProbe = 0`.
- **O5 — 천장 쪽 거울상.** 스냅은 위로 최대 4cm 올리면서 **위쪽 sweep을 하지 않는다.** 몸 높이 + 4cm
  이내 통로에서는 "위로 스냅 → 머리 파묻힘 → 다음 틱 밀어내기가 내림"이 반복돼 25Hz 위치 진동이
  날 수 있다. 단 **속도 킥은 없다**(그때 outward가 아래라 `ClearVelocityIntoSurface`가 위 방향
  속도만 지운다 → D5 유지). 진폭 ≤ 4cm이고 그 정도 통로면 이미 끼어 스턴 상태다. 좁은 파이프
  구간을 라이브로 볼 때 같이 확인한다.
- **O3 — `TryStepUp`에 접지 조건이 없다.** 언리얼 CMC는 `StepUp`을 접지 이동(`MoveAlongFloor`)에서만
  부르는데, 여기선 공중에서 벽을 스쳐도 최대 `stepOffset`만큼 턱 위로 올라탄다(FlapWang에서
  점프·낙하 중 선반에 달라붙는 무료 등반). **이번 슬라이스에서 고치지 않았다** — 옛 코드도 모든
  수평 sweep을 통짜로 들어올려 공중에서 같은 높이를 무시했으므로 *새로 생긴 문제가 아니고*,
  공중 이동을 바꾸는 것은 경사 떨림의 범위 밖이다. 라이브에서 실제로 거슬리면 그때 `&& onGround`
  한 줄로 표준에 맞춘다.

## 10. 확인 결과 (2026-08-28 라이브)

### 떨림 — 해결됨 (실측)

원래 떨던 자리(x ≈ 132.77, 32° 경사 위)에서:

| | 수정 전 | 수정 후 |
|---|---|---|
| 화면상 새 위치 | 두 자리를 **5~8cm** 오감 | 12번 샘플 **소수점 4자리까지 동일** |
| 클라 vs 서버 | 위상이 갈려 0.028씩 어긋남 | **소수점 4자리까지 일치** |
| `[ReconSpike]` | 70틱 주기로 쏟아짐 | **0건** |

경사를 타고 지나가는 구간도 **매끄럽다**(사용자 육안). 이 슬라이스의 목적은 달성됐다.

### 라이브에서 새로 드러난 것 — 둘 다 이 슬라이스 소관 아님

**(가) 맵의 막다른 쐐기가 이제 진짜로 가둔다.** x=132.77에서 새 몸이 놓일 수 있는 세로 여유가
**10cm**이고 그 위 **2.22m가 통째로 바위**다. 앞은 x=133.00에서 닫히고, 전진 속도가 상수라
후진도 못 한다 — **기하학적으로 탈출 불가**다.

맵은 이 브랜치가 한 줄도 안 건드렸으니 함정 자체는 원래 있었다. 다만 **예전엔 빠져나왔을
개연성이 높다 — 그리고 그건 버그 덕분이었을 것이다**: 옛 커널은 몸을 지오메트리 안에 파묻었고
(파묻힌 캡슐은 sweep이 못 본다 = 벽을 뚫는 메커니즘 그 자체) `ClearVelocityIntoSurface`가 매 틱
위로 +4.16m/s를 꽂았다. 즉 **고치면서 우연한 탈출구가 막혀 원래 있던 함정이 드러났다**(추론 —
옛 커널로 같은 자리를 재현해 보면 확정된다).

→ 어제 "아트 쪽 별건"으로 미뤄 둔 판단을 **우선순위 올림**. 고칠 방향은 ① 맵에서 "들어갈 수
있는데 나올 수 없는 자리"를 없애거나 ② 갇힘/낙사 감지 후 리스폰 규칙을 만드는 것(현재 이 게임엔
그런 규칙이 아예 없다 — 맵 아래로 빠지면 무한 추락하는 것도 같은 이유).

**(나) 남의 새 날갯짓이 물리적으로 불가능한 속도로 보인다.** 직전 슬라이스(남의 새를 시뮬로
굴리기)의 알려진 대가가 라이브에서 확인된 것이다. 남의 입력은 클라에 오지 않아 "안 눌렀다"로
가정하고 굴리는데, 클라가 9틱(0.18초) 앞서므로 남이 한 번 날갯짓하면 오차가 4.1~9.5m 쌓인다.
그걸 시간상수 0.1초로 녹이므로 화면상 상승 속도가:

```
평지에서 날갯짓   → 4.14 / 0.1 = 41 m/s   (진짜 날갯짓 23의 1.8배)
떨어지다 날갯짓   → 9.54 / 0.1 = 95 m/s   (4배)
```

충돌 시 한 번씩 "팍 튀는" 것도 같은 뿌리일 수 있으나(충돌은 남의 궤적을 잘못 짚기 가장 쉬운
지점 + 컷오프가 없어 클수록 빨리 튐), 스턴 권위 불일치로 인한 되돌리기일 수도 있다.
**보정량을 로그로 찍어 갈라야 한다 — 짐작으로 고치지 않는다.**

→ **별개 슬라이스.** 유력한 처방은 "보정 속도에 상한을 두어 화면상 이동이 진짜 날갯짓(23m/s)보다
빨라지지 않게" — 원인은 두고 증상만 정확히 없앤다. 시간상수 튜닝(0.1→0.2~0.3)은 임시방편이고,
남의 입력 중계는 오차를 9틱→약 4.5틱으로 줄이지만 와이어 신설이 필요하다.

### 아직 안 본 것

- **FlapWang 턱·계단·문턱** (`stepOffset = 0.1`). 폭발 반경이 가장 크다 — 고치려던 게임이 아닌데
  같은 커널을 쓰고, 이동 방식이 근본적으로 바뀌었다(모든 sweep에 0.1 공짜 → 막혔을 때만 3-sweep).
  이 경로를 지키는 건 합성 스텁 `StepQuery` 하나뿐이다.
- **O4** — 지면을 스치며 플랩할 때 맵에 안 닿았는데 스턴이 걸리는지.
- **O5** — 가장 좁은 파이프 구간에서 머리 쪽 미세 진동.
- **O1** — 새 두 마리가 경사에서 부딪힐 때 위로 툭 튀는지(`ClearVelocityIntoSurface`가 살아 있는
  유일한 경로라 둘이 부딪혀야만 관찰된다).
