# 남의 새가 어색한 것 — 렌더 보정 재설계

## 1. 증상

라이브에서 셋이 보고됐다.

1. **남의 새 날갯짓이 진짜보다 훨씬 빠르게 보인다.**
2. **부딪힐 때 내 새가 팍 튄다.**
3. 클·서의 충돌 위치가 다른 것 같다.

## 2. 측정 — 추측 대신 숫자로

결정론 시뮬로 재현했다(네트워크 없음 = 상한 조건). 새 두 마리를 나란히 세우고 서로 다른 주기로
날갯짓시켜 주기적으로 몸싸움이 나게 한 뒤, 매 틱 T마다 **T−9의 상태에서 9틱을 재생**하되
남의 입력만 "안 눌렀다"로 두고 진실과 비교했다(리드 9틱은 라이브 실측 `snapAge`).

프로브: `LeagueOfPhysical-Shared/Tests/EditMode/FlappyRemoteSyncProbe.cs` (진단용 임시).

**남의 새 위치 오차**

| 창 | 표본 | 평균 | 최대 |
|---|---|---|---|
| 조용 (남이 안 누른 창) | 312 | **0.000 m** | 0.000 m |
| 날갯짓 (남이 누른 창) | 279 | **2.116 m** | **4.788 m** |

**내 새 위치 오차 — 내 입력은 정확히 아는데도**

| 창 | 표본 | 평균 | 최대 |
|---|---|---|---|
| 조용 | 312 | **0.000 m** | 0.000 m |
| 날갯짓 | 279 | 0.508 m | **2.776 m** |

**충돌 유무 오판**: 591창 중 **101창(17%)** 에서 클라 예측과 진실이 "부딪혔나"에 대해 갈렸다.

## 3. 원인

**조용한 창의 오차가 정확히 0**이라는 것이 열쇠다. 클·서가 같은 구체 코드를 돌리므로 남이 아무것도
안 누른 구간에서는 한 치도 안 어긋난다. 즉 **시뮬은 멀쩡하다.**

오차는 전부 하나에서 온다 — **클라는 남이 그 9틱 동안 무엇을 눌렀는지 알 수 없어 "안 눌렀다"로
가정한다.** 남이 실제로 날갯짓하면 그 가정이 틀리고, `FlapImpulse = 23 m/s`만큼의 세로 속도가
9틱 동안 적분돼 최대 4.8m가 벌어진다.

그리고 **그 틀린 몸이 내 몸을 민다.** 새끼리 몸싸움(`FlappyBodyCollisionSystem`)은 클·서 모두
같은 알고리즘으로 돌지만(모든 새가 `Simulated`이라 `_birds == _bodies`), 입력이 틀리면 부딪히는
순간의 상태가 달라진다. 그래서 내 입력을 정확히 아는데도 내 새가 최대 2.8m 틀리고, 17%의 창에서는
충돌 유무 자체가 갈린다.

**증상 3(충돌 위치가 다르다)의 정체가 이것이다** — 충돌 판정 코드가 다른 게 아니라, 판정에
들어가는 위치가 다르다.

### 이 구조는 의도된 것이고, 유지한다

직전 슬라이스(`2026-08-27-flappy-remote-simulation-design.md`)가 남의 새를 외삽에서 시뮬로
바꾼 것은 측정 근거가 있었다(외삽은 `MaxFallSpeed`를 모르고 맵을 뚫는다). 이번 측정도 그 결정을
뒤집지 않는다 — **남의 입력을 모르는 것은 어떤 방식으로도 못 고친다.**

로켓 리그도 같은 선택을 하고 같은 대가를 적어 두었다(GDC 2018, Jared Cone):

```
Rocket League Networking
  · Server buffers player inputs
  · Client predicts everything          ← 채택안

Predict Everything
  · Works well with ball (predictable)
  · Not as well with cars (unpredictable)   ← 우리와 같은 한계
  · Expensive corrections
```

보정 방식도 우리 `Reconciler`와 같은 모양이다: *"Revert all physics actors to that frame in
history / Run multiple physics frames to catch up."*

**그래서 이 슬라이스는 시뮬을 건드리지 않는다.** 고치는 것은 **그 대가를 화면이 어떻게 흡수하는가**
하나다.

## 4. 지금 화면이 하는 일과, 왜 어색한가

`RenderCorrectionSmoother`는 이렇게 그린다:

```
보이는 위치 = 시뮬 위치 + 오차오프셋
오차오프셋 = (보정 직전에 보이던 자리 − 새 권위 자리),  시간상수 0.1초로 지수 감쇠
```

이것은 **언리얼의 `NetworkSmoothingMode.Exponential`과 같은 방식**이다. 문제는 갭이 클 때
**시작 순간의 속도**다:

```
보이는 속도(t=0) = 시뮬 속도 + 갭 / 시간상수
                 = 시뮬 속도 + 4.788 / 0.1
                 = 시뮬 속도 + 47.9 m/s
```

진짜 날갯짓이 23 m/s인데 그 위에 47.9가 얹힌다. **"2~4배 빨라 보인다"의 정체가 이 항이다.**
지수 감쇠는 갭에 비례해 시작 속도가 커지므로, 갭이 큰 게임일수록 나빠진다. 사람 캐릭터는 한 틱에
이만큼 튀지 않아 언리얼에서는 문제가 안 되지만, 우리 새는 튄다.

## 5. 결정

**언리얼 표준의 뼈대를 그대로 가져오되, 보간 계산 한 군데만 다른 표준 기법으로 대체한다.**

### 5.1 내 새 — 스무딩을 없앤다

에픽 공식 문서:

> "Network smoothing is applied **only to simulated proxies**, not to the autonomous proxy."
> 오토노머스 프록시는 보정을 받으면 저장된 이동을 재생해 새 위치를 구할 뿐이고, 그 과정에 메시
> 스무딩이 없다.

**이유**: 내가 조종 중이라, 녹이는 동안 내 입력과 화면 속 내 몸이 어긋난다. 부드러움을 조작감으로
사는 셈인데, 내 몸에서는 그 값이 비싸다.

지금 우리는 내 새를 `LocalTeleport = 3m`까지 녹이고 있다. **측정된 내 새 오차 최대 2.8m는 그
아래라 전부 녹고 있었다** — 몸싸움마다 0.1초씩 조작이 미끄러졌다. 이것을 제거한다.

### 5.2 남의 새 — 언리얼 3문턱 구조

| 언리얼 | 하는 일 |
|---|---|
| (문턱 아래) | 즉시 채택 — 우리 `MinCorrection` |
| `NetworkSimulatedSmoothLocationTime` | 보간에 걸리는 시간 |
| `NetworkMaxSmoothUpdateDistance` | 보간 도중 화면이 서버에서 이 이상 뒤처지지 않게 붙잡는다 |
| `NetworkNoSmoothUpdateDistance` | 이보다 멀면 보간 없이 즉시 이동 |

지금 우리에겐 뒤의 둘이 없다(`RemoteTeleport = ∞`). 그래서 리스폰·큰 랙에서 새가 맵을 가로질러
미끄러진다. 셋 다 넣고 **이름도 언리얼을 따른다**.

> ∞가 된 사연: 예전 컷오프가 3m였는데 남의 날갯짓은 정상적으로도 그것을 넘어, 날갯짓마다
> 순간이동으로 보였다. **진단은 맞았고 처방이 과했다** — 답은 ∞가 아니라 제대로 된 크기의 문턱이다.

### 5.3 보간 계산 — 언리얼과 다르게 간다

지수 감쇠 대신 **속도까지 맞추는 보간**을 쓴다. 목표는 Murphy의 projective velocity blending과
같다(*Believable Dead Reckoning for Networked Games*, Game Engine Gems 2) — **이음매에서 속도가
끊기지 않게** 하는 것. 그 목표를 정확히 만족시키는 표준 구성은 **오차에 대한 3차 에르미트 보간**이다.

보정이 도착한 순간(t=0)에 두 가지를 안다:

```
P0 = 보정 직전에 화면에 그려지던 위치
V0 = 그때 화면이 움직이던 속도        (직전 두 렌더 위치의 차 ÷ dt)
```

그리고 시뮬은 매 프레임 자기 위치 `S(t)`와 속도 `Vs(t)`를 준다. 화면은 시뮬에 **오차 E(t)** 를
얹어 그린다:

```
보이는 위치 = S(t) + E(t)
```

E가 만족해야 할 것 넷:

```
E(0)  = P0 − S(0)      ← 이음매에서 위치가 안 튄다
E'(0) = V0 − Vs(0)     ← 이음매에서 속도가 안 끊긴다   ★ 지수 감쇠에 없던 것
E(T)  = 0              ← 보간시간 T가 지나면 시뮬과 일치
E'(T) = 0              ← 끝날 때도 속도가 안 튄다
```

넷을 만족하는 3차식은 유일하다. `u = t/T`, `e0 = E(0)`, `d0 = E'(0)·T`로 두면:

```
E(u) = e0·(2u³ − 3u² + 1) + d0·(u³ − 2u² + u)
```

**이것이 시작 속도 폭발을 없애는 이유**: 화면 속도(t=0) = `Vs(0) + E'(0)` = `Vs(0) + V0 − Vs(0)`
= `V0`. 즉 **보정 직전 속도 그대로 출발한다.** 갭이 아무리 커도 `갭/시간상수` 항이 생기지 않는다.
지수 감쇠는 `E(t) = e0·e^(−t/τ)`라 `E'(0) = −e0/τ`가 갭에 비례해 커지는 것이 문제였다.

권위 속도는 이미 `EntitySnap.velocity`로 오고, `V0`는 스무더가 직전 두 프레임의 렌더 위치로
직접 구한다 — 새로 나를 것이 없다.

**왜 언리얼과 다르게 가나**: 언리얼의 지수 감쇠가 §4에서 본 대로 우리 증상의 직접 원인이다.
사람 캐릭터는 한 틱에 4.8m씩 튀지 않아 언리얼에서는 드러나지 않는 한계다. 뼈대(문턱·역할 분리·
이름)는 언리얼을 따르고, 이 계산 한 군데만 데드레코닝 표준으로 바꾼다.

## 6. 상수 — 측정에서 뽑는다

| 상수 | 값 | 근거 |
|---|---|---|
| `MinCorrection` | **0.025 m** (유지) | 이 크기는 눈에 안 보인다. 숨길 튐이 없는데 녹이면 0.1초 내내 조금씩 틀린 자리에 있게 돼 오히려 오차가 는다 |
| `NetworkSimulatedSmoothLocationTime` | **0.1 s** (유지) | 지금 값. 보간 방식이 바뀌어 시작 속도 폭발이 사라지므로 시간을 늘릴 이유가 없다. 라이브에서 부족하면 먼저 조정할 값 |
| `NetworkNoSmoothUpdateDistance` | **8 m** | 정상 날갯짓 오차 최대가 4.788m다. 그 위로 넉넉히 잡아 **정상 날갯짓이 절대 순간이동으로 보이지 않게** 한다. 8m를 넘는 갭은 날갯짓으로 설명되지 않는다(리스폰·스폰 직후·큰 랙) |
| `NetworkMaxSmoothUpdateDistance` | **5 m** | 정상 오차 최대(4.788m)를 막 넘는 값. 정상 구간에서는 목줄이 당겨지지 않고, 그 이상 뒤처지면 붙잡는다 |

> 두 값 모두 **측정 최대치 4.788m를 기준선**으로 잡았다. 이 기준선은 리드 9틱·`FlapImpulse 23`·
> `Gravity 70`에서 나온 것이라, 셋 중 하나가 바뀌면 다시 재야 한다.

## 7. 무엇을 고치나

| 파일 | 변경 |
|---|---|
| `GameFramework/Runtime/Scripts/Netcode/RenderCorrectionSmoother.cs` | 지수 감쇠 → §5.3의 3차 에르미트 오차 보간. 문턱 이름을 언리얼에 맞춤. 권위 속도를 받도록 `OnCorrection` 시그니처 확장(`V0`는 스무더가 스스로 구한다) |
| `LOP-Client/Assets/Scripts/Netcode/RenderCorrectionSmootherFactory.cs` | 내 새용 스무더를 만들지 않는다. 남의 새 상수를 새 값으로 |
| `LOP-Client/Assets/Scripts/Entity/EntityBinder.cs:122` | (실제로는 손대지 않음 — 아래 "실제 구현과의 차이" 참고) |
| `LOP-Client/Assets/Scripts/Netcode/PredictedEntityInterpolator.cs` | `OnCorrection`/`Tick`이 `deltaTime`을 받아 스무더로 넘기도록만 확장("스무더가 없을 때" 분기는 만들지 않음) |
| `LOP-Client/Assets/Scripts/Netcode/Reconciler.cs` | `NotifyRenderCorrections`가 위치와 함께 **속도**도 넘김 |

**실제 구현과의 차이.** 위 표는 계획 시점 기준이고, 실제로는 "내 새엔 스무더를 안 붙인다"가 아니라
**`RenderCorrectionSmootherFactory.Create(local: true)`가 `smoothTime = 0`을 주는 쪽**으로 갔다.
`EntityBinder`는 손대지 않았고, `PredictedEntityInterpolator`에 "스무더가 없을 때" 분기도 만들지
않았다 — 이유: `PredictedEntityInterpolator.Cleanup()`이 조건 없이 `renderCorrectionSmoother.Reset()`을
부르므로, 스무더 자체가 null이었다면 내 새를 정리할 때마다 널 참조 예외가 났을 것이다.
`smoothTime = 0`은 `RenderCorrectionSmoother.OnCorrection`의 `_smoothTime <= 0f` 가드에서 항상 즉시
스냅으로 처리되어(§5.3) "스무더 없음"과 같은 결과(블렌드 없음)를 널 분기 없이 더 단순하게 낸다.

**시뮬은 한 줄도 안 바꾼다.** `FlappyWorld`·`FlappyBodyCollisionSystem`·`Reconciler`의 롤백/재생
로직은 그대로다.

## 8. 검증

**결정론 테스트 (`GameFramework` EditMode)** — `RenderCorrectionSmoother` 자체를 검사한다:

1. 갭 4.788m를 먹였을 때 **첫 프레임의 겉보기 속도**가 지수 감쇠(47.9 m/s)보다 확연히 작다
2. 보정 직후 렌더 속도가 **보정 직전 렌더 속도와 연속**이다(속도 점프 없음)
3. `MinCorrection` 미만은 즉시 채택(오프셋 0)
4. `NoSmoothUpdateDistance` 초과는 즉시 채택(오프셋 0)
5. 보간 도중 렌더가 시뮬에서 `MaxSmoothUpdateDistance` 이상 뒤처지지 않는다
6. 보간시간이 지나면 렌더 == 시뮬 (수렴)

**라이브 (2인)** — 남의 날갯짓이 진짜 속도로 보이는가, 몸싸움 때 내 새가 미끄러지지 않는가.

## 9. 하지 않는 것

- **시뮬 변경 없음.** 남의 새는 계속 예측 대상이고 계속 내 몸을 민다(사용자 결정).
- **입력 중계 없음.** 직전 spec §4가 기각했고 이번 측정도 뒤집지 않는다.
- **내 새 2.8m 오차를 없애지 않음.** 그건 남의 입력을 모르는 데서 오는 것이라 렌더로 못 고친다.
  이 슬라이스는 그 오차를 **감추지 않기로** 한다(즉시 반영). 없애려면 몸싸움 결합을 끊어야 하고,
  그건 사용자가 하지 않기로 결정했다.

## 10. 열린 항목

- **⚠️ 곡선이 최고 겉보기 속도를 낮추지 않는다 — 라이브의 첫 확인 항목.** 구현 리뷰에서 계산으로
  드러났다. 지수 감쇠의 최대는 t=0의 `갭/T = 47.9 m/s`인데, 에르미트의 최대는 u≈0.54의
  **`1.5·갭/T = 79 m/s`** 다. 흡수해야 할 총량(4.788m를 0.1초에)이 같으므로 평균은 47.9로 고정이고,
  **곡선은 움직임을 줄이는 게 아니라 뒤로 옮긴다.** 즉 이 슬라이스가 고치는 것은 *이음매의 저크*이지
  *최고 속도*가 아니다.

  사용자 증상("2~4배 빨라 보인다")이 저크 때문인지 속도 때문인지는 **눈으로만 판정된다.**
  속도 쪽이면 레버는 곡선이 아니라 `NetworkSimulatedSmoothLocationTime`이다 — 최고속도가 1/T로
  줄어 0.2초면 62.5, 0.3초면 49 m/s가 된다(그만큼 화면이 오래 뒤처진다).

  | T | 에르미트 최고 겉보기 속도 |
  |---|---|
  | 0.1초 (현재) | 79 m/s |
  | 0.2초 | 39 m/s |
  | 0.3초 | 26 m/s |

  **위 두 문단의 "0.2초→62.5/0.3초→49"와 이 표의 "0.2초→39/0.3초→26"은 둘 다 계산이 맞지만
  서로 다른 걸 재고 있다 — 모순이 아니다.** 위 문단(62.5/49)은 **위치 갭(G)과 플랩 속도(ΔV=23)를
  각 T에서 다시 정확히 합성**한 최고값이다. 에르미트의 속도항(`h10'·ΔV`) 기여분은 애초에 T로
  나뉘지 않고 `[0,1]` 구간에서 거의 고정폭이라 — **T를 늘려도 줄지 않는다.** 반면 이 표(39/26)는
  T=0.1의 총합(79)을 **위치항처럼 1/T로 단순 비례 축소**한 값이라, 줄지 않는 속도항 기여분까지
  같이 줄여 버려 **실제보다 낙관적으로(작게) 나온다.** 즉 T를 늘려 최고 속도를 낮추려는 대책은
  이 표(39/26)가 아니라 위 문단(62.5/49) 쪽을 기준으로 판단해야 한다.

- **⚠️ 연속 보정(back-to-back correction)에서는 에르미트가 지수 감쇠보다 잔여 오차를 더 천천히
  지운다 — 구현 리뷰의 새 지적.** 20ms 틱 한 번 지나는 동안 남는 오차 비율이 `h00(u=0.2) = 0.896`
  (에르미트, u=Δt/T=0.02/0.1)인데 옛 지수 감쇠는 `exp(-0.2) = 0.819`였다. **한 틱에 남기는 몫이
  0.896/0.819 ≈ 1.7배** — 남의 새가 연달아 보정받는 상황(활공 없이 계속 미세 보정이 오는 경우)
  에서는 정상상태 렌더 지연이 지수 감쇠 때보다 대략 1.7배 커진다는 뜻이다. 그 지연의 상한은
  `MaxSmoothDistance = 5m`(목줄)이 잡아 주지만, 그 상한 자체가 이번 라운드까지 5m로 유지됐다.
  **이건 §10 첫 항목(최고 속도)과 반대 방향으로 당기는 레버다** — `SmoothTime`을 늘려 최고 속도를
  낮추면(같은 원리로 `h00`이 더 1에 가까워져) 이 정상상태 지연은 더 나빠진다. 즉 "최고 속도가
  문제냐, 잔여 지연이 문제냐"를 먼저 라이브에서 가려야 어느 레버를 당길지 정할 수 있다 — 곡선
  자체를 바꾸는 결정이 아니라 **`SmoothTime` 하나로 두 증상을 동시에 만족시킬 수 없다는 사실**이
  이번 라운드의 결론이다.

- **`NetworkMaxSmoothUpdateDistance`가 실제로 발동하는지** — 보간이 0.1초로 짧아 목줄이 한 번도
  안 당겨질 수 있다. 그러면 값이 아니라 존재 자체가 죽은 코드다. 라이브에서 발동 횟수를 세어 보고,
  0이면 제거를 검토한다.
- **내 새 스무딩 제거의 체감** — 몸싸움에서 미끄러짐 대신 즉시 튐이 된다. 표준이지만 이 게임에서
  더 나은지는 라이브에서 봐야 한다. 나쁘면 되돌리기 쉽다(팩토리 한 줄).
