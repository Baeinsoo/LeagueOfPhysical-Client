# 결승선 — 통과 판정 일원화와 골인 연출

작성일: 2026-09-04
상태: 확정 (구현 플랜은 별도)
관련: `2026-09-03-flappy-chaser-design.md`(추격자), `2026-08-05-flappy-multiplayer-concept-design.md`(기획)

## 1. 왜

**결승선을 넘어도 아무 일도 일어나지 않는다.** 새가 그냥 계속 날아가고, 한참 뒤에 결과 화면이
뜬다. 클라에는 "통과했다"를 아는 경로가 아예 없다 — 판정은 서버만 하고, 그 결과는 판이 끝날 때
등수로만 온다.

만들려는 것: **선을 넘으면 중력 없이 직선으로 달리다 감속해 멈추고, 서버가 확정한 등수가 뜬다.**
(100m 주자가 결승선을 지나 감속하는 그림, 카트라이더의 골인.)

그런데 새를 멈추려면 **클라가 통과를 알아야** 하고, 그러려면 판정이 시뮬(클·서 공통 코드)로
들어와야 한다. 그 순간 "누가 통과를 판정하는가"가 다시 열린다 — 이 문서의 절반은 그 정리다.

## 2. 범위

두 부분으로 나눈다. 1은 **동작이 바뀌지 않는 정리**이고, 2가 새 기능이다.

**Part 1 — 통과 판정을 시뮬로 (Flappy + Skydive)**
- 서버 전용 `FinishLineTrackingSystem`을 없애고, 판정을 공용 시뮬로 옮긴다
- 두 게임이 같은 부품을 쓴다
- **등수 결과는 지금과 같아야 한다** — 그게 이 부분의 검증 기준이다

**Part 2 — 골인 연출 (Flappy)**
- 통과 뒤 감속해 정지
- 서버가 확정한 등수를 스냅샷으로 받아 표시
- 추격자 벽을 결승선에서 멈춘다

**안 하는 것**
- 관전·나가기 UI(다른 캐릭 보기, 나가기) — 완주자와 탈락자가 **같은 UI를 쓰므로** 별도 슬라이스로
  뺀다. 지금도 탈락자가 그 상태다(한 새만 강제로 보고 못 나감)
- 결승선 자체의 아트(체크 지점 모양·배너)
- 골인 사운드·카메라 연출

## 3. Part 1 — 통과 판정을 시뮬로

### 3.1 지금 구조

`FinishLineTrackingSystem`(서버)이 러너의 End 페이즈에서 매 틱 돈다:

1. 첫 틱에 씬에서 `FinishLine` 마커를 찾아 렌더러 바운드를 기억
2. 감시 중인 몸마다 `ActorRegistry`에서 액터를 찾아 **콜라이더 바운드**를 읽음
3. `FinishLineOverlap.Past(몸, 선, 축, 방향)` ≥ 0 이면 `FinishOrderTracker.Observe`

판정 자체는 옳다. 문제는 **클라가 이 답을 못 쓴다**는 것뿐이다.

### 3.2 클라가 서버에 물어보면 안 되는 이유

내 새는 예측으로 굴러가므로 서버 답은 약 0.2초 뒤에 온다. 11m/s면 **2.2m를 더 날아간 뒤에야**
감속이 시작된다 — 하필 손맛의 순간이다. 그래서 클라도 스스로 판정해야 한다.

스턴·대시가 이미 이 구조다: 클라가 같은 규칙으로 예측하고, 스냅샷의 서버 값과 어긋나면 되돌린다.

### 3.3 그러면 판정이 둘이 된다 — 그래서 합친다

시뮬은 **클·서가 같이 돌리는 코드**다. 판정을 시뮬에 넣으면 서버에는 판정이 둘이 된다:
기존 추적기(등수용)와 시뮬(감속용). 같은 질문에 두 곳이 각자 답하는 구조다.

같은 식을 쓰더라도 **읽는 자리가 다르면**(콜라이더 vs 진실원본) 언제 갈릴지 보장할 수 없고,
갈리면 *감속은 시작했는데 추격자에겐 아직 안 끝난 새*가 생긴다.

**그래서 하나로 합친다. 시뮬이 판정하고, 서버는 그 기록을 읽어 등수만 매긴다.**

### 3.4 새 구조

```
Shared (게임을 안 가림)
├─ FinishLineBounds   결승선 바운드 홀더. 맵 마커가 스스로 등록
├─ FinishState        컴포넌트 — 처음 넘은 틱 + 그때의 깊이 (틱 −1 = 아직)
├─ FinishSystem       축·방향을 받아 판정. 안에서 FinishLineOverlap.Past를 부른다
└─ FinishOrder        기록들을 등수 순으로 정렬 (순수 함수)

FlappyWorld.Detection   → FinishSystem.Tick   (X, 커지는 방향)
SkydiveWorld.Detection  → FinishSystem.Tick   (Y, 작아지는 방향)

서버 룰   FinishState를 모아 FinishOrder로 정렬 → 기존 FinishPlacements 그대로
```

**몸 바운드는 `Transform` + `CapsuleShape`로 조립한다.** 콜라이더가 원래 그 둘로 만들어지므로
(`PhysicsBodyFactory`: `radius = CapsuleShape.Radius`, `center.x = 0`) **같은 값**이고, 되돌리기
재생 중에도 얼지 않는다. 시뮬이 엔진 트랜스폼을 읽으면 안 되는 이유는 정확도가 아니라 이것이다 —
재생 중엔 물리를 안 돌려 콜라이더가 한 틱 전에 멈춰 있고, 그러면 같은 코드가 라이브와 재생에서
다른 답을 낸다(`FlappyWorld`의 `Depenetrate`가 이미 같은 이유로 진실원본을 쓴다).

**결승선 바운드는 맵 마커가 준다.** `WindVolume`이 쓰는 통로 그대로 —
`[SceneInjectMonoBehaviour]` + `[Inject] Construct(FinishLineBounds)`. 맵이 올라올 때 마커가
스스로 등록하므로, 시뮬이 첫 틱에 씬을 훑는 우회가 없다. 클·서가 같은 맵의 같은 마커를 보므로
값이 같다.

마커가 없을 때의 폴백 좌표(Skydive의 `GroundY`)는 홀더가 받는다 — 지금 추적기가 갖고 있던 책임을
그대로 옮긴다.

### 3.5 한 틱의 순서

```
Mutation   : 스턴·대시 → 이동 → 밀어내기 → 맵에 막히며 이동
Detection  : 통과 판정          ← 이동이 끝난 자리
```

`Detection`은 아키텍처 문서가 "상태를 스캔해 파생 사건을 만드는 자리"로 정의해 둔 페이즈이고,
두 게임 모두 아직 비어 있다. 통과 판정이 정확히 그 모양이다.

**이동 뒤여야 한다.** 앞에 두면 한 틱 전 자리를 보고 통과를 한 틱 늦게 잡는다. 지금 서버 추적기도
`world.Tick`이 끝난 뒤(End 페이즈)에 본다 — 같은 자리다.

### 3.6 사라지는 것 / 남는 것

**사라진다**
- `FinishLineTrackingSystem` — 매 틱 씬을 훑고 `ActorRegistry`를 뒤지던 서버 시스템
- `FinishOrderTracker` — 누가 언제 넘었는지를 따로 들고 있던 상태. 이제 그 정보가 `FinishState`에
  있으므로, 남는 일은 정렬뿐이다(`FinishOrder`). 두 곳이 같은 사실을 들고 있지 않게 한다
- `FlappyRaceProgress` / `SkydiveProgress` — 중심 기준 좌표 비교. **이미 사용처가 없고**,
  바운드 규칙으로 대체된다

**그대로 남는다**
- `FinishLineOverlap` — 판정식. 이미 축을 받는 순수 계산이다
- `FinishRecord` + `SameRankAs` — 기록과 동률 규칙
- `FinishPlacements` — 등수. 먹이는 쪽만 바뀐다

### 3.7 덤으로 고쳐지는 것

지금 추적기는 콜라이더를 못 찾으면 **크기 0인 바운드**로 대체한다:

```csharp
bounds = new Bounds(GetPosition(entity), Vector3.zero);   // 중심 기준
```

그 몸만 반지름(0.45m)만큼 늦게 통과 판정된다. 주석은 "있어선 안 되지만"이라고 적어 뒀지만
조용히 다른 답을 내는 경로다. 새 구조에는 이 갈래가 없다 — 몸 바운드가 항상 `CapsuleShape`에서
나온다.

### 3.8 되돌리기

`FinishState`를 두 게임의 저장·복원(`SaveGameState`/`LoadGameState`)에 넣는다. 클라가 통과를
예측하므로 되돌릴 수 있어야 한다.

### 3.9 이 부분의 검증 기준

**등수가 지금과 같게 나와야 한다.** 동작을 바꾸는 작업이 아니다. 2인 라이브에서 완주 틱과 깊이,
그리고 결과 화면의 등수를 옮기기 전후로 대조한다.

## 4. Part 2 — 골인 연출

### 4.1 통과 뒤 움직임

| | |
|---|---|
| 중력 | 없음 |
| 세로 속도 | 0 — 완전한 수평 직선 |
| 입력 | 무시(날갯짓·대시 안 먹음) |
| 전진 | `FinishBrake`(m/s²)로 감속해 **0에서 멈춤** |

대시와 같은 모양인데 **지속이 아니라 감속**이라는 것만 다르다. 감속은 통과한 **다음 틱부터**
시작된다 — 통과하는 그 틱은 아직 레이스 중이었으므로 평소 규칙으로 난다.

`FinishBrake`는 MasterData 열(`finish_brake`)로 둔다. 11m/s에서 약 2초에 멈추는 값(≈5.5)을
초기값으로 삼고, 라이브에서 조정한다.

**남의 새는 로컬 판정이 필요 없다.** 클라는 남의 새를 굴리지 않고 스냅샷 보간으로 그리는데,
그 스냅샷에는 서버에서 이미 감속한 위치가 들어 있다. 따라서 남의 새도 저절로 감속해 보인다.

### 4.2 등수

**서버만 매길 수 있다.** 남들이 언제 어떤 깊이로 들어왔는지가 있어야 하는데, 클라는 남의 새를
0.23초 늦게, 스냅샷으로만 본다.

`EntitySnap`에 `int32 finish_placement = 22`를 더한다. **0 = 아직**이다.

- proto3는 기본값을 안 실으므로 달리는 동안 **비용이 0**이다
- 모든 엔티티 스냅에 실리므로, 나중에 "남의 새 위에 2등 뱃지"를 붙일 재료가 이미 생긴다
- 서버는 `FinishOrder`로 정렬한 목록에서 그 사람의 순위를 뽑아 채운다. 공동 순위 규칙은
  `FinishPlacements`가 이미 갖고 있으므로 그 계산만 작은 순수 함수로 꺼낸다

클라는 받은 값을 표시용 보관소에 넣고 UI가 읽는다 — **시뮬 상태가 아니므로 월드 컴포넌트에 두지
않는다.** (`FinishState`는 시뮬이 쓰는 값, 등수는 서버가 알려주는 표시값이다.)

### 4.3 화면

내 새가 통과하면 등수를 화면 가운데에 띄운다("1등"). 탈락 표시(`RaceEliminatedView`)와 같은
밴드·같은 모양이고, 문구와 색만 다르다.

관전·나가기 버튼은 이 슬라이스에 넣지 않는다(§2) — 완주와 탈락이 **같은 UI를 써야** 하므로,
그 UI를 만드는 슬라이스에서 두 상태를 함께 다룬다.

### 4.4 추격자 벽을 결승선에서 멈춘다

지금 곡선대로면 벽은 75.2초에 결승선에 닿고 **그 뒤로도 계속 간다.** 70초에 완주한 새는 결승선
11m 뒤(643m)에 멈춰 서는데, 벽이 그 자리에 76.3초에 도달한다 — 멈춰 선 지 4초쯤 뒤에 **벽이 그
새를 통과한다.** 완주자는 추격자 판정에서 빠져 안 죽는데, 화면에서는 벽에 먹히는 것처럼 보인다.

`FlappyChaserCurve.XAt`에 상한 인자를 더해 결승선에서 멈춘다. 서버 시스템과 클라 뷰가 같은
결승선 값을 넘기므로 멈추는 자리도 하나다.

**잡는 능력은 안 줄어든다** — 벽이 결승선에 도달한 시점에 아직 못 들어온 사람은 전부 벽 뒤에 있다.

## 5. 산업 표준 매핑

- **판정을 시뮬에 두고 클라가 예측·서버가 권위** — 이 프로젝트의 스턴·대시와 같은 구조이고,
  fast-paced 넷코드의 표준(예측 + reconcile)이다.
- **`Detection` 페이즈** — 아키텍처 문서의 Generation Phase 3(상태 스캔으로 파생 사건 발생)에
  그대로 대응한다. `IsDead → DeathEvent`와 같은 자리에 `넘었나 → 통과 기록`이 들어간다.
- **맵이 좌표를 정한다** — 결승선 마커는 Unreal의 `ATriggerVolume` 계열 골 마커에 대응한다.
  코드가 좌표를 갖지 않는다(`FinishLine`의 기존 주석이 이미 그렇게 적고 있다).
- **통과 뒤 자동 감속** — 레이싱 장르 관례(카트라이더·마리오카트: 골인하면 조작이 끊기고
  차가 스스로 감속한다). 조작을 끊는 이유는 골인 뒤 행동이 등수에 영향을 주지 않게 하려는 것이다.

## 6. 테스트

| 무엇 | 어디 | 무엇을 지키나 |
|---|---|---|
| `FinishSystem` | LOP-Shared EditMode | 부리가 닿으면 통과 / 중심만 넘은 건 아직 / **처음 넘은 틱만 기록**(뒤 틱이 덮어쓰지 않는다) / 아직이면 틱이 −1 / 두 축(X 증가·Y 감소) 모두 |
| `FinishOrder` | LOP-Shared EditMode | 먼저 닿은 순 / 같은 틱이면 깊이 / 완전 동률은 순서를 만들지 않는다 (기존 `FinishOrderTracker` 테스트를 옮긴다) |
| `FinishLineBounds` | LOP-Shared EditMode | 마커가 등록되면 그 바운드 / 없으면 폴백 좌표로 두께 0인 선 |
| `FlappyMoveSystem` | LOP-Shared EditMode | 통과 뒤엔 중력이 안 실린다 / 세로 속도 0 / 날갯짓이 안 먹는다 / 감속해 0에서 멈추고 음수로 안 간다 |
| `FinishPlacements` | 서버 EditMode | **변경 없음** — 그대로 통과해야 한다(먹이는 쪽만 바뀌었다는 증거) |

배선(홀더 등록, 스냅샷 채우기, UI)은 자동 테스트가 안 붙는다 — **2인 라이브**로 확인한다:

- Part 1: 옮기기 전후로 **완주 틱·깊이·등수가 같다**
- Part 2: 통과하면 수평 직선으로 감속해 멈춘다 / 등수가 뜨고 서버 로그와 일치한다 /
  벽이 결승선에서 멈춘다 / 남의 새도 감속해 보인다

## 7. 열린 항목

- 관전·나가기 UI (완주·탈락 공통) — 다음 슬라이스
- 결승선 아트(체크 지점 모양), 골인 사운드·카메라
- 남의 새 위 등수 뱃지 — 재료(`finish_placement`)는 이 슬라이스에서 생긴다
- `FinishBrake` 값 — 초기 5.5(약 2초). 라이브에서 조정
- Skydive의 통과 뒤 처리 — 이 슬라이스는 Skydive의 **판정 경로만** 옮기고 연출은 안 건드린다

## 8. 이 설계에 이르기까지 (박제)

논의 중에 네 번 방향을 틀었다. 같은 자리를 다시 밟지 않도록 남긴다.

**① "시뮬은 좌표, 서버는 형상" — 폐기.** 처음엔 시뮬이 `x ≥ 결승선x`(중심 기준)로 따로 판정하게
하려 했다. 그건 서버 판정보다 몸 반지름만큼 늦게 걸리는 **다른 규칙**이었다. 같은 식을 써야 한다.

**② "콜라이더가 더 정확하다" — 사실이 아니다.** 콜라이더는 진실원본이 아니라 **그것을 복사한
몸**이다(`MotionBridge.PushMotion`이 `rb.position = World.Transform.Position`). `radius`도
`CapsuleShape`에서 왔고 x 중심이 0이라, `collider.bounds.max.x`는 정의상
`World.Transform.x + BodyRadius`다. 시뮬이 콜라이더를 안 읽는 이유는 정밀도가 아니라 되돌리기다.

**③ 판정 시점을 이동 *앞*에 두려 했다 — 틀렸다.** 한 틱 전 자리를 보게 되어 통과를 한 틱 늦게
잡는다. 서버는 이미 이동이 끝난 뒤에 본다.

**④ "판정 둘을 같은 자리에서 읽게 맞추자" → "하나로 합치자".** 둘을 남기면 계속 맞는지 지켜봐야
한다. 시뮬이 판정하고 서버가 그 기록을 읽으면 검사가 하나가 되고, 콜라이더냐 진실원본이냐 하는
문제 자체가 사라진다. Skydive도 구조가 같아 함께 옮긴다.
