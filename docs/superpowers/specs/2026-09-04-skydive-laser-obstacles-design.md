# Skydive 레이저 장애물과 체크포인트 복귀

> 코스에 **닿으면 죽는 레이저**를 놓고, 죽으면 **마지막으로 지난 선반으로 되돌린다.**
> 곁들여 **텔레포트를 명시적으로 표현하는 범용 장치**를 GameFramework에 만든다.

이 문서는 `2026-08-30-skydive-game-mode-design.md` §3(코스 — 레이저·강체·경계)을 이어받아,
그 뒤에 생긴 것들(선반·바람·스태미나·키네마틱 컨트롤러)에 맞춰 다시 세운 것이다. 원 스펙에서
**바뀐 곳은 원 스펙 §3.3 하나**다 — 판정 알고리즘과 그 안의 터널링 수치. 나머지 결정은 그대로
살아 있다.

---

## 1. 무엇이 문제인가

코스에는 지금 **선반과 바람**이 있다. 선반은 "어디로 가야 하나"를 묻고 바람은 "어떻게 실릴 것인가"를
묻는데, **틀렸을 때 잃는 것이 시간뿐**이다. 그래서 모든 선택이 "조금 손해"와 "조금 이득" 사이에만
있고, 긴장이 없다.

레이저는 **틀리면 크게 잃는** 첫 장치다. 그리고 움직이는 레이저는 *"천천히 가면 안전"* 을 깬다 —
오래 머물수록 노출 시간이 길어지기 때문이다. 이것이 패러세일이 지배 전략이 되지 않게 하는 축이다.

**지금 스카이다이브에는 죽음이 아예 없다.** `SkydiveRuleSystem`에 `// 스카이다이브에는 탈락이 없다.`
라고 적혀 있고, 판이 끝나는 길은 결승 통과와 시간 초과뿐이다. 그래서 레이저는 *맞으면 어떻게 되는가*
없이는 아무 일도 일어나지 않는 장식이다. 이 슬라이스가 둘을 함께 짓는 이유다.

---

## 2. 결정 요약

| 무엇 | 결정 |
|---|---|
| 레이저의 상태 | **없다.** 틱을 넣으면 위치가 나오는 식뿐 |
| 맞았는지 판정 | **Conservative Advancement** (Bullet·Box2D 표준). 서버만 |
| 맞으면 | **마지막으로 지난 선반으로 복귀** + 속도 0 + 스태미나 만땅 + 짧은 무적 |
| 클라 예측 | **하지 않는다.** 죽음은 서버 권위 |
| 텔레포트 표현 | **명시적 카운터**를 스냅샷에 실어 보낸다 (거리 임계값에 기대지 않는다) |
| 배치 | 구간마다 다른 어법 — 문지기 → 격자 → 합침 |
| 굽기 전 검사 | 구멍이 열리는가 · 부활 지점이 유효한가 · 회전이 읽을 수 있는가 |

## 3. 레이저는 상태를 갖지 않는다

모든 레이저를 **"시간을 넣으면 자세가 나오는 식"** 으로만 정의한다.

```
angle(t) = StartAngle + AngularSpeed × t          (고정 빔은 AngularSpeed = 0)
lit(t)   = ((t + Phase) mod Period) < OnTicks     (상시 점등은 OnTicks ≥ Period)
```

클라와 서버가 같은 식을 각자 계산한다. **스냅샷에 실을 것이 0바이트이고, 롤백에서 되돌릴 것이
없다.** 레이저를 수백 개 깔아도 네트워크 비용이 늘지 않는다.

### 3.1 네 종류는 한 식의 변형이다

| 종류 | 어떻게 만드나 | 코스에서 하는 말 |
|---|---|---|
| 고정 빔 | `AngularSpeed = 0` | "여긴 못 지나간다" — 길을 나눈다 |
| 회전 빔 | `AngularSpeed ≠ 0`, `SweepHalfRange = 0` | "3초에 한 번 열린다" — 타이밍을 강요한다 |
| 왕복 빔 | `SweepHalfRange > 0` (삼각파) | "지금 오고 있다" — 위험이 예고된다 |
| 점멸 빔 | `OnTicks < Period` (위 셋과 직교) | 위상을 어긋나게 깔면 리듬 구간이 된다 |

왕복은 각도에 **삼각파**를 씌워 만든다. 진행각을 접어 `[-HalfRange, +HalfRange]`를 오간다:

```
Fold(x, half):
    period = 4 × half
    m = Mod(x + half, period)                    // [0, period)
    return m ≤ 2×half ? m - half : 3×half - m

angle(t) = StartAngle + Fold(AngularSpeed × t, SweepHalfRange)
```

검산: `x=0 → 0`, `x=half → +half`(정점), `x=2·half → 0`, `x=3·half → −half`(저점). 주기 `4·half`.

### 3.2 데이터 모델

```
Laser (설정 데이터 — anemic, 로직 없음)
    Pivot          : Vector3    회전 중심
    Length         : float      빔 길이 (Pivot에서 뻗어 나가는 선분)
    Radius         : float      빔 굵기(반지름)
    StartAngle     : float      rad, XZ 평면 (회전축은 Y)
    AngularSpeed   : float      rad / 틱
    SweepHalfRange : float      0이면 전회전, >0이면 왕복 폭
    Period, OnTicks, Phase : int   점멸 (틱 단위)
```

점멸 파라미터를 **정수 틱**으로 두는 것은 우연이 아니다. 그래야 **한 틱 안에서 켜짐 상태가 변하지
않고**, 판정은 틱 시작에 `lit(tick)`을 한 번만 보고 꺼져 있으면 그 레이저를 통째로 건너뛸 수 있다.
실수 시각에 켜졌다 꺼지면 §4의 시간 감기 도중에 상태가 바뀌어 판정이 훨씬 복잡해진다.

빔은 **Pivot에서 한쪽으로만 뻗은 선분**(시계바늘)이다. 통로를 가로지르는 빔은 Pivot을 벽 쪽에 둬서
만든다. 회전축을 Y로 고정하는 이유는 코스가 수직 통로이고, 수평면에서 도는 빔이 낙하 경로를 가장
잘 가르기 때문이다.

### 3.3 차단(엄폐)은 계산하지 않는다

"레이저가 기둥에 막힌다"를 매 틱 레이캐스트로 계산하지 않는다. 대신 **레이저마다 각도 범위를
제한해** 기둥 쪽으로 오지 않게 배치한다. 결과는 같고(기둥 뒤가 안전하다), 계산은 0이며,
**레이저가 어디까지 오는지 플레이어가 눈으로 읽을 수 있다**는 이득이 덤으로 붙는다.

## 4. 맞았는지 판정하는 법

### 4.1 문제 — 시간을 끊어 보면 뚫고 지나간다

한 틱 사이에 캐릭터는 크게 움직인다. 다이브 종단속도 90 m/s에 틱 간격 `interval`을 곱한 거리다
(`interval`은 러너가 넘겨주는 값이며 코드에 박지 않는다). 캡슐 반지름은 0.3 m대이고 빔은 얇다.
그래서 **틱 시작과 틱 끝에서만 겹침을 보면 레이저를 통과해도 잡히지 않는다** — 터널링이다.

### 4.2 원 스펙의 방식과 그 결함

원 스펙 §3.3은 **캐릭터 경로를 캡슐 반지름보다 작은 조각으로 쪼개** 조각마다 정적 검사를 하자고
했다. 두 가지가 어긋난다.

1. **수치가 낡았다.** 스펙은 다이브를 40 m/s로 잡았으나 젤다 맞춤 이후 **90 m/s**다. 조각 수가
   7에서 17로 늘고 비용도 그만큼 늘어난다.
2. **더 중요한 결함: 레이저가 계산에 들어가지 않는다.** 캐릭터만 쪼개고 레이저는 틱 하나로 고정해
   본다. 회전 빔이 그 틱 안에 캐릭터를 훑고 지나가면 **캐릭터를 아무리 잘게 쪼개도 잡히지 않는다.**

### 4.3 채택 — Conservative Advancement

**"확실히 안전한 만큼만 시간을 앞으로 감는다."** 지금 거리가 `d`이고 둘이 가까워질 수 있는 최대
속도가 `v`이면, `(d − R) / v` 만큼은 절대 닿지 않는다. 그만큼 건너뛰고 다시 잰다.

```
입력: 이번 틱의 캡슐 축 이동 (A0→A1),  레이저 angle(t),  허용 거리 R = 캡슐반지름 + 빔반지름
      t는 이 틱 안에서 0..1로 정규화한 시간

Dc = |A1 − A0|                       // 이 틱에 캐릭터가 가는 거리
Dl = |AngularSpeed| × Length         // 이 틱에 빔 끝이 그리는 호의 길이
v  = Dc + Dl                         // 접근 속도 상한 (t 단위당)

t = 0
반복 (최대 MaxIterations회):
    d = SegmentDistance(캡슐축(t), 레이저선분(t))
    if d ≤ R:        →  명중, 시각 t
    if v ≤ 0:        →  통과
    t += (d − R) / v
    if t ≥ 1:        →  통과
반복 상한 도달  →  통과 (관대하게)
```

**왜 새지 않는가.** 움직이는 두 도형 사이 거리 함수는 *각 도형 위 점들의 최대 속도의 합*을 기울기
상한으로 갖는다. 캡슐은 이 틱 동안 **평행이동만** 하므로 모든 점의 속도가 `Dc`이고, Pivot을 도는
선분은 가장 빠른 점이 끝점이며 그 속도는 **호의 길이 `ω × Length`** 다.

이것은 새로 만든 논증이 아니라 **Mirtich 원식 그대로**다 — CA의 표준 상한은 선속도에 *각속도 ×
바운딩 스피어 반지름*을 더해 만든다. 우리 빔은 Pivot을 중심으로 반지름이 `Length`이므로 그 항이
`ω × Length`가 된다.

> **Box2D의 회전 한계가 우리에겐 적용되지 않는 이유.** Box2D 문서는 *"회전이 충분히 크면 놓칠 수
> 있다"* 고 경고한다. 임의 볼록 도형의 sweep을 선형 근사하기 때문이다. 우리는 도형이 **선분 대
> 선분**이고 회전이 **Y축 고정 1자유도**라 그 근사를 하지 않는다. 그래도 구현 시 §9의 "회전 훑기"
> 테스트로 실증한다.

### 4.3.1 2D 엔진을 근거로 삼은 것이 아니다

CA의 안전 시간은 `거리 ÷ 최대 접근 속도`이고, 이는 거리 공간 논증이라 **차원을 가리지 않는다.**
근거도 3D 쪽이 더 두껍다 — Mirtich 원논문이 3D 강체이고, **우리가 실제로 쓰는 PhysX가 자기 CCD를
*best-effort conservative advancement scheme*이라고 문서에 적어 두었다.** Bullet도 3D다. Box2D는
같은 알고리즘을 쓰는 곁다리 확인일 뿐이다.

3D라서 실제로 달라지는 곳은 둘이고, 둘 다 우리에게 유리하다.

| | 일반적인 3D | 우리 경우 |
|---|---|---|
| 회전 자유도 | 3자유도라 일반 각(角)CCD가 어렵다 | 레이저는 **Y축 고정 1자유도**, 캐릭터 캡슐은 회전조차 없다 |
| 두 선분의 관계 | 대개 **꼬인 위치(skew)** — 2D엔 없는 경우 | 그래서 2D 거리 루틴을 못 쓰고 **3D 선분-선분 최단거리**를 쓴다 |

두 번째가 §4.3 의사코드의 `SegmentDistance`가 반드시 3D 판이어야 하는 이유다(수직 캡슐 축과 수평
빔은 거의 항상 어긋나 있다).

### 4.4 반복 상한과 관대한 처리

스칠 때는 `d`가 `R`에 천천히 수렴해 반복이 늘어난다(CA의 알려진 성질). **`MaxIterations = 16`** 을 두고
(Box2D의 `b2_maxTOIIterations`가 20이다), **상한에 닿으면 통과로 본다.** 억울한 죽음이 놓친 죽음보다 나쁘기 때문이다. 상한에 걸린 횟수는
계측 로그로 남겨, 실제로 유의미하면 그때 값을 조정한다.

### 4.5 틱당 회전 상한 — 정확성이 아니라 가독성과 비용

`AngularSpeed`에 상한을 둔다. **정확성 때문이 아니다**(4.3 논증대로 회전이 커도 새지 않는다).

- **가독성**: 한 틱에 크게 도는 빔은 플레이어가 읽을 수 없다. 피할 수 없는 것은 장애물이 아니라
  주사위다.
- **비용**: `Dl`이 커지면 안전 전진 폭이 잘아져 반복이 늘어난다.

**시작값 `MaxAngularSpeedPerTick = 15°`.** 20 Hz 기준으로 초당 300°(0.83바퀴)라 게임플레이에 충분히
빠르면서, 한 틱에 15°면 다음 틱 위치가 눈으로 예측된다. 상한은 코스 굽기 검사(§7.2)가 강제하므로,
표에 과한 값을 적으면 **굽기 자체가 거절된다.**

### 4.6 판정은 서버만 한다 — 그래서 결정론 요구가 없다

죽음은 서버 권위이고 클라는 예측하지 않는다(§5.3). 따라서 **레이저 판정은 서버에서만 돈다.**
클라는 레이저를 *그리기만* 한다.

그 결과 **`cos`/`sin`을 자유롭게 쓸 수 있다.** IEEE 754가 초월함수의 끝자리를 정하지 않아 윈도우
클라와 리눅스 서버가 갈릴 수 있지만, 클라가 그린 빔이 1e-7 라디안 어긋나는 것은 아무 문제가
아니다. 나중에 클라가 죽음을 예측하고 싶어지면 **그때 각도 룩업 테이블을 넣는다** — 지금은 짓지
않는다.

## 5. 맞으면 — 체크포인트 복귀

### 5.1 체크포인트에는 저장할 상태가 없다

**체크포인트 = 마지막으로 지난 선반.** 선반 고도 표(2600 / 2200 / 1800 / 1400 / 1000 / 600 / 200)와
죽은 지점의 y만 있으면 계산된다:

```
Checkpoint(deathY) = 선반 고도 중 deathY보다 큰 것들의 최솟값
                     그런 선반이 없으면(첫 선반 위에서 죽음) 스폰 고도
```

진행도를 따로 기록하지 않는다. 지금도 `SkydiveProgress`가 y 하나로 완주를 판정하는 것과 같은
이유다 — 코스가 아래 한 방향이라 한 축이면 충분하다.

### 5.2 부활 상태

| 무엇 | 값 | 왜 |
|---|---|---|
| 위치 | 그 선반의 **부활 지점** (표에 명시) | 아래 참조 |
| 속도 | 0 | 떨어지던 속도를 물려주면 부활 직후 통제가 안 된다 |
| 스태미나 | 만땅 | 이미 시간을 크게 잃었으므로 자원까지 뺏지 않는다 |
| 자세·활공 | 초기화 (활공 해제) | 부활 직후 펴진 상태로 시작하면 조작이 끊긴다 |
| 무적 | 부활 후 **2.0초** 동안 레이저 판정 제외 | 부활 지점 근처를 지나는 빔에 즉시 다시 죽는 고리를 막는다 |

**부활 지점은 선반 표(`SkydiveCourseBuilder.Shelves`)에 열을 하나 더해 명시한다.** 규칙으로 유도하지 않는 이유는 선반마다 구멍 위치가 다르고,
"구멍에 안 빠지면서 판 위"라는 조건을 규칙 한 줄로 만들면 선반 표가 바뀔 때마다 조용히 어긋나기
때문이다. 명시하면 굽기 전 검사(§7.2)가 그 좌표를 직접 확인할 수 있다.

**동시 부활**은 부활 순번에 따라 **반지름 2 m 원 위로 결정론적으로 흩는다**(0°, 60°, 120° …).
캐릭터끼리는 단단한 벽이라 같은 자리에 겹쳐 놓으면 서로 밀어낸다.

무적은 **서버만 안다.** 부활 지점은 선반 위이고 레이저는 구멍 근처에 놓이므로 무적 중에 빔을
통과하는 그림이 나올 일이 드물다. 실제로 눈에 띄면 그때 연출을 붙인다.

### 5.3 클라는 죽음을 예측하지 않는다

**서버 권위.** 근거는 이미 잠긴 결정이다 — 2026-07-12에 같은 이유로 클라 데미지 예측을 짓지 않기로
했다. 잘못 예측한 죽음은 되돌릴 때 훨씬 잔인하고("죽었다가 살아남"), 스치는 판정에서 클라·서버가
갈리면 그 대가가 400 m짜리 위치 불일치다.

대가는 왕복 지연만큼 늦게 부활하는 것이다. 그 사이 클라는 계속 떨어지다가 부활 위치로 튄다.

### 5.4 새로 실어 보낼 것은 거의 없다

`EntitySnap`이 이미 **위치·속도·스태미나**를 싣는다. 부활이 바꾸는 것이 정확히 그 셋이므로 와이어에
추가할 것은 §6의 텔레포트 카운터 하나뿐이다.

## 6. 텔레포트 — 명시적 신호 (범용 장치)

### 6.1 거리 임계값에 기대지 않는다

클라의 렌더 보정 스무더에는 `NoSmoothUpdateDistance = 8 m`가 있고 주석이 *"리스폰·스폰 직후·큰 랙"* 을
지목한다. 400 m 부활은 이 값을 넘으므로 **우연히** 잘 동작한다.

그러나 이것은 **큰 랙을 위한 안전망이지 의도를 나타내는 신호가 아니다.** 3 m짜리 텔레포트(문·발사대·
되돌리기)는 임계값 아래라 그대로 미끄러진다. 짧은 텔레포트는 앞으로 충분히 생길 수 있으므로,
**"이번 이동은 텔레포트다"를 상태에 명시적으로 싣는다.**

### 6.2 불리언이 아니라 카운터

스냅샷은 unreliable이다(청킹 설계 참조). 텔레포트한 틱의 패킷 하나가 유실되면 **불리언은 영영
관측되지 않고** 그대로 미끄러진다. 단조 증가 카운터는 그 다음 스냅샷에도 바뀐 값이 들어 있어
늦게라도 반드시 관측된다.

```
GameFramework.World.Transform
    int TeleportCount                         // 단조 증가

GameFramework.World.EntityMotionExtensions
    Teleport(entity, position)                // 위치를 쓰고 카운터를 +1 — 범용 API

GameFramework.Netcode.RenderCorrectionSmoother
    OnTeleport()                              // 스무딩과 목줄을 통째로 건너뛴다

GameFramework.World.WorldBase
    SaveState / LoadState 가 카운터를 함께 보관   // 재생이 텔레포트를 다시 트리거하지 않게

LOP-Shared  EntitySnap
    int teleport_count                        // 필드 추가
```

클라 `Reconciler`는 엔티티마다 마지막으로 본 카운터를 들고 있다가, 도착한 스냅의 값이 다르면
그 보정을 **텔레포트로 처리**한다. 내 것이든 남의 것이든 같은 경로다.

`NoSmoothUpdateDistance`는 **그대로 둔다** — 이제 텔레포트가 그것에 의존하지 않을 뿐, 진짜 랙을
위한 안전망으로는 여전히 필요하다.

> 함정: proto에 *필드*를 더하는 것은 MessageId를 바꾸지 않지만, 재생성 스크립트가 `MessageIds.cs`를
> 지워 ID가 밀린 전례가 있다. 서브스크립트를 개별 실행하고 ID diff를 확인한다.

## 7. 코스 배치와 굽기 전 검사

### 7.1 구간마다 다른 어법

`SkydiveCourseBuilder`의 `Winds` 표 옆에 `Lasers` 표를 둔다. 표가 곧 코스 설계다.

| 구간 | 어법 |
|---|---|
| 3000 → 2600 | 없음 — 조작을 익히는 자리 |
| 2600 → 2200 | 구멍 문지기 1 (회전 빔 하나, 느리게) |
| 2200 → 1800 | 구멍 문지기 2 (왕복 빔) |
| 1800 → 1400 | 격자 연습 — 통로를 가르는 고정 빔 한 층 |
| 1400 → 1000 | 격자 + 문지기 |
| 1000 → 600 | 격자를 빠르게 (점멸 추가) |
| 600 → 200 | 셋을 합친다 |

**구멍 문지기**는 선반 구멍 바로 위에 놓아 *"열릴 때 들어가라"* 를 강요한다. 구멍이 이미 코스의
핵심이라 결정이 선명하고, 다이브로 곤두박질치면 타이밍을 못 맞춰 **패러세일로 멈춰야** 한다 —
원 스펙이 원했던 반-다이브 압박이 여기서 나온다.

### 7.2 굽기 전 검사 세 가지

바람의 `FindImpassableSection`과 같은 자리에서, 표를 굽기 **전에** 검사한다. 여기서 걸리면 씬은
손대지 않은 그대로다.

1. **구멍이 열리는가** — 문지기 레이저가 한 주기 안에 구멍을 비우는 순간이 있는가. 고정 빔이 구멍을
   완전히 덮으면 거절한다. 이것이 없으면 **에러 하나 없이 판이 안 끝나는** 상태가 된다.
2. **부활 지점이 유효한가** — 선반 판 위에 있고, 구멍 밖이며, 그 자리에 상시 점등 빔이 걸치지
   않는가.
3. **회전이 읽을 수 있는가** — `|AngularSpeed| ≤ MaxAngularSpeedPerTick` (§4.5).

### 7.3 보이게 만들기 — 바람에서 배운 것

바람 슬라이스의 실패는 *"시뮬 값은 맞는데 화면에 인코딩이 안 돼 있었다"* 였다. 레이저는 보이는 것이
본질이라 위험이 낮지만, 조건이 하나 있다.

**켜지는 순간이 미리 읽혀야 한다.** 회전·왕복 빔은 다가오는 것이 보이므로 괜찮다. **점멸 빔은 예고
없이 켜지면 운이 된다** — 켜지기 **0.4초** 전부터 **가는 선**을 그려 예고한다. 예고는 그림일
뿐이고 판정에는 들어가지 않는다.

## 8. 코드가 어디에 사는가

| 레포 | 무엇 |
|---|---|
| **GameFramework** | `Transform.TeleportCount` · `EntityMotionExtensions.Teleport` · `RenderCorrectionSmoother.OnTeleport` · `WorldBase`의 저장·복원에 카운터 포함 |
| **LOP-Shared** | `Laser`(설정) · `LaserField` · `LaserGeometry.At(laser, t)`(순수) · `LaserSweep.TimeOfImpact(...)`(순수) · `SkydiveCheckpoints`(순수) · `LaserVolume`(맵 마커) · `EntitySnap.teleport_count` |
| **서버** | `SkydiveLaserSystem` — 판정하고 부활시킨다 |
| **클라** | `LaserView` — 같은 `At()`으로 그린다 · `Reconciler`에 카운터 비교 |
| **클라 에디터** | `SkydiveCourseBuilder`의 `Lasers` 표 · 검사 셋 · 시각물 굽기 |

`LaserVolume`이 **공용 패키지**에 있어야 하는 이유는 `WindVolume`·`SpawnPoint`와 같다: 맵 씬은 클라에서
굽고 서버가 읽는데, 스크립트가 한쪽에만 있으면 반대쪽에서 missing script가 되고 그 빈 컴포넌트가 씬
주입을 끊는다.

`LaserGeometry`·`LaserSweep`은 컨텍스트 없는 순수 커널이므로 **static**이고 `*System` 이름을 붙이지
않는다. `SkydiveLaserSystem`은 월드를 조작하므로 무상태 DI 인스턴스다.

### 8.1 `SkydiveWorld.Tick`에서의 자리

판정은 **이동 뒤**에 온다. 이번 틱에 지나온 경로가 있어야 판정할 수 있기 때문이다.

```
자세 → 바람 → 속도 → 이동 → [레이저 판정·부활] → 스태미나
```

부활이 스태미나를 만땅으로 만든 뒤 같은 틱에 스태미나 단계가 도는데, **부활이 활공을 끄므로 그 틱에는
소모가 없다**(소모는 활공 중에만 일어난다). 회복은 값을 더할 뿐이라 만땅을 넘지 않는다.

## 9. 테스트

순수 함수가 대부분이라 EditMode로 거의 전부 검증된다.

| 무엇 | 어떻게 |
|---|---|
| 각도 식 | 고정·회전이 틱에 따라 기대값. 삼각파는 `0 / +half / 0 / −half` 네 경계 |
| 점멸 | `OnTicks` 경계 앞뒤, 위상 어긋남, 상시 점등 |
| **터널링** | 다이브 속도로 얇은 빔을 지나가면 잡힌다 — **먼저 RED를 확인** |
| **회전 훑기** | 정지한 캐릭터를 회전 빔이 한 틱 안에 쓸고 지나가면 잡힌다 — 원 스펙의 서브스텝이 못 잡던 바로 그 경우 |
| CA 효율 | 멀리 있으면 반복 1회로 끝난다 |
| 스침 | 반복 상한에 닿으면 통과로 판정한다 |
| 체크포인트 | y → 선반. 첫 선반 위에서 죽으면 스폰 고도 |
| 텔레포트 | 카운터가 오르면 스무딩을 건너뛴다 / 그대로면 평소대로 녹인다 / 저장·복원이 카운터를 보존한다 |
| 빌더 검사 | **항상 닫힌 문지기**를 던지면 거절한다. 판 밖 부활 지점을 던지면 거절한다. 과한 회전을 던지면 거절한다 |

마지막 줄이 중요하다. 통과하는 배치만 검사하면 **검사기가 진짜로 막는지는 아무것도 검증되지
않는다** — 바람에서 같은 구멍을 겪었다.

## 10. 산업 표준 매핑

| 우리 것 | 대응 |
|---|---|
| `Teleport` / `TeleportCount` | Unity NGO `NetworkTransform.Teleport()`, Photon Fusion `NetworkTransform.Teleport()` — 둘 다 상태에 텔레포트 표시를 실어 보낸다 |
| `LaserSweep.TimeOfImpact` | **Mirtich 박사논문 §2.3.2**(3D 강체, CA 원전) · **PhysX**(문서가 자기 CCD를 *best-effort conservative advancement scheme*이라 명시) · Bullet `btContinuousConvexCollision`(Coumans가 회전까지 확장) · Box2D `b2TimeOfImpact`(용도가 *tunnel prevention*으로 명시) |
| 회전 위험을 따로 다루는 것 | PhysX가 *sweep 기반 CCD*(직선)와 *speculative CCD*(빠른 회전)를 나누고 5부터 병용을 허용한다 — 업계도 빠른 회전을 sweep이 못 잡는 별도 위험으로 취급한다 |
| `LaserField` / `LaserVolume` | `WindField` / `WindVolume`과 같은 자리. 볼륨이 그 안의 규칙을 정하는 Unreal `APhysicsVolume` 계열 |
| 상태 없는 위험물 = `f(tick)` | 결정론 시뮬의 표준 — 상태가 없으면 롤백할 것도 없다 |

## 11. 이번에 하지 않는 것

- **움직이는 강체**(회전 날개·셔터) — 레이저와 달리 밀어내기(collide-and-slide)라 캐릭터를 실제로
  움직여야 하고, 롤백이 유니티 콜라이더를 되감지 않는 문제를 정면으로 만난다. 별도 슬라이스.
- **경계**(코스 밖으로 나감) — 원 스펙 §3.5. 죽음 시스템이 생기면 그 위에 얹힌다.
- **클라의 죽음 예측** — 필요해지면 각도 룩업 테이블부터 넣는다(§4.6).
- **레이저 차단의 실시간 계산** — 각도 범위 제한으로 대체한다(§3.3).

## 12. 알고 가는 위험

1. **레이저가 결정을 만들지 못할 위험.** 바람에서 겪은 실패의 재발이다. 대응은 §7.3의 예고와
   §7.1의 구간별 어법이지만, 실제로 결정이 생기는지는 **플레이로만 확인된다.**
2. **벌의 크기가 안 맞을 위험.** 400 m는 대자 종단속도로 약 6.7초, 300초 판의 2%대다. 너무 무르면
   레이저를 무시하고 뚫는 것이 최적해가 된다. 부활 고도와 무적 시간을 튜닝 손잡이로 남긴다.
3. **CA 반복 상한에 자주 걸릴 위험.** 걸리면 그 판정은 관대하게 통과가 되므로, 잦으면 레이저가
   조용히 약해진다. 상한 도달 횟수를 계측 로그로 남긴다.
4. **왕복 지연만큼 늦는 부활.** 클라가 예측하지 않으므로 맞은 뒤 잠깐 더 떨어지다가 튄다. 이것이
   거슬리는지는 플레이로 판단한다.
