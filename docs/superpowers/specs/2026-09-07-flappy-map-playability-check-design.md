# Flappy 맵 플레이 가능성 검사 (Playability Check) — 설계

맵 씬 하나를 열고 메뉴를 누르면 **그 맵을 플레이할 수 있는지**를 세 각도로 재서 리포트 하나를
찍는 에디터 도구. 프로토타입(`Assets/Scripts/FlappyRaceSlice/FlappySimJudge.cs`)의 밸런싱
판정기를 지금의 멀티 구조로 옮기면서, **판정을 게임의 진짜 값·진짜 커널 위에 다시 세운다.**

---

## 1. 왜 지금인가

지금 Flappy는 **밸런싱 근거가 하나도 없다.** 로드맵에 남은 항목 중 여럿이 "숫자를 못 봐서 못
정한 것"이다 — 추격자 곡선이 적정한가, 대시 한 번이 몇 초를 벌어 주나, 오토파일럿이 왜 스턴
예산을 못 지키나. 이 도구가 그 숫자를 만든다.

프로토타입에는 도구가 넷 있었고(`FlappySimJudge`·`FlappyCourseScan`·`FlappyPlayRecorder`·
`FlappyAutoPilot`) 전부 **단일 씬 + `FindObjectOfType<FlappyPlayer>()`** 전제라 지금 구조에서
돌지 않는다. 더 나쁜 것은 그 판정기가 **프로토타입 물리를 복제해 들고 있다**는 점이다. 그 파일의
주석이 스스로 적어 뒀다:

> "전진속도와 낙마시간은 씬의 `FlappyPlayer`에서 읽는다 — **시뮬과 게임이 어긋나면 튜닝이 무의미하다.**"

**그 전제가 이미 깨져 있다.** 진짜 게임은 `FlappyMoveSystem` + `KinematicMover` +
`FlappyConfig`(마스터데이터)로 돈다. 도구가 읽는 값과 게임이 도는 값이 다른 곳에서 온다.

이 슬라이스는 넷 중 **하나**만 옮긴다. 그 하나가 배선이 맞는지 증명하면 나머지가 따라온다.

---

## 2. 무엇을 재는가

```
LOP/Debug/Flappy 맵 검사
    ① 클린런   — 한 번도 안 부딪히고 결승선까지 갈 경로가 있나 (자리별)
    ② 낌 지점   — 어디 끼어 못 나오는 자리가 있나              (기존 스캐너 흡수)
    ③ 스턴 예산 — 구간별로 몇 번까지 부딪혀도 안 잡히나
```

### 왜 셋이 한 리포트인가

세 답이 **서로를 해석해 준다.** 따로 보면 뜻이 안 선다.

| ① | ② | ③ | 읽는 법 |
|---|---|---|---|
| ❌ | — | — | 맵이 물리적으로 불통. 나머지는 볼 필요 없다 |
| ✅ | ❌ | — | 클린런은 되지만 한 번 발 헛디디면 끝. 낌 자리부터 고친다 |
| ✅ | ✅ | 앞이 빡셈 | 어려운 구간을 **뒤로** 옮기면 해결된다 |
| ✅ | ✅ | 넉넉 | 통과 |

프로토타입도 A+B+C를 한 번에 찍었다. 같은 이유다.

## 3. ① 클린런 — 어떻게 재나

프로토타입의 Tool A는 **개구 안이 아닌 상태를 버렸다** — 즉 "한 번도 안 부딪히는 경로가 있나"였다.
그 질문을 그대로 가져오되, 재는 방법은 세 가지 단순화를 거쳐 훨씬 작아진다.

### 3.1 단순화 1 — 무충돌이면 물리가 포물선이다

한 번도 안 닿는 경로만 세므로, 그 동안 커널이 하는 일은 `위치 += 속도 × dt`뿐이다.
collide-and-slide도 밀어내기도 돌지 않는다. **물리 자체는 근사가 아니라 정확히 같은 답이다.**
맵에서 필요한 정보는 "이 한 스텝 사이에 몸이 뭔가 스쳤나" 하나뿐.

> **정정(2026-09-10).** *자유공간 판정* 쪽에는 그 뒤 두 번째 근사가 들어왔다. 캐시가 스폰 순서에
> 따라 다른 답을 주던 버그를 고치면서(1600회 탐색 중 133회가 순서에 따라 갈렸다) **질의를 0.1m
> 격자 점으로 스냅해 재게** 했다. 덕분에 "누가 언제 묻든 같은 답"이 됐지만, 장애물이 각 축으로
> 최대 반 칸 부풀어 보인다. 즉 ❌는 이제 **"그렇게 부푼 장애물에 대해 경로가 없다"**는 뜻이다.
> 물리(포물선)는 여전히 정확하고, 근사는 높이 눈금과 이 자유공간 두 곳에 있다.

> 2026-09-07에 지면 훑기를 껐으므로(`groundProbe: 0`) "닿았다"는 이제 **몸 기준 sweep 둘**뿐이다.
> 이 도구의 무접촉 판정이 게임의 스턴 판정과 정확히 같은 뜻이 되는 것도 그 덕이다.

### 3.2 단순화 2 — 가로가 상수라 "열 = 틱"

`velocity.x = ForwardSpeed`(11) 고정이라 매 틱 정확히 **0.22m** 전진한다. x는 선택의 대상이 아니고,
코스(634m)는 **약 2,880개의 열**로 쪼개진다.

### 3.3 단순화 3 — 세로 속도가 이산이다

가장 큰 수확. 세로 속도는 연속값이 아니라 **사다리**다.

```
날갯짓  →  vy = FlapImpulse(23)  (덮어쓴다. 중력 다음에 오므로 늘 정확히 23)
그 다음  →  매 틱 Gravity × dt = 1.4 씩 감소, −MaxFallSpeed(30)에서 고정

  23 → 21.6 → 20.2 → … → −28.8 → −30 (이하 고정)
```

**"날갯짓하고 몇 틱 지났나"만 알면 세로 속도가 완전히 결정된다.** 값이 39가지뿐이다.
(출발 직후 `vy = 0`에서 시작하는 갈래가 하나 더 있어 실제로는 60가지쯤.)

| | 상태 |
|---|---|
| 프로토타입 | `(y, vy)` — vy를 눈금으로 뭉개야 했다 |
| **여기** | **`(높이 버킷, 날갯짓 후 경과틱)`** — vy는 근사 없이 정확 |

### 3.4 탐색

```
열   = 틱 (약 2,880개)              x는 매 열 +0.22 고정
상태 = (높이 버킷, 경과틱)        높이만 눈금(0.1m), 나머지는 정확
분기 = 날갯짓 / 안 함             두 갈래
버림 = 이 스텝에서 몸이 닿으면    ← 여기가 "무충돌"의 정의
```

열당 상태 수는 대략 `통로높이 200칸 × 60` ≈ 12,000개. 비트 한 장이면 **열당 1.5KB, 전체 4MB**라
2,880열을 전부 보관할 수 있다. (계획 문서가 실측 y 범위(89m)로 다시 잡음: 열당 약 69,000상태 =
8.7KB, 전체 **약 25MB** — 여전히 문제없다는 결론은 그대로.)

### 3.5 자유공간은 게으른 격자

"이 자리에 몸이 들어가나"를 매번 물리엔진에 묻지 않고 **0.1m 격자에 캐시**한다. 전체를 미리 채우면
570만 칸(≈12초)이라, **탐색이 실제로 밟는 칸만 채운다.** 통로 주변만 훑으므로 훨씬 적게 든다.

격자는 ①의 네 자리 탐색이 **공유**한다 — 가장 비싼 부분이라, 자리가 넷이어도 비용은 4배가 아니다.

### 3.6 경로 뽑기 — 부모 포인터가 필요 없다

보통 이런 탐색은 "어디서 왔는지"를 기록해야 경로를 뽑고, 그러면 메모리가 수백 MB로 뜬다.
**여기선 사다리 덕에 되짚기가 결정적**이라 필요 없다.

```
지금 상태가 (높이 y', 경과틱 k') 일 때 직전 상태는

   k' = 0  (날갯짓했다)  →  y = y' − 23 × dt,        경과틱은 아무거나
   k' > 0  (안 했다)     →  y = y' − vy(k') × dt,     경과틱 = k' − 1
```

계산 한 줄로 나온다. 그래서 **정방향으로 "닿나?"만 비트로 기록(4MB) → 역방향으로 경로 하나 추출**
두 패스면 끝이다. 눈금 반올림 때문에 역산이 버킷 경계에 걸릴 수 있으므로 인접 1칸까지 본다.

### 3.7 검증 — 진짜 커널로 재생해 증명한다

높이를 0.1m로 뭉갰으니 탐색이 찾은 경로가 진짜로도 되는지는 아직 모른다. 그래서 뽑아낸
**날갯짓 순서를 게임의 진짜 커널(`Step`, 곧 `KinematicMover`)로 재생**한다.

```
끝까지 무접촉  →  ✅ 증명됨. 눈금과 무관하게 확실
중간에 접촉    →  🟡 "탐색은 찾았으나 재생이 어긋남"
```

**근사로 빠르게 찾고, 정확한 것으로 검증한다.** 재생 비용은 경로 하나 × 2,880틱이라 무시할 만하다.

> **정정(2026-09-10) — 처방과 글자 둘 다.** ㉠ 글자는 `⚠️`가 아니라 **`🟡`**다(§6 주석 참고).
> ㉡ **"눈금을 조여라"는 통하지 않는 처방이라 코드가 명시적으로 거부한다.** 실측된 원인은 눈금이
> 굵어서가 아니라 **반올림 편향이 틱마다 누적**된 것이다 — 0.1m 눈금이 낙하 초반 한 틱치 하강
> (약 0.028m)보다 굵어 첫 몇 틱은 모델 안에서 아예 안 내려가고, 그 편향이 190번의 날갯짓에 걸쳐
> 약 7m로 쌓인다. 눈금을 좁혀도 비례해서 나아지지 않는다. 리포트는 이제 이 처방을 안내하지 않는다.
> ㉢ 그리고 **이 재생 경로는 더 이상 ①의 주 경로가 아니다.** 주 증명은 **봇 비행**이고, 탐색+재생은
> 봇이 못 갔을 때의 두 번째 답이다 — 그 결과가 아래 §8과 ROADMAP의 2026-09-07 항목에 있다.

### 3.8 자리마다 따로 — 공정성

맵의 스폰이 넷이고 **높이가 15m 벌어져 있다**(실측):

```
PlayerSpawn_1  x=−2  y=−6      PlayerSpawn_3  x=−2  y= 4
PlayerSpawn_2  x=−2  y=−1      PlayerSpawn_4  x=−2  y= 9
```

그러면 클린런 가능 여부가 자리마다 다를 수 있고, **그건 밸런싱이 아니라 공정성 문제다** — 자리
배정이 곧 불이익이 된다. "넷 중 하나라도 되면 ✅"로 뭉치면 정확히 이 문제가 안 보인다.
**자리마다 따로 돌리고 따로 보고한다.**

③ 스턴 예산은 넷 다 `x = −2`로 같고 추격자도 새도 x만 보므로 **자리와 무관하다** — 한 번만 센다.

### 3.9 막혔을 때 무엇을 알려주나

`❌`만 찍으면 고칠 수가 없다. 프로토타입이 하던 것을 이어받는다.

```
❌ 막힘 — x=412.6에서 생존 상태 0
   최협 회랑: x=380  생존 상태 34개  높이 폭 0.7m
```

"어디서 끊겼나"와 "그 직전이 얼마나 아슬아슬했나"를 같이 낸다. 폭이 0.7m인데 몸이 0.9m면
원인이 바로 보인다.

## 4. ③ 스턴 예산 — 어떻게 재나

### 4.1 식

새의 위치는 `−2 + 11 × (경과 − 멈춰있던시간)`, 추격자는 닫힌 식(`FlappyChaserCurve.XAt`).
잡힘 판정은 `새 뒷면(x − BodyRadius) ≤ 벽`이다. 잡히지 않을 조건을 **멈춰 있어도 되는 시간**으로 풀면:

```
허용 정지시간(t) = t − (추격자위치(t) − 출발x + BodyRadius) / ForwardSpeed
허용 스턴 횟수(t) = 허용 정지시간 ÷ StunTime
```

### 4.2 상한 하나 더 — 무적

스턴이 끝나면 무적(`InvulnTime` 0.6초)이 붙어 그 사이엔 다시 안 걸린다. 즉 **연속으로 맞아도
한 번당 1.4초**가 최소 주기다.

```
n번 맞으려면 최소  (StunTime + InvulnTime) × n − InvulnTime  초가 걸린다
```

이걸 안 넣으면 예산을 과소평가한다. **"아무리 못해도 이보다 빨리 맞을 수는 없다"** 는 물리적 상한이다.

### 4.3 현재 맵의 계산 결과

코스 `x −2 → 632`(634m), 클린런 57.6초. 추격자 시작 −60, 초기 7, 가속 0.075, 상한 10.

| 경과 | 클린런 위치 | **허용** 누적 | **가능한** 최대 | |
|---|---|---|---|---|
| 10초 | 108m | 10번 | 7번 | 안전 — 못 채운다 |
| 20초 | 218m | 13번 | 14번 | ⚠️ 여기서부터 |
| 30초 | 328m | 16번 | 21번 | |
| 40초 | 438m | 17번 | 29번 | |
| 57.6초 | 632m (골인) | 19번 | 41번 | |

> **가장 빨리 잡히는 경우 = 19.0초 · 14번째 스턴.**
> 즉 **출발 후 19초(코스의 33%)까지는 아무리 부딪혀도 안 잡힌다.**

이 사실은 아무도 재 본 적이 없다. 의도한 것이면 그대로 두고, 아니면 `ChaserStartX`나
`ChaserInitialSpeed`를 조일 근거가 된다. **도구를 짓기 전에 종이로 낸 값이므로, 도구가 같은 값을
내는지가 첫 검증이 된다.**

### 4.4 정직하게 밝힐 가정

이 계산은 **스턴이 아닌 시간엔 `ForwardSpeed`로 온전히 전진한다**고 본다. 실제로는 무적 중에도
벽에 막히면 못 나가므로 **실제는 이보다 나쁘다.**

그래서 이 숫자는 **상한**이다 — "이 횟수를 넘으면 반드시 잡힌다". 넘지 않는다고 안 잡히는 건 아니다.
그 차이(막혀서 기는 경우)는 **② 낌 검사가 따로 잡는** 영역이라 한 도구 안에서 서로를 보완한다.
리포트에도 이 가정을 한 줄 적는다.

## 5. 코드가 앉는 자리

```
Assets/Scripts/MapTools/            ← 새 asmdef. 순수 C#, 유니티 에디터 비의존
    CleanRunSearch.cs                  상태공간 탐색 + 되짚기 (자유공간을 함수로 주입받음)
    StunBudget.cs                      추격자 곡선 + 스턴 손해 + 무적 상한
    PlayabilityReport.cs               세 결과 → 리포트 문자열

Assets/Scripts/Editor/
    FlappyMapPlayabilityCheck.cs    ← 메뉴 + 맵 콜라이더·마커·마스터데이터 읽기 + 검증 재생
                                       (기존 FlappyMapTrapScanner를 흡수·개명)

Assets/Tests/EditMode/MapTools/     ← 새 테스트 asmdef
```

가르는 기준은 **"유니티가 필요한가"** 다. 탐색과 산수는 자유공간 판정을 함수로 주입받으면 유니티
없이 돌고 테스트도 된다. 콜라이더·`SpawnPoint`·`FinishLine`·마스터데이터를 읽는 껍데기만 에디터
쪽에 둔다. 이 레포에 이미 있는 모양(`FlappyRaceSlice.Logic` ↔ 그 테스트 asmdef)과 같다.

> **테스트를 위해 기존 어셈블리를 옮기지 않는다** — 새 코드를 처음부터 테스트되는 자리에 둘 뿐이다.

### 기존 스캐너 흡수

`FlappyMapTrapScanner`가 이미 갖고 있는 넷은 셋 다 쓰는 토대라 **그대로 살린다**.

| 기존 | 새 쓰임 |
|---|---|
| `TryReadFlappyConfig` | ~~③이 쓴다~~ **정정(2026-09-07 최종 정리)**: ③이 쓰는 건 더 뒤에 더한 `TryReadFullConfig`(추격자 값까지 포함)다. 같은 `.bytes`를 두 번 읽던 중복은 없앴다 — `TryReadFullConfig`가 읽은 `LOP.FlappyConfig`에서 `FlappyShape`를 골라 담는 `ShapeFrom` 하나로 합쳤다(`TryReadFlappyConfig`는 삭제됨). |
| `TryReadBounds` | ①②가 쓴다 |
| `Step(state, flap, …)` | ①의 검증 재생이 쓴다 |
| `EscapesBySearch` | ②로 남는다 (①과 목표가 달라 따로) |

**낌 판정 로직 자체는 한 줄도 안 고친다.** 파일과 이름만 옮긴다.

### 출발점·결승선은 맵이 정한다

서버 룰(`FlappyRaceRuleSystem`)이 `SpawnPoint`/`FinishLine` 마커를 `FindObjectsByType`으로 읽는다.
**도구도 같은 마커를 같은 방법으로 읽는다** — 새 설정이 없고, 게임과 도구가 같은 진실원본을 본다.

## 7. 테스트

순수 부분은 자유공간 판정을 함수로 주입받으므로 유니티 없이 합성 맵으로 돌린다.

| 무엇을 | 어떻게 |
|---|---|
| 빈 하늘이면 클린런 성공 | 자유공간 = 항상 참 |
| 몸보다 좁은 통로면 실패 | 높이 0.5m 틈(몸 0.9m) → ❌ + 막힌 x 보고 |
| **날갯짓을 찾아낸다** | 안 누르면 부딪히고 누르면 넘는 턱 → ✅ + 그 위치에 날갯짓 |
| **자리마다 답이 다르다** | 위쪽만 막힌 합성 맵 → 아래 ✅ / 위 ❌ |
| 되짚기가 진짜 경로를 낸다 | 뽑은 날갯짓 순서를 다시 앞으로 굴려 같은 곳 도착 |
| 스턴 예산 산수 | §4.3의 손계산(19.0초 · 14번째)과 일치 |
| **무적 상한이 실제로 문다** | `InvulnTime = 0`이면 답이 달라져야 한다 — 안 달라지면 그 코드는 죽은 것 |

**각 테스트를 일부러 깨뜨려 빨강을 확인하고 넘어간다.** 이 프로젝트는 "초록인데 아무것도 안 지키는
테스트"를 한 슬라이스에서 여섯 개 만든 적이 있다.

에디터 껍데기(메뉴·콜라이더·마커 읽기)는 단위 테스트하지 않는다 — 배선뿐이고, 틀리면 도구가
아예 안 돈다.

## 8. 알고 남기는 약점

> ⚠️ **측정으로 뒤집힌 전제 — 2026-09-07, 실제 맵 실행.** 아래 원문은 "검증 재생이 잡는 실패는
> 한 방향(❌)뿐이고, 눈금이 문제가 되는 건 그 ❌ 쪽뿐"이라고 적었다. **실측은 반대를 보였다** —
> 실제 맵의 네 스폰 전부 탐색이 경로를 **찾았는데(✅ 쪽)** 재생 증명에서 전부 어긋났다. 즉
> 눈금이 문제를 일으킨 건 아래 표의 "✅ 잡힌다" 칸이었지 "❌ 못 잡는다" 칸이 아니다. §3.7이
> 설계한 대로 재생이 그 어긋남을 잡아냈으니 검증 메커니즘 자체는 옳게 작동했다 — 틀린 건
> "❌만 조심하면 된다"는 아래의 방향 가정이다. §12의 관련 항목도 같은 이유로 틀렸다. 원인
> 분석과 전체 경위는 `docs/ROADMAP.md`의 "Flappy 맵 플레이 가능성 검사" 항목 참고. 아래
> 원문은 그 자체로 틀린 진단의 기록으로 남겨 둔다 — 조용히 지우면 이 문서를 나중에 읽는
> 사람이 "처음부터 이랬나"로 헷갈린다.

검증 재생은 **한 방향만** 잡는다.

```
탐색 "된다"   → 재생이 확인하거나 반박한다     ✅ 잡힌다
탐색 "안 된다" → 진짜 안 되는지 확인 못 한다    ❌ 못 잡는다
```

격자 눈금(0.1m)이 너무 굵어 실제로는 지날 수 있는 통로를 막힌 걸로 볼 수 있는데, 그 경우는 검증할
방법이 없다. 그래서 **`❌`가 나오면 "눈금을 0.05로 조여 다시 눌러 보라"를 리포트에 같이 찍고**,
눈금을 상수 하나로 노출해 둔다.

## 10. 결정 기록

### 대시를 탐색에서 뺀다

대시는 0.2초 동안 중력 없이 전진 2배로 **수평 직선**을 그린다. 날갯짓만으로 못 지나는 긴 수평
통로가 대시로는 열릴 수 있고, 대시 한 번은 2.2m 이득이라 스턴 한 번(−8.8m)의 1/4을 되받는다.
그런데 대시에는 **게이지**가 있어(`DashChargeBase` 0.13/초, 낙하 중 `+1.2/초`) 상태에 넣으면
탐색 차원이 `(높이, 경과틱)` → `+충전량`으로 늘어 상태 수가 십수 배가 된다.

**빼기로 한다.** 세 가지 이유다.

1. **대시 없이 무충돌이 되는 맵이 좋은 맵이다.** 대시를 써야만 지나갈 수 있는 구간이 있다면 그건
   대시 활용처가 아니라 함정이다.
2. **보수적 답이 밸런싱에 더 쓸모 있다.** "빼고도 통과"면 안심이고, "빼면 실패"일 때 그때 물으면 된다.
3. **나중에 얹을 수 있다** — 차원 하나 추가라 구조를 안 바꾼다.

### 스턴 예산은 구간별 곡선으로 낸다

예산은 고정값이 아니다. 간격은 출발 직후가 가장 좁고(50~58m) 그 뒤로 계속 벌어져서, 같은 난이도
구간이라도 **앞에 있으면 치명적이고 뒤에 있으면 여유**다. 숫자 하나(최악)로 뭉개면 그 사실이
사라진다. **구간별 누적 허용선**이면 "출발 직후 20초는 3번 이하로 설계하라"처럼 맵 디자인에 바로
대응된다. 비용도 거의 같다 — 어차피 시간에 따른 간격 곡선을 계산해야 한다.

## 11. 산업 표준 매핑

| 개념 | 표준 용어 | 어디서 |
|---|---|---|
| 만든 레벨을 끝까지 갈 수 있는지 자동 검사 | **playability check** | PCG(절차적 레벨 생성) 문헌 표준 |
| 같은 뜻의 좁은 변형 | beatability | 마리오 레벨 생성 연구 — A\* 에이전트로 검증 |
| 그걸 *어떻게* 재나 | reachability analysis (상태공간 탐색) | 방법 이름이지 도구 이름이 아니다 |
| 레벨 검사 → 리포트라는 *모양* | Map Check | 언리얼 에디터. 다만 그쪽은 에셋 설정 오류지 플레이 가능성이 아니다 |
| 여러 검사를 돌려 리포트 | Auditor | Unity Project Auditor |

도구 이름은 **`FlappyMapPlayabilityCheck`** 로 한다 — PCG 표준어를 그대로 쓴다. 세 검사의
공통분모가 정확히 "이 맵을 플레이할 수 있나"이기 때문이다(낌 = 불가, 클린런 없음 = 상한이 없음,
예산 0 = 불가). 이 레포는 `FlappyMapTrapScanner`·`FlappyRaceMap.unity`처럼 **`Map`** 을 쓰므로
(프로토타입만 `Course`) 거기에 맞춘다.

하위 검사 이름:

```
① 무충돌 경로   CleanRunSearch    (탐색 방법은 reachability, 답하는 건 "클린런이 되나")
② 낌 지점       TrapScan          (기존 로직 그대로, 이름만 짧게)
③ 스턴 예산     StunBudget
```

프로토타입의 `SimJudge`("판정기")는 **어디에도 없는 임의 명명**이라 가져가지 않는다.

  — §8 맨 위 2026-09-07 정정 참고.** 실제 맵에서 돌려 보니 문제는 `✅` 쪽에서 났다(네 스폰
