# 캐릭터끼리 부딪힌다 — 접촉 충격량과 몸 접지

스카이다이브에서 사람 몸을 **실제 물리에 가깝게** 부딪히게 만든다. 서로 통과하지 않고, 부딪힌
속도를 주고받고, 남의 머리 위에 세게 떨어지면 지면에 떨어진 것과 같이 죽는다.

> 사용자 표현: *"카트라이더가 충돌이 없으면 재미가 반감되지 않나? 그 이치로 접근중이야."*
> 부딪힘이 **결과를 만들어야** 한다 — 라인이 틀어지고, 코스에서 밀려나고, 밟히면 손해를 본다.

---

## 1. 왜 지금

스카이다이브는 메커니즘이 거의 다 들어갔고(코스·바람·레이저·문·착지 충격) 재미를 판정하는
구간에 있다. 그런데 **사람이 서로를 통과한다.** 스펙 `2026-08-30-skydive-game-mode-design.md`
§4.1이 *"좁은 길목에서 막아서기가 전략이 된다"* 고 요구해 둔 것이 비어 있는 상태다.

준비는 이미 되어 있다.

| | 상태 |
|---|---|
| 겹침 계산 (`BodyOverlap`) | ✅ 있음 — 순수 산수, 물리엔진 비의존 |
| 속도 교환 (`VerticalBounce`) | ⚠️ 있음, 단 **세로 성분만** |
| 짝 순회·결정론 (`BodyCollisionSystem`) | ✅ 있음 — id 순서·절반씩 밀기 |
| 남도 예측 (`CharactersPredictedSyncPolicy`) | ✅ 스카이다이브에 이미 등록됨 |
| 스카이다이브가 부르는가 | ❌ **안 부름** |

`VerticalBounce` 주석이 이 슬라이스를 미리 적어 뒀다:

> 가로로도 밀리는 게임은 이걸 쓰면 안 되고, **접촉 법선 방향의 일반 충격량이 필요하다.**
> 식 자체는 그 일반형을 y 성분으로 제한한 것이라, 일반화할 때 참고할 수 있다.

`SkydiveWorld.Mutation`에도 자리가 예약돼 있다 — *"슬라이스 6의 몸싸움이 이 사이에 들어온다"*.

### 1.1 Flappy는 만들었다 버렸다 — 그 이유가 여기서는 성립하지 않는다

`FlappyWorld` 주석에 기록돼 있다:

> 몸싸움을 두면 **남의 새도 클라가 굴려야 하는데**, 남의 입력은 오지 않으므로 "안 눌렀다"로 굴러
> 상대가 날갯짓할 때마다 크게 어긋났다. … **보정의 80%가 옆에 새가 있을 때 났고, 원인이 몸싸움이었다.**

버린 원인은 **탭이 순간의 사건이라 예측할 방법이 없다**는 것이다. 스카이다이브 입력은 성질이
정반대다.

| | Flappy | Skydive |
|---|---|---|
| 입력 | 탭 = 순간 사건 | 자세 = **계속 유지되는 값** |
| 남을 굴리려면 | 다음 탭을 맞혀야 한다(불가능) | "하던 자세를 계속한다"고 두면 된다 |
| 매 틱 스냅샷에 오는 것 | 위치뿐 | 위치 + **자세·활공·스태미나** |
| 자세 변경이 속도에 미치는 방식 | 즉시(`velocity.y = FlapImpulse`) | **가속도**를 바꾼다 → 오차가 `Δa·t²/2` |

**이것은 근거이지 결론이 아니다.** 그래서 §7이 측정과 판정 기준을 못박는다.

## 3. 커널 — `ContactImpulse`를 만들고 `VerticalBounce`는 그 위에 얹는다

식은 이미 일반형의 y 제한이다. 스칼라를 벡터로 바꾸면 끝난다.

```
지금  vy' = vy - (1+e) × (Δvy × nᵧ)   × 0.5 × nᵧ
후    v'  = v  - (1+e) × dot(Δv, n)   × 0.5 × n
```

`0.5`는 등질량 축약이다 — 일반형 `j = -(1+e)·v_closing / (1/m₁ + 1/m₂)`에서 `m₁ = m₂ = m`을 넣고
`v' = v + (j/m)n`으로 정리하면 `0.5`가 남는다. 질량을 나중에 도입하려면 이 상수 자리를 연다.

**그대로 두는 것 둘.**

- `RestingSpeed = 1.5f` — 이보다 느리게 다가온 접촉은 튕기지 않는다(`e`를 0으로 본다). 얹혀 있을
  때 미세하게 떠는 것을 막는 장치라, 사람 위에 서는 것을 허용하는 이번 결정에서 오히려 더 필요하다.
- **이미 멀어지는 중이면(`closing >= 0`) 건드리지 않는다.** 안 그러면 떨어져 나가는 몸을 다시 붙인다.

### 3.1 `VerticalBounce`는 지우지 않는다 — 래퍼로 남긴다

클라 프로토타입 `Assets/Scripts/FlappyRaceSlice/FlappyBird.cs`가 `VerticalBounce.ResolveVy`를 직접
부른다(단독 플레이 스파이크라 World Core를 쓰지 않는다). 지우면 그쪽이 깨진다.

**`VerticalBounce.ResolveVy`를 `ContactImpulse` 위의 얇은 래퍼로 바꾼다.** 식이 한 벌만 남고,
기존 `VerticalBounceTests`가 **그대로 일반형의 회귀 검사**가 된다.

### 3.2 축 제한은 커널이 아니라 시스템에 둔다

Flappy는 전진 속도가 상수라 가로로 밀리면 안 된다. 그 사정은 **게임의 사정**이지 물리식의 성질이
아니므로, 커널은 순수한 3D로 두고 `BodyCollisionSystem`이 "어느 축으로 밀릴 수 있는가"를 인자로 받는다.

**제한은 결과가 아니라 입력에 건다.** 마스크를 씌운 속도·법선을 커널에 넣고, 돌아온 값에서 허용된
축만 쓴다.

```
masked(v) = v * axisMask        (성분별 곱, 정규화하지 않는다)
결과 = ContactImpulse.Resolve( masked(vSelf), masked(vOther), masked(n), e )
```

**결과에만 마스크를 씌우면 안 된다.** 다가오는 속도(`dot(Δv, n)`)가 전 축으로 계산되어, 가로
상대속도가 있을 때 세로 답이 달라진다. 입력에 씌우면 세로 마스크가 옛 `VerticalBounce`와
**정확히 같은 식**으로 축약된다.

- Flappy = 세로만 → **옛 `VerticalBounce`와 결과가 같아야 한다**(§8 회귀 테스트로 박는다)
- Skydive = 전 축

## 4. 틱 순서 — 표준에서 갈라지는 지점

### 4.1 표준(Box2D)은 쪼개져 있다

```
① 속도 적분 → ② 속도 제약(충격량) → ③ 위치 적분 → ④ 위치 제약(밀어내기)
                    ↑ 이동 앞                          ↑ 이동 뒤
```

이 순서의 전제는 **접촉이 여러 틱 지속되고, 매 틱 반복해서 조금씩 푼다**는 것이다. 쌓인 상자
더미를 안정적으로 세우기 위한 구조이며, 위치 보정을 일부러 덜 해서(겹침을 조금 남겨) 접촉이
이어지게 한다.

### 4.2 우리 속도에서는 그 전제가 깨진다

```
틱 N  : A가 B 위 1m. 겹침 없음         → ② 아무 일 없음
        이동 → A가 B 속으로 0.7m 파고듦
        ④ 밀어내서 떼어냄
틱 N+1: 이미 떨어져 있음               → ② 아무 일 없음
                                          ↑ 부딪혔는데 속도 교환이 한 번도 없었다
```

초속 90 m/s에서는 위치 보정이 남기는 여유(`Slop = 0.01`)가 한 틱을 못 버틴다. **밟았는데 아무 일도
일어나지 않는다** — 이 슬라이스의 가장 극적인 장면이 조용히 실패한다.

**그래서 감지→해소를 한 번에, 이동 뒤에 둔다.** `BodyCollisionSystem`이 원래 그 모양이다(한 호출이
밀어내기와 속도 교환을 함께 한다). 표준에서 벗어나는 지점이므로 이유를 여기에 남긴다.

> `SkydiveWorld`에 예약돼 있던 자리(이동 **앞**)는 이 슬라이스에서 **이동 뒤로 정정한다.**
> 예약 당시에는 "모두의 속도가 정해진 뒤"라는 조건만 보고 적었고, 위 실패 경로는 검토되지 않았다.

맵 밀어내기(`Depenetrate`)가 이동 앞에 남는 것은 이유가 다르다 — **sweep이 "시작부터 겹친" 것을
히트로 못 내기 때문**이며, 몸싸움은 sweep을 쓰지 않으므로 그 이유가 걸리지 않는다.

### 4.3 뚫고 지나가지 않는가 — 검산 (⚠️ 처음 계산은 틀렸다)

몸은 반지름 0.4 m · 높이 1.8 m이므로 캡슐 심(축) 선분 길이는 `1.8 − 0.8 = 1.0 m`이고, 겹침 조건은
두 심 사이 거리 `< 0.8 m`다.

#### ❌ 처음에 한 계산 — 잰 창이 틀렸다 (기록으로 남긴다)

가로 오프셋 `dx`에서 **겹침이 유지되는** 세로 구간(창)을 재고, 그것이 한 틱 이동보다 넓으니
안전하다고 결론지었다.

```
창 = 2 × ( 1.0 + √(0.64 − dx²) )        1.0 = 심 길이,  0.64 = (2r)²
```

| | 값 |
|---|---|
| 최대 상대속도 | 다이브 90 − 활공 6 = **84 m/s** |
| 한 틱(50 Hz) 상대 이동 | **1.68 m** |
| 창 — 수직 정렬(`dx = 0`) | 2 × (1.0 + 0.8) = **3.6 m** → 여유 2.14배 |
| 창 — 최악(`dx → 0.8`, 거의 스침) | 2 × (1.0 + 0) = **2.0 m** → 여유 1.19배 |

여기서 **"Conservative Advancement는 넣지 않는다 — 산술적으로 필요가 없다"** 고 적었다.

#### ✅ 정정 — 겹침이 아니라 **세로 접촉**이 필요했다

위 계산은 **"한 틱은 겹친 채로 지나간다"** 만 증명한다. 그런데 이 슬라이스가 원하는 것은 겹침이
아니라 **세로 접촉 방향**이다 — 밟은 쪽이 접지로 잡히고 세로 속도를 주고받으려면 접촉 방향에
세로 성분이 있어야 한다(`BodyCollisionSystem`이 `pushDir.y`로 접지를 보고한다).

그런데 두 심 선분이 **세로로 겹치는 동안에는 `dy = 0`** 이라 접촉 방향이 **순수 가로**가 된다.
즉 세로 접촉이 존재하는 구간은 위 창 전체가 아니라, 심 선분이 **안 겹치는** 부분뿐이다:

```
세로 접촉이 나오는 발 높이 차 d ∈ (1.0, 1.8)      너비 0.8 m
   1.0 = 심 선분 길이(그 아래로는 두 선분이 겹쳐 dy = 0)
   1.8 = 몸 높이(머리 위에 정확히 선 자세 — 그 위로는 아예 안 닿는다)
```

| | 값 |
|---|---|
| 한 틱 상대 이동 | **1.68 m** |
| 세로 접촉 창 | **0.8 m** |
| 여유 | **0.48배 — 불합격** |

한 틱이 창보다 **두 배 넓다.** 겹치기 직전 틱의 발 높이 차 `d₀`는 (1.8, 3.48)에 고르게 분포하고,
한 틱 뒤 `d₁ = d₀ − 1.68`은 (0.12, 1.8)에 고르게 떨어진다 — 그중 창 안(1.0~1.8)은 **48%뿐**이다.
나머지 절반은 "안 겹침 → 가로 방향으로 깊이 겹침"으로 한 틱에 건너뛰어, **밟혔는데 접지도 세로
속도 교환도 없이 옆으로 밀려난다.** 최종 리뷰(2026-09-09)가 잡아낸 C1이 이것이다.

#### 그래서 채택한 것 — 훑어서 얻은 접촉 방향

`BodySweep`(`LaserSweep`과 같은 Mirtich Conservative Advancement)이 **틱 안에서 둘이 처음 닿는
시각**을 찾아 그때의 방향을 접촉 방향으로 쓴다. 깊이 파고들기 전의 방향이라 위에서 밟은 접촉은
세로로 나온다.

- **훑기는 방향만 정한다.** 자리와 속도는 여전히 **틱이 끝난 모습**에서 푼다 — 충돌 시각으로
  되돌리면 이미 끝난 맵 이동과 싸우게 되고 몸을 벽 속으로 밀어 넣을 수 있다.
- **걸음 수 상한은 그 짝의 상대 이동 거리에서 뽑는다**(상수가 아니다). 낙하 속도를 올려도
  상한이 따라오므로 "조용히 다시 못 찾기 시작"하지 않는다.
- **결론을 못 낸 접촉(스치는 짝은 수렴이 느리다)은 버리지 않고** 옛 방식(틱 끝 모습)으로 물러선다 —
  버리면 몸이 그냥 통과한다.
- 세로로만 밀리는 게임(Flappy Race)은 이동 전 자리를 안 넘기므로 **동작이 그대로**다.

> **교훈.** 검산은 맞았는데 **잰 대상이 틀렸다.** "뚫고 지나가나?"를 물었지만 실제로 필요한 것은
> "세로로 닿는가?"였고, 두 창은 2.0 m와 0.8 m로 두 배 넘게 다르다. 원 계산을 지우지 않고 남겨
> 두는 이유다.

### 4.4 확정된 틱 순서

```
자세 → 바람 → 이동속도 결정 → 맵 밀어내기 → 이동(맵 sweep)
  → 몸싸움           밀어내기(절반씩) + 속도 교환
  → 접지·착지 충격 확정
  → 스태미나
```

## 5. 접지와 착지 충격을 이동에서 떼어낸다

지금은 `MoveBlockedByMap`이 접지와 착지 충격을 직접 쓴다.

```csharp
groundState.IsGrounded = result.grounded;                       // 맵 기준으로 덮어쓴다
impact.DownwardSpeed = (wasGrounded == false && result.grounded && ...) ? ... : 0f;
```

닿는 대상이 **맵과 사람 둘**이 되면 이 판단은 이동의 일이 아니다. 별도 단계로 뺀다.

```
① 이동 전 기록 : 아래로 가던 속도, 직전 접지 여부
② 이동(맵)     : 위치·속도 갱신 → 맵에 닿았나
③ 몸싸움       : 밀어내기 + 속도 교환 → 아래쪽으로 사람에 닿았나
④ 확정         : 접지     = 맵 OR 사람
                 착지 충격 = (직전에 안 닿았는데 지금 닿았고 아래로 가고 있었으면) 그 속도
⑤ 스태미나     : ④의 접지를 읽는다 (지금과 동일)
```

**규칙이 한 곳에만 남는다** — "무엇에 닿았든 판단은 하나"가 코드로 드러난다.

`BodyCollisionSystem`은 이를 위해 **아래쪽 접촉이 있었는지**를 돌려준다(밀어내는 방향의 세로
성분이 위를 향하면 = 내가 상대 위에 있다).

### 5.1 결과로 따라오는 것

- 남의 머리에 다이브로 박으면 **죽는다** — 착지 규칙(`> 15 m/s`)이 그대로 적용된다
- 활공으로 살살 내려앉으면 **설 수 있고 스태미나가 찬다**
- 밟힌 쪽은 운동량을 받아 **아래로 밀린다**

### 5.2 덤 — 잠복 버그가 이 자리에서 닫힌다

`GroundState.IsGrounded`는 2026-09-08에 `SkydiveSavedState`로 들어갔지만, 읽고 쓰는 자리가 이동
안쪽에 박혀 있어 추적이 어려웠다. ④가 접지의 **유일한 writer**가 되면 그 문제가 구조적으로 사라진다.

## 7. 측정 — 스카이다이브에서 잰다

### ① 예측 오차의 크기 (EditMode, 영구)

스펙 `2026-08-30-skydive-game-mode-design.md` §7.3이 지정한 그대로: 순수 시뮬로 **"9틱 전 상태에서
9틱을 예측한 결과 vs 진실"** 을 **자세를 바꾼 창 / 안 바꾼 창**으로 나눠 잰다.

자세를 안 바꾼 창은 정확할 수밖에 없다(그대로 굴리면 된다). **자세를 바꾼 창의 오차가 이 설계의
진짜 위험**이다. 테스트로 남겨 두면 낙하 물리를 만질 때 자동으로 다시 검사된다.

### ② 그 오차가 아픈가 (라이브 A/B)

Flappy가 원인을 짚어낸 지표를 그대로 쓴다 — **옆에 사람이 있을 때 보정량이 늘어나는가.**
몸싸움을 껐다 켜서 두 번 잰다. 사람이 하는 플레이라 두 판이 똑같을 수는 없으므로, **같은 판을
비교하는 것이 아니라 "옆에 사람이 있는 구간 / 없는 구간"의 차이를 각 판 안에서 본다** — 판끼리
비교하면 조작 차이가 결과에 섞인다.

| | 기준 |
|---|---|
| 보는 값 | recon **max** (avg 아님 — 러버밴딩은 최악의 순간에 보인다) |
| 합격 | 몸싸움 켠 판의 max가 **0.3 m 미만** |
| 불합격 | 0.3 m 이상이 반복 → 원 스펙 §4.3 **입력 지연** 검토 |

`0.3 m`의 근거: 보정 스무딩 문턱이 0.06 m(이 아래는 눈에 안 보인다)이고 텔레포트가 1.8 m다. 그
사이에서 "부딪힐 때만 잠깐 커지는" 정도가 0.3 m다.

측정은 **MPPM 클론**에서 한다 — 메인 에디터가 부하를 지고 있으면 잡음이 판정을 삼킨다.

## 8. 테스트

| 대상 | 무엇을 |
|---|---|
| `ContactImpulse` | 정면 충돌에서 속도가 교환된다 / `e = 0` · `e = 1` 극단 / 이미 멀어지면 무변경 / 스치면 거의 안 바뀐다 |
| 축 제한 | **세로만 고르면 옛 `VerticalBounce`와 결과가 같다** (Flappy 회귀 박제) |
| `BodyCollisionSystem` | 짝을 어떤 순서로 넘겨도 결과가 같다 / 절반씩 민다 / 아래쪽 접촉을 옳게 판별한다 |
| `SkydiveWorld` | 사람 위에 세게 떨어지면 죽는다 / 살살 내려오면 서고 스태미나가 찬다 / 옆치기는 안 죽는다 |
| 되감기 | 같은 입력을 재생하면 같은 결과 |
| 예측 오차 | §7① |

**전부 일부러 깨뜨려 빨강을 확인한 뒤 넘어간다.** 이 영역은 "테스트가 검사하는 척만 하는" 사고가
두 번 났다(레이저 굽기 검사기가 실제 레이저를 못 보고 있었고, `HalfSpaceQuery.Raycast`가 항상
`None`을 돌려주는 스텁이었다).

## 9. 산업 표준 매핑

| 우리 것 | 대응 |
|---|---|
| `ContactImpulse` | Box2D `b2ContactImpulse` · Unity `Collision.impulse` · `ForceMode.Impulse` |
| 등질량 반발 식 | 강체 충돌의 표준 임펄스 해법 (`j = -(1+e)v_rel / (1/m₁ + 1/m₂)`) |
| 감지→해소를 이동 뒤 한 번에 | 이산 충돌 방식(discrete collision response). Box2D식 split은 §4.2 이유로 채택하지 않음 |
| 축 제한을 시스템이 갖는 것 | 게임별 제약이라 커널 밖. Quantum이 systems=인스턴스 / `FPMath`=static util로 가르는 것과 같은 선 |

## 11. 알고 시작하는 위험

1. **좁은 구멍에서 둘이 낄 수 있다.** 선반 구멍·문에 둘이 동시에 들어가면 몸싸움이 한 명을 벽으로
   밀고 맵이 다시 밀어내며 떨 수 있다. 산술로 미리 정할 수 없어 **플레이로 본다.**
2. **남의 머리는 발판이 아니다.** 밟고 서 있어도 상대가 옆으로 가면 따라가지 않고 캡슐 곡면을 타고
   미끄러져 떨어진다. 자연스러운지도 플레이로 판단한다.
3. **밟기가 강할 수 있다.** 발판이 귀한 게임에서 남의 머리에서 스태미나를 채우는 플레이가 생긴다.
